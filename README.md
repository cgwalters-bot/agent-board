# agent-board

> This text was generated by an LLM (cgwalters-bot). cgwalters has not reviewed it yet.

agent-board is the board and control side of a coding-agent coordinator that keeps its whole record on GitHub: a project board, its issues and their pull requests. It reads the board, previews repairs, decides what job an issue should get and follows the pull requests that come back. [agentic-job](https://github.com/cgwalters-forge/agentic-job) runs one agent job safely; the [tracker](https://github.com/cgwalters-forge/tracker) repository holds the bounds and the token. agent-board does not run agents itself.

## Where it fits

The pitch is "gh-aw, but more flexible, supporting containers, and helping secure the rest of CI". agent-board is the board and scheduling side of that; agents run through agentic-job, and [Why not GitHub Agentic Workflows](https://github.com/cgwalters-forge/agentic-job/blob/main/README.md#why-not-github-agentic-workflows) explains that choice.

gh-aw's `update-project` and `dispatch-workflow` safe outputs let an agent edit a project item or start a workflow. On top of that, agent-board keeps the [job plan](docs/job-plans.md) on the issue, dispatches it once per plan with a record on the issue, can [batch](docs/job-plans.md#batching) small sibling sub-issues into one run, [holds back](docs/job-plans.md#overlap) runs that overlap open bot pull requests, and previews board repairs with `reconcile plan`.

What it lacks today: reconcile repairs are previewed but not applied from CI ([#7](https://github.com/cgwalters-forge/agent-board/issues/7)); a default board still needs `project init` for Turn, Run and Result fields; result discovery and linking the pull request remain manual. Operators can now look up a dispatch run and apply its board update at a terminal.

## Commands

All read commands work live (`--owner ORG --project N`, `GH_TOKEN` with project and issue read) or offline (`--snapshot FILE`). Output follows `gh`: `--json`/`--jq`, gh exit codes; the binary is also built as `gh-agent-board`.

| `reconcile plan [--emit]` | Preview deterministic repairs as safe-output proposals; never applies them. |
| `check proposals --as ID` | Refuse proposals outside an identity's assignment/field policy (`policy/agents.toml`). Not complete output validation. |
| `project init` | Create the Turn, Run and Result fields if missing (writes). |
| `project status-update --status on-track\|at-risk\|off-track` | Publish a project status update (writes); see [docs/status-updates.md](docs/status-updates.md). |
| `item add [--priority P1] [--turn OPTION]`, `item edit` | Add an issue / set fields; add defaults Turn to Coordinator when available. Write only with `--apply`. |
| `ask create\|list\|resolve` | Put a question to the operator as a `question` issue and mark the blocked item Needs human; write only with `--apply`. |
| `ask add`, `ask read`, `ask resolve D<n> TEXT` | Use one configured operator-editable [decisions document](docs/decisions.md); writes require `--apply`. |
| `request dispatch`, `run record [--apply] [--caller OWNER/REPO --kind implement --yes]` | Print `gh workflow run` argv for agentic-job's [dispatch caller](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/dispatch.md); propose Run/Result updates or apply with the operator's GH_TOKEN. CI still uses independent check/apply only. |
| `dispatch ISSUE --dry-run\|--apply` | Print, or send once and record on the issue, the `workflow_dispatch` request the newest accepted [job plan](docs/job-plans.md) comment proposes ([#46](https://github.com/cgwalters-forge/agent-board/issues/46)); `--batch N` adds small sibling sub-issues to one run ([batching](docs/job-plans.md#batching)), and `--bot LOGIN` holds it back while bot pull requests or runs overlap it ([overlap](docs/job-plans.md#overlap)); `--collaborators-only` refuses issues that are unlocked or have input from non-collaborators, and `--status-app-id ID` admits that GitHub App's status comments ([collaborator input](docs/job-plans.md#collaborator-input)). |
| `epic plan ISSUE --dry-run` | Check the newest accepted [epic plan](docs/epic-plans.md) and print its mutations. |
| `epic apply ISSUE --config FILE` | Preview an epic plan, or apply once with the bot's token and `--apply`; a claim prevents replay after partial failure. |
| `poll --dry-run\|--apply` | Preview one pull request poll pass, or explicitly apply its steps in `--follow` repositories. `--config` reads trusted repository-owned settings; apply requires `--dispatch-workflow` or the file's `dispatchWorkflow`. `--review-workflow` selects eligible exact-head job reviews and repeated `--fix-pool` selects fix pools. See [poll behavior and limits](docs/design.md#current-implementation-limits). |
| `supervise health\|trigger\|execute` | The controller's supervisor: a read-only health report, whether its agent runs, and an executor whose one action is a capped, fixed-brief triage or research dispatch on an open issue without a supervisor note. See [supervisor limits](docs/design.md#current-implementation-limits). |
| `apps create --org ORG --role ROLE [--config FILE]` | Register a role's GitHub App through GitHub's manifest flow (one browser click), write its private key only to `--key-file` (0600) or `--key-stdout`, and print the app id and the names to store; reuses an app with `--key-stored`. See [docs/apps.md](docs/apps.md#agent-board-apps-create). |
| `test project` | Staging integration test; holds a write token. Not for local use. |

`output check`/`output apply` are unsupported; sweeping is disabled.

### Forgejo board (read only)

Forgejo's API has no projects, so `--board-config agent-board.json` (trusted,
default branch) can make the board the issues of some Forgejo repositories
instead. It is read by `snapshot create`, `project view`, `item list`,
`item view` and `reconcile plan`; nothing writes to Forgejo.

```json
{
  "board": {
    "forge": "forgejo",
    "url": "https://forge.example/",
    "tokenEnv": "FORGEJO_TOKEN",
    "repositories": ["example/intake"],
    "membership": {"label": "agent-board"},
    "recorders": [1234]
  }
}
```

`membership` is `{"label": NAME}` (open and closed issues with that label) or
`"open"` (every open issue). Priority comes from one `priority/P1`..`priority/P3`
label and Turn from one `turn/coordinator`, `turn/operator`, `turn/worker`,
`turn/external`, `turn/none` or `turn/<policy identity>` (read as Worker) label;
zero, two or an unknown value leaves the item's fields incomplete and
`reconcile plan` says why. `blocked/<reason>` labels fill a Blocked list. Run and
Result come from the newest comment by a `recorders` user id (not login, which
can be renamed and re-registered) whose first line is
`<!-- agent-board-run: URL -->` or `<!-- agent-board-result: URL -->`; with no
recorders, comments are not read. Coverage is complete only when the issues read
match the listing's `X-Total-Count`. Status and close reasons do not exist there,
so they are null. Without `board`, or with `"forge": "github"`, nothing changes.

## Install

Rust supporting edition 2024; no prebuilt releases, and not installable with `gh extension install`.

Live HTTPS requests use the platform trust store through rustls-platform-verifier,
not bundled Mozilla roots. Install sandbox egress proxy or corporate/private CA
certificates in the system trust store; TLS certificate and hostname verification
remain enabled. The offline client test checks this verifier selection, not an
end-to-end TLS handshake with a locally installed CA.

    cargo install --git https://github.com/cgwalters-forge/agent-board agent-board
    agent-board item list --snapshot fixtures/board.json   # from a clone, no token

## New organization

### Rehearse without credentials

From a clone of this repository, after [installing](#install), run:

```sh
agent-board item list --snapshot fixtures/board.json
agent-board reconcile plan --snapshot fixtures/board.json --emit
agent-board project view --snapshot fixtures/board.json --json project,coverage
```

All three should exit 0 without `GH_TOKEN` or `GITHUB_TOKEN`. The fixture is
sample data, not your staging board: listing it proves the CLI works, the plan
is a proposal rather than a write, and coverage describes which facts the
snapshot contains. This does not prove live token access, dispatch, inference,
review or container isolation. The offline CLI test executes these README
commands so this starting point stays reproducible.

### Connect one lane

Bring up one lane at a time; a working scripted trial does not establish a
scheduled real-agent/review loop. Keep writes and scheduling off until their
previews and prerequisites are checked.

1. **Choose the identities and install.** Start with agentic-job's
   [Try it](https://github.com/cgwalters-forge/agentic-job/blob/main/README.md#try-it)
   and [Install](#install) above (Cargo with edition-2024-capable Rust, not
   `gh extension install`). Choose a public target repository on `main`, a
   trusted caller repository that holds the workflow/bounds, and an existing
   organization Project v2. These are separate identities, not an assumption
   that tracker or its project is already provisioned for your organization.

2. **Prove model-free dispatch first.** Follow the
   [ten-minute scripted trial](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/dispatch.md#ten-minute-scripted-trial):
   copy [dispatch.yml](https://github.com/cgwalters-forge/agentic-job/blob/main/.github/workflows/dispatch.yml)
   and [dispatch.toml](https://github.com/cgwalters-forge/agentic-job/blob/main/.github/agentic-job/dispatch.toml),
   replace the local reusable call with a reviewed compatible SHA, set exact
   `repos` and keep `bases = ["main"]`. Commit to the protected default branch,
   allow the actions, then dispatch `kind=research` against an existing issue.
   This two-file route does not need `hosted.toml`; it differs from the README's
   three-file `example.yml` trial. Implement also needs the apply environment/PAT.
   Bounds protect documentation too: explicitly list intended documentation
   files in `unprotected_files`, rather than broadly unprotecting the repository.

3. **Provision inference and network before selecting a real agent.** Follow
   [Switch to a real agent](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/dispatch.md#switch-to-a-real-agent)
   for `AGENT`, `AGENT_MODEL`, `AGENT_RUNNER`, `INFERENCE_URL`,
   `INFERENCE_AUDIENCE`, optional runner/agent configuration and `APPLY_ENVIRONMENT`.
   The current [reusable workflow](https://github.com/cgwalters-forge/agentic-job/blob/main/.github/workflows/agentic-job.yml)
   has no `tailscale-*` inputs. Hosted access to a private broker needs
   caller-owned composition: policy → agent (`prepare` → pinned tailnet join
   with tailnet DNS disabled → `secure-host` → `run`) → check → apply; see
   [example-compose.yml](https://github.com/cgwalters-forge/agentic-job/blob/main/.github/workflows/example-compose.yml).
   Match [broker admission](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/inference.md#which-workflows-a-broker-admits)
   to the identity: repository-narrowed `any_workflow` for composition versus
   SHA-specific `called_workflows` for reusable jobs. Adapting that example into
   a production private-broker dispatch still requires operator work.

4. **Install review independently.** Follow review's
   [Another repository](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/review.md#another-repository)
   instructions to copy and retarget the caller and three trusted
   `workflow/review.*` files, including permissions; its
   [Configuration](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/review.md#configuration)
   covers model/broker variables and admission. Choose merge policy and rules
   separately: an agent verdict is not human authorization. If enabling
   `AGENT_REAL_REVIEWS`, allow Actions review submission and consume exact-head
   submitted reviews, not verdict comments.

5. **Provision and read the board before writes.** Check access and schema
   against [Operator decisions](docs/design.md#8-operator-decisions).
   Pre-create Status options `Triage`, `Backlog`, `Todo`, `In Progress`, `Draft`,
   `In Review`, `Blocked`, `Needs human`, `Done`, `Cancelled`, and the Priority
   single-select with `P0`, `P1`, `P2`. `project init` writes only missing
   Turn/Run/Result fields, not those options. For asks, provision the `question`
   label and an assignable operator. Start with `snapshot create` and
   `reconcile plan` previews. To copy/edit the scheduled preview, use
   [reconcile.yml](.github/workflows/reconcile.yml) and
   [Provisioning the reconcile preview](#provisioning-the-reconcile-preview):
   retarget owner/project/repository and keep its read token only in the
   main-only `staging-project-read` environment, with Projects/Issues Read and
   no write secret. Live writes are separate: the
   [live template](live/board-test.yml) documents protected `Main`/`PAT`, Projects
   and Issues Read and write, organization approval and token-owner project
   access; `GITHUB_TOKEN` permissions do not grant organization Projects writes.

6. **Preview an accepted plan, then wire scheduling/polling deliberately.** Use
   [job-plan dispatch](docs/job-plans.md#dispatch), beginning with
   `dispatch ISSUE --dry-run` and configured caller/workflow/operator/planner.
   Apply needs a writer's user token and records the plan before dispatch.
   The plan's `runner`/`pool` inputs target
   [tracker's dispatch caller](https://github.com/cgwalters-forge/tracker/blob/main/.github/workflows/dispatch.yml),
   not the generic or existing staging caller. Copy and retarget
   [agent-board.json](https://github.com/cgwalters-forge/tracker/blob/main/.github/poll/agent-board.json):
   its owner/project selection, exact repository lists, caller and identities
   must match your setup. Its optional `brokerOutage` names tracker's
   broker outage issues, so a fix or continuation run that failed during one
   gets its round back instead of `needs-human`, and its optional
   `operatorAnswers` takes the operator's comment on a `needs-human` pull
   request as the answer, starting a round on it, and its optional
   `rebaseRounds` rebases an approved pull request that only conflicts
   without using its fix rounds; see
   [poll limits](docs/design.md#current-implementation-limits). Read the
   [board scheduler](https://github.com/cgwalters-forge/tracker/blob/main/README.md#the-board-scheduler)
   and audit dispatch/fix bounds, profiles and pools before enabling
   `BOARD_DISPATCH=apply`. Identities must come from repository-owned
   configuration, never dispatcher-set workflow inputs.
   [Tracker's poll.yml](https://github.com/cgwalters-forge/tracker/blob/main/.github/workflows/poll.yml)
   still runs the live legacy poll alongside agent-board preview. CLI `poll
   --apply` support does not enable that preview lane: do not run two appliers.

**Staging is not a green end-to-end example.** The walkthrough's
[live fixture 38547777384](https://github.com/cgwalters-forge-stage/board-test/actions/runs/38547777384)
read project 2 and board-test and created a scratch issue, but adding it to the
project failed with `FORBIDDEN: Resource not accessible by personal access token`;
cleanup succeeded. This does not identify the exact token setting at fault.
The staging caller used older `tailscale-*` inputs without `runner`/`pool` or
explicit `SAFE_OUTPUTS_PAT` forwarding; simply advancing its pin is incompatible.
Its review was an older fake review (review callers disabled), and no scheduler
was present. These are walkthrough observations, not a current setup guarantee.

**Operator-only handoff:** provision/authorize tailnet OAuth, federated workflow
identity, tags/ACLs (document changes in the private wiki); admit the specific
repository/workflow identities and finite budgets at the broker; keep model
credentials only at the broker; provision protected apply/reconcile/live-test
secrets and effective Projects access, including organization approval and
token-owner access. The walkthrough could not inspect variable names (403) or
project schema/access with its own token; connectivity, secret correctness and
end-to-end success remain unverified. No secret values are needed in this guide.

### Repeat the staging trial

After the prerequisites above are satisfied, use a disposable staging repository
and project selected by the operator's trusted repository configuration. Do not
reuse a production board or enable a scheduled applier for this trial. Follow
the [job-plan format and dispatch commands](docs/job-plans.md): the caller must
actually accept the plan's inputs before proceeding.

Use at most three small, independent issues: one research task and two harmless
documentation tasks. Add them with `item add` previews before explicitly applying
each addition. For each issue, have an accepted writer post a plan, inspect
`dispatch --dry-run`, then explicitly dispatch it once. Stop at the first failed
prerequisite; do not work around bounds, expand token permissions blindly, or
replace an ambiguous dispatch record to force a retry. Keep batching and
scheduled dispatch off so each result can be attributed to its own plan.

Inspect the dispatch record and linked Actions run, then follow
`agent-board run record --help` to preview the matching Run/Result update before
applying it. Verify any returned PR and exact-head review separately; neither a
successful dispatch nor a recorded run proves the task succeeded. Result linking
and reconcile repair application are not automatic (see [Commands](#commands)).

Report the date, reviewed workflow revision, non-secret configuration names,
issue/plan/run/PR links, exact commands and exit statuses, expected versus actual
results, and every undocumented guess or workaround. Mark unattempted steps as
unverified, including container execution and CI security claims unless actually
tested. Record any cleanup failures; only remove scratch objects created by the
trial. Fix the first blocker and repeat from the published instructions rather
than treating this checklist as evidence of a successful end-to-end run.

## Workflows here

Locally, with that repository at `../actions` or `FORGE_ACTIONS`, run `just lint`.
- `reconcile.yml`: every ten minutes on main, reads cgwalters-forge-stage project 2 with a read-only environment token and uploads `reconcile plan --emit` proposals as an artifact; nothing is applied. Until `STAGING_PROJECT_READ_TOKEN` is provisioned in that environment, each run logs a notice and skips successfully instead of failing.
- `review.yml`: cgwalters-forge/actions' [cgwalters-review](https://github.com/cgwalters-forge/actions/blob/main/.github/workflows/cgwalters-review.yml) wrapper of agentic-job's review, pinned by commit, on pull requests and `/review` comments.
- `site.yml`: builds and link-checks the [documentation site](https://cgwalters-forge.github.io/agent-board/) in `site/`, a Starlight rendering of this README and `docs/` like [agentic-job's](https://cgwalters-forge.github.io/agentic-job/), after secure-host with `contents: read`; on main it uploads the Pages artifact and a separate deploy-only job publishes it. Locally, `just site-test` and `just site-build`.

### Provisioning the reconcile preview

To preview whole-board status drift on every poll, add `statusReconcile` to the
caller's trusted default-branch `agent-board.json` (not workflow inputs):

```json
{
  "statusReconcile": {
    "enabled": true,
    "project": "https://github.com/orgs/example/projects/1",
    "repositories": ["example/intake", "example/code"],
    "runRepositories": ["example/runners"]
  }
}
```

This is off by default. Supply the board with `--owner`/`--project` or
`--snapshot`; it must match the configured project. Each poll prints a
`status-preview=` plan to stderr, even with `poll --apply`: **board proposals are
never applied**. `reconcile plan --config agent-board.json` uses the same rules;
`--emit` lowers proposals, retaining issue versus PR identity. Existing poll
settings, including `operator`, remain required. There are at most 500 additional
read requests per pass; exceeding the bound fails without publishing a partial
status plan. Preview errors are reported on stderr and in the final exit status,
but do not stop the existing PR poll from running. Run URLs are only read in
`runRepositories` so editable board text
cannot send token-bearing reads to arbitrary repositories or API paths.

The opt-in rules inspect every in-scope issue and PR without Lead, Workflow or
assignment exemptions: closed/merged content or a nonempty set of all-merged
linked PRs becomes Done; an open `needs-human`/`question` label or an outstanding
operator review request becomes Needs human; otherwise a draft PR or active
recorded Run becomes In Progress. A completed recorded Run releases In Progress
or Needs human to Todo. Terminal facts win, then human asks, then active work.
Missing run data is unknown, not proof that no live job exists. Linked PR facts
come from complete native PR-valued project fields. Existing coverage and status
schema checks still block incomplete or ambiguous repairs.

Plan preconditions are not sufficient authority to apply these proposals. An
independent checker must reread the decisive facts for each reason: content and
linked PR states for `terminal_content`, open labels/current-head review requests
for `open_human_ask`, and draft state plus the recorded run's identity/status for
`active_work` or `inactive_work`. A board Run URL is not proof of run/item
correlation; completion of that run alone is not proof of no other live job.

Relative to tracker#443: missing Status (Triage) and terminal-drift previews were
already present; the above rules extend them to PRs and current work facts.
This opt-in mode deliberately maps all closed content to Done, including
NOT_PLANNED; the default legacy rules retain Cancelled. Tracker closure with a
reason, Draft-item action generation, gist/waiting-patch inventory, complete
live-job absence detection, umbrella/epic classification, Priority defaults and
off-board inventory remain deferred: these need facts or proposal types not
provided by this board snapshot. None are silently inferred from board prose.

Before enabling the preview, create the dedicated `staging-project-read`
environment here. Set its deployment branches and tags to **Selected branches
and tags**, with only a **branch** rule for `main` and no tag rules. Do not use
“Protected branches only”: that can admit other protected branches. Keep changes
to this environment's protection and secrets restricted to trusted administrators.
Provision `STAGING_PROJECT_READ_TOKEN` only as a secret of that environment, with
organization Projects **Read** and repository Issues **Read** on the staging
repository (plus GitHub's required Metadata read). It is a separate read-only
token, not the staging write PAT. Remove any repository or organization secret
of the same name accessible to this repository, so a branch workflow cannot
bypass the environment by omitting `environment`. If previously provisioned
as a repository secret, revoke it and provision a new read-only token in the
environment. This preview environment must contain no write credentials.
Before eventual live apply, cgwalters must set the staging **apply**
token's organization Projects permission to **Read and write**. No write token
is needed or used for this preview.
