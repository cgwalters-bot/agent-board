# Forges

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

agent-board is meant to work on any forge that has issues and something that
can hold a board. Each forge is read into the same normalized snapshot, so
`item list`, `item view` and `reconcile plan` work unchanged on top of it. What
works today:

| Forge | Board reads | Writes, plans and dispatch |
|---|---|---|
| GitHub | Projects v2 | Yes |
| Forgejo | Issues of configured repositories, fields from labels; pass identity and broker pacing | Stage 3 epics; stage 4 apply: claims, starts, recovery, leases and one rerun; no activation ([contract](#a-forgejo-pass)) |
| GitLab | No | No ([#294](https://github.com/cgwalters-forge/agent-board/issues/294)) |

Existing dispatch callers still use GitHub Actions. The backend boundary also
offers opt-in native Forgejo start, recovery, active inventory, status, rerun,
admission, reservation binding and release ([dispatch](dispatch.md#native-forgejo-adapters-not-activated)).
The Forgejo pass selects them for stage 4; other dispatch callers remain GitHub-only.
The design's approach to other forges, capability
negotiation rather than weakened guarantees, is in
[Rust boundaries](design.md#7-rust-boundaries).

## GitHub

The board is an organization Project v2, chosen with `--owner ORG --project N`
and read with a `GH_TOKEN` that has project and issue read. Status, Priority,
Turn, Run and Result are project fields ([setup](setup.md#connect-one-lane)).
Every command works here. Only `github.com` is supported for live reads.

## Forgejo

Forgejo's API has no projects, so `--board-config agent-board.json` (trusted,
default branch) can make the board the issues of some Forgejo repositories
instead. It is read by `snapshot create`, `project view`, `item list`,
`item view` and `reconcile plan`; these commands do not write to Forgejo.

```json
{
  "board": {
    "forge": "forgejo",
    "url": "https://forge.example/",
    "tokenEnv": "FORGEJO_TOKEN",
    "repositories": ["example/intake"],
    "membership": {"label": "agent-board"},
    "recorders": [1234]
  }
}
```

`membership` is `{"label": NAME}` (open and closed issues with that label) or
`"open"` (every open issue). Priority comes from one `priority/P0`..`priority/P3`
label and Turn from one `turn/coordinator`, `turn/operator`, `turn/worker`,
`turn/external`, `turn/none` or `turn/<policy identity>` (read as Worker) label;
zero, two or an unknown value leaves the item's fields incomplete and
`reconcile plan` says why. `blocked/<reason>` labels fill a Blocked list. Run and
Result come from the newest comment by a `recorders` user id (not login, which
can be renamed and re-registered) whose first line is
`<!-- agent-board-run: URL -->` or `<!-- agent-board-result: URL -->`; with no
recorders, comments are not read. A recorder marker must have valid, equal
`created_at` and `updated_at` timestamps; an edited marker makes the item
incomplete rather than falling back to an older record. This stops an ordinary
issue writer editing a recorder's comment; the administrator and same-second
limitations [below](#comments-recorders-and-editors) still apply.
Coverage is complete only when the issues read match the listing's
`X-Total-Count`. Close reasons are null. Status is also null by default;
`board.statusLabels: true` opts into the six [Status labels](#labels-and-status).
Missing Status is null, while duplicate or unknown Status labels make the item
incomplete. Old boards ignore Status labels and retain `status_field_absent`.
The GitHub token variables are never sent to the Forgejo host.
Without `board`, or with `"forge": "github"`, the board is a GitHub project.

`url` may be `https://` or `http://` and may carry a port, as for a Forgejo
reached inside a cluster (`http://forgejo-http.forgejo.svc:3000/`); it may not
carry credentials, a query or a fragment. Plain HTTP sends the token
unencrypted with each request, so the CLI warns on stderr when an `http://` URL
names a host that is not loopback, a private, link-local or unique-local
address, a single-label name, or a name ending in `.svc`, `.cluster.local`,
`.local` or `.internal`. Item identities keep only the host name, without
scheme or port, so two instances on one host cannot share a board. Run and Result
marker URLs must still be `https://`.

Forgejo drops a label name the repository does not have from `labels=`, and
with none left lists every issue ([issue.go#L448-L461][fj-labels-filter]), so
the reader refuses a listed issue without the membership label rather than
let a deleted or renamed label widen the board. The write side keeps that.

### Board-write library boundary

`Forge::board_write` is a deterministic controller primitive, not an
agent-output publisher. It refuses by default on other backends. Forgejo
implements one scoped label replacement, issue open/close, append-only
comments, and plan claims with their receipts. The Forgejo pass's applying
stage 4 calls its claim and receipt operations; no deployed caller is activated. Its explicit
`apply` argument previews when false; each attempted mutation consumes the
caller's remaining write cap, including an ambiguous failure. Each operation
has at most 32 read requests and each comment at most 16,000 characters.

The authenticated `/user` id must be a configured recorder. Targets must be
configured issue identities, not pull requests. Membership labels remain
required. Label names resolve to one exclusive id from complete bounded
repository and organization listings; no labels are created. Labels are read
again immediately before writing and read back afterward, preserving unrelated
labels. State and comments are also read back. Repeating an observed effect
does not write again; errors hold rather than retrying automatically. Any
edited recorder comment on the issue holds every comment, claim and receipt
write, a replay included, and open membership is checked on the last issue
read before the write. There is no atomic compare-and-swap in Forgejo, so a
concurrent change after the final read is still possible.

A claim names a recorder's unedited plan comment, a job plan with
`agent-board-dispatch` or an epic plan with `agent-board-epic-apply`, as
`COMMENT-ID@CREATED`, its creation time in UTC
([below](#claims-and-recovery)). It is refused where any
recorder already claimed that plan, a repeated or ambiguous claim included,
and after writing it counts only if the thread read again shows it as the
earliest. A concurrent writer's comment can get a lower id and become visible
only later, so this needs one pass per board, as the pass's lease gives.
Receipts are further comments by the claim's author whose first line
is `<!-- agent-board-receipt: CLAIM-ID -->`; plain comments may not start with
a claim or receipt line. `Forge::plan_claim` reads a plan's earliest claim and
its receipts back for recovery. Stage 4 chooses and claims job plans and
uses the native dispatch adapters. Stage 3 claims epic plans, and creates
issues with `Forgejo::create_issue`, which reads the new issue back (number,
repository, poster id, title, body and labels) and never repeats the POST.
Its writer reaches the work repositories and `epics.repository` without the
membership label, open issues only ([epics](#epics)). Arbitrary
agent proposals must still go through independent check/apply; the CLI's
`output check` and `output apply` remain unsupported. No caller settings or
deployment are changed here.

## A Forgejo pass

This is the contract for a second, separate `agent-board pass` that drives a
Forgejo board ([#271](https://github.com/cgwalters-forge/agent-board/issues/271),
tracker#786). **The end-to-end pass is not built**. `agent-board pass --config FILE`
now accepts a Forgejo board: identity checks, then stage 1's
broker usage and grants, stage 3's epics where `epics` is set (#514,
[below](#epics)), and stage 4's candidates, holds and runs in flight
(#522, [below](#stage-4-in-preview)), with one `not built on Forgejo yet` line
for each of stages 2, 5 and 6. Preview writes and dispatches nothing;
`--apply` supports stages 3 and [4](#stage-4-apply). A preview can be
[recorded and replayed](#recording-and-replay). `--fix-bounds`, and
`--record` with `--replay` (a seeded recording), are refused before
credentials are read.
The library board primitives above implement only part of the write contract;
native dispatch/run/lease primitives implement the sections below independently
of scheduler wiring. Offline tests are not live proof.
The remaining driver wiring covers Status/snapshots (#523) and live CI (#515). [`fixtures/forgejo/pass-contract.json`](../fixtures/forgejo/pass-contract.json)
holds its per-stage capability inventory and a verdict for every
[pass option](pass.md#one-configuration-file); a test fails when an option is
added to that table without one.

Native semantics were checked against Forgejo
[v17.0.1][fj-tag] (`363f3dc30beef902b187af5a5244ff7af44901e6`, the newest
stable release on 30 October 2026; v15.0 is the LTS) and its v17.0 Actions
docs; the links below are that commit. A deployment on another version proves
these again before it is enabled. Nothing assumes GitHub's GraphQL, Projects,
sub-issues, `lastEditedBy` or ref updates; where Forgejo has no equivalent,
the feature is refused, not approximated.

### One instance, one host, one token

The instance is the configuration's `board`, as for the reads (`url`,
`tokenEnv`, `repositories`, `membership`, `recorders`), in the pass's own
trusted file, with `"forge": "forgejo"`. Its
scope is fixed by that file alone:

* **Host.** Every request goes to the canonical `url` (scheme, host and port
  as given, under its path). A URL from a response (an `html_url`, a run link,
  a marker) is data: it is checked to be on that instance before it is
  followed or written anywhere, and it never carries the token elsewhere. There
  is no GitHub request, no GitHub fallback and no GitHub token: the token
  variables `GH_TOKEN` and `GITHUB_TOKEN` are neither read nor sent, as today.
  The broker's `/usage` and grant are read without any forge token, as today.
* **Repositories.** Reads and writes stay within the board's `repositories`,
  `workRepositories`, `epics.repository`, `dispatchRepo` and the publication
  issues, all repositories of this instance. A plan, issue, comment or run that
  names anything else is held, not followed.
* **Token.** One bot user's access token from `tokenEnv`, with the scopes
  `read:user`, `read:issue`, `write:issue`, `read:repository` and
  `write:repository` ([scopes][fj-scopes], [route groups][fj-api-scopes]) and
  no admin, organization or `all` scope. At the start of every preview or applying pass,
  `GET /user` must name `bot` with an id in `recorders`; otherwise nothing is
  written. Not the Actions automatic token: its user's id is negative, so it
  can be no recorder, and the comments it writes wake no workflow
  ([notifier_helper.go#L137-L150][fj-actions-user]).
* **Identities.** `operator` and `bot` stay logins, each resolved to its user
  id once a pass (bot through `GET /user`, operator through `GET /users/{login}`), and each id must be in `recorders`, or
  nothing the pass reads counts as theirs: a login can be renamed and
  registered again, an id cannot. Every trust decision compares ids.

Two instances are two configurations, crons, callers and tokens. A Forgejo
pass reads nothing of a GitHub board and publishes nothing there, and the
other way round. Its usage and hold snapshots, where set, go only to an issue
of a private repository on its own instance.

### Capabilities by stage

Each verdict is `same` (forge-independent), `native` (the Forgejo mechanism
below, to be built) or `refused`: a Forgejo pass refuses a configuration that
sets a refused option, and what depends on a refused capability holds until a
reviewed mechanism replaces it.

The preview rejects every explicitly supplied refused option, even `false`,
an empty collection or a nested setting, with
`unsupported_capability: OPTION: REASON` from the contract, before token lookup.
It also temporarily rejects `holds`, usage publication
(`usage.repository`/`usage.issue`) and `usage.probe` (#523). Leases and reruns
are accepted. Sweep and revisit remain deferred: follow-ups to #513 must own
their scheduling and publication semantics; neither is silently enabled by
this preview or claimed as built by the native adapters.

Stage 1 accepts broker-only `usage: {"url": "http://broker.internal/usage"}`;
GitHub still requires its publication repository and issue. It reuses the
GitHub pass's snapshot, grants, pacing and `usage:` rendering, but never its
publication or snapshot fallback. Missing readings hold pools; failed reads
report failures, with grants still deciding when available. No broker is no
reading, never a reason to access GitHub. The Forgejo transport and separate
credential-free broker share the 500-request/15-minute pass bound. The preview
is opt-in through a trusted config file, with no caller or adapter activation.

| Stage | Forgejo | Refused |
| --- | --- | --- |
| 1 Usage | Broker read unchanged; the snapshot is a new comment in a private repository (`GET /repos` `private`) | |
| 2 Follow pull requests | Nothing | All of it: fix, rebase, continuation and answer rounds, reviews, required checks and their reruns, merges and merge queues, `--fix-bounds` |
| 3 Epics | `epic` issues, children from relationship comments (below), plan and receipt comments, creating issues, Priority labels, closing, a planning run | Sub-issue APIs (none exist) |
| 4 Schedule | Candidates, Priority, holds from labels and [dependencies][fj-deps], WIP from complete run listings, pool pacing, plan claims, dispatch, one rerun, file-based leases | Overlap waivers, the start breaker, `replanAfterDays`, `bodyPlans`, direction |
| 5 Status | Derived as on GitHub, round-tripped through `status/` labels | Close reasons |
| 6 Cost | Nothing | Publishing to a `data` branch |

PR follow-up is the largest gap: a Forgejo pass follows no pull request, and
every option of it (`follow`, `pr.*`, `state`) is refused, with `maintain`,
whose digest reads the operator's pull requests across GitHub. Work whose run
opens a pull request must still hold its issue until a person merges or closes
it. GitHub names a pull request's closing issues; no such field was found in
Forgejo's pull request API, so stage 4 matches them itself (#522, below), and
an item whose match cannot be read is held, as an unreadable hold is today.

### Stage 4 in preview

A preview's stage 4 applies the GitHub pass's rules to what it reads of this
instance, in the same order, and prints the same lines: `hold wip|pools|budget: …`,
`candidates: N (…)`, `hold OWNER/REPO#N: why`, and `wip: no slot left; …`.
It reads no plan, so where GitHub would print `start triage|implement …`, it
prints `would start OWNER/REPO#N pool=P` (or `held by --max-dispatch: would
start …`), choosing the pool from stage 1's snapshot.

* **Runs in flight.** The caller's `waiting`, `blocked` and `running` runs,
  listed twice by the dispatch adapter's
  [active inventory](#dispatch-and-runs) within its page cap. Each counts
  toward `wip`, and its title (`KIND OWNER/REPO#N (POOL)`, from the caller's
  `run-name`) holds that issue. A listing that fails, or is cut short, holds
  every new start and is a failure.
* **Candidates.** The open issues (with `membership`'s label, if any) of each
  board repository that is also a work repository, at most 4 pages of 50; a
  longer or shifting listing is an incomplete board, which starts nothing.
  Issues labelled `epic` or `question` are not work. A live epic's child
  ([below](#epics)) is a candidate whoever opened it, ranked first by its
  epic's Priority; any other issue only where its poster's id is the bot's or
  the operator's, and others are counted as opened by others. With `epics`
  set, a candidate's own newest parent comment is read before it starts: one
  naming an epic that is not live, or that does not list it back, holds it
  as `epic-not-live`.
* **Rank.** By the one `priority/` label, P0 first, unlabelled last, then age.
  Two `priority/` labels, or an unknown value, hold the issue.
* **Holds.** As on GitHub: `needs-human` and `needs-design`, `status/blocked`
  where `statusLabels` is set, and a run in flight, which hold before anything
  more is read; then open [dependencies][fj-deps] and a matching pull request.
  The dependency listing has no total, so it is read to an empty page, at
  most 4 pages of 50; more holds, a blocker the token cannot read counts as
  open, and a repository without dependencies enabled (404) has none. A read
  that fails holds the issue and is a failure.
* **Matching pull requests.** The open pull requests of the issue's
  repository (`GET /repos/{o}/{r}/pulls?state=open`, at most 4 pages of 50,
  read once a pass) whose poster's id is the bot's or the operator's, and whose
  body closes the issue as [`stacks_on`](job-plans.md#stacking) reads GitHub's:
  a closing keyword (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`,
  `resolve`, `resolves` or `resolved`, any case, with an optional colon), then
  `#N`, `OWNER/REPO#N` or the issue's URL on this instance. `Part of #N` does
  not match, and a visitor's pull request never holds an issue. A listing that
  fails or has more holds the issue too. Unlike GitHub's closing references,
  a pull request in another repository is not read.

An issue is keyed by its instance URL and `OWNER/REPO#N`, so two
configurations for two instances never share one, and every request goes to
the configuration's own instance.

### Recording and replay

`--record FILE` previews live, as without it, and saves the pass's reads to
FILE: the GitHub pass's replay fixture (`agent-board/pass-replay/v1`, its
clock and one request with its answer a line) with `"forge": "forgejo"` and
the canonical `instance` added. Every forge read and broker read is kept in
the order the pass made it, with its body and `X-Total-Count`, a 404 as
`{"status": 404}`, or a failure's message; a broker read by its endpoint
only, as on GitHub. Request headers, and so the token, are never kept, and a
recording makes no write: it is a preview, and refuses `--apply`.
A fixture keeps what the reads answered, such as the bot's `/user` record, so
look at it before committing it.

`--replay FILE` previews the recording at its clock with no client, broker
or credential variable: it reads only the file, and sends nothing. It runs
the same stages under the same request bound, so a stage built later is
recorded and replayed with no change here. The time bound is the replay's
own: a recording cut short by it does not replay. A fixture of another instance, or a GitHub
one, is refused before any read, and a GitHub pass refuses a Forgejo fixture.
Each read must be the next one recorded: a missing or different request
fails that read, every read after it, and the pass, as does a request
recorded but never read. A seeded recording (`--record` with `--replay`)
stays GitHub-only.

### Stage 4 apply

`--apply` is off by default. No deployment, token or caller is provisioned or
activated. Applying work requires the existing `leases: true` setting, with
one preprovisioned slot per WIP unit on the private caller's
`agent-board-leases` branch. Slots are `leases/0.json` through
`leases/(wip-1).json`, initially `{"free":"initial"}`. No lease means no start.

The concrete threat is duplicate work after a pass races or dies around a
dispatch. Stage 4 uses one existing claim/reservation protocol, in order:

1. Read the newest job-plan comment by a recorder id, unedited under the
   comment rules below. Validate its target, kind, runner and configured pool.
   No plan holds for a person; it does not synthesize a triage plan. Stacked
   plans are held because Forgejo stack resolution is not wired.
2. Admit a unique `run: 0` lease reservation, then `BoardOperation::Claim`.
3. Reread the thread and claim, membership, labels, dependencies, matching
   pull requests, WIP, leases and pool/budget pacing before the start POST.
4. Call the native dispatch adapter once, bind a confirmed id, then append
   `BoardOperation::Receipt` with the run link or refusal/ambiguity.

A 204, lost reply or unverifiable 201 is receipted and never retried. A claim
without a receipt is recovered read-only, even when WIP is full or pacing
holds. Exactly one matching run is bound and receipted as found; no match,
several matches, a missing reservation or an edited recorder record holds
for a person without another claim or POST. The reservation preserves the
chosen pool. Starts run serially, not concurrently.

`reruns: true` enables one rerun of a failed receipted run. The adapter checks
all jobs' attempts; stage 4 records run id and attempt 1 before POST. Attempt
2 or an existing rerun record holds, even after a lost rerun reply. Completed
runs release their leases; expired leases are reaped with the existing
ownership checks. Ambiguous unbound reservations are not released early.

Every attempted mutation is capped: starts/reruns by `--max-dispatch`, other
writes (lease operations, claims, receipts and cancellation) by `--max-writes`.
A start needs space for four normal writes before admission. A cap reached
after an unexpected failure never authorizes another write; recovery observes
what remains. All I/O shares the 500-request/15-minute pass bound.

To prevent two scheduled passes observing the same free capacity, an applying
Forgejo Actions pass lists its **own pass workflow's** active runs on the
configured instance, not GitHub. Actions `SERVER_URL` must match `board.url`;
`REPOSITORY` and `RUN_ID` identify its run (`FORGEJO_*`, with `GITHUB_*`
compatibility aliases). Another running pass holds stage 4. Outside Actions,
both caps are required and serialization against the schedule is not promised.
These bounded observations are not an atomic cross-workflow lock: deployments
must serialize pass invocations. Status and snapshots are not part of this
applying slice (#523); other refusals remain in force.

### Labels and Status

Priority, Turn and Status are one label each in an exclusive scope:
`priority/P0`..`priority/P3`, `turn/…` and `status/todo`, `status/backlog`,
`status/blocked`, `status/in-progress`, `status/needs-human`, `status/done`.
The labels must exist, with `exclusive` set, before a pass writes: Forgejo
silently drops a name it does not know ([issue_label.go#L359-L368][fj-label-names]),
so a pass resolves names to ids from the repository's and its organization's
labels, refuses a missing or non-exclusive one, and never creates labels.
Adding a label to an exclusive scope removes the others in it
([RemoveDuplicateExclusiveIssueLabels][fj-exclusive]), but one path swallows
that removal's error, so every label write is read back: the write counts only
when the issue then has exactly the one label of its scope. Priority and Turn
read with two labels of their scope, none or an unknown value are incomplete,
as today. The API takes no If-Match and labels have no version: the pass reads
the issue's labels again just before a write and leaves one a person changed,
as stage 5 does with Status.

Status round-trips through its label when `board.statusLabels` is true:
the snapshot reads `status/…` as Status. No `status/` label is no Status,
which the future Forgejo stage 5 makes Todo;
two, or an unknown value, is incomplete and keeps whatever is there. Stage 5
writes the derived value with one label write, and the next read must show it.
Blocked and Backlog stay a person's holds; `status/blocked` is the board's
Blocked, and the `blocked/<reason>` labels keep filling the Blocked list. Forgejo
has no close reason ([issue.go#L121][fj-close]), so a closed issue is Done and
nothing reads Cancelled from it; `triageClose` closes with a comment that says
the verdict. Closing an issue with open dependencies fails with 412
([issue.go#L939-L940][fj-close-412]) and is reported, not forced.

### Comments, recorders and editors

Forgejo's API names a comment's author but not who last edited it; the edit
history is only in the web UI ([content_history.go#L20-L29][fj-history]), and
any user with issue write access may edit anyone's comment
([issue_comment.go#L596][fj-edit]). So a comment counts as a record (a plan, a
dispatch claim, a receipt, a run or result marker, a snapshot) only where its
author's id is in `recorders` (for an operator plan, the operator's id) and its
`updated_at` equals its `created_at`: never edited, by anyone. A recorder's
comment edited since is held as edited by someone else, as GitHub's
`lastEditedBy` check holds a writer's plan edited by another. That check stops
an ordinary writer, not an administrator: a repository's admins and owners,
and site admins, may edit a comment and set its `updated_at` to any time since
the issue opened ([issue.go#L329-L346][fj-backdate], used by
[issue_comment.go#L611][fj-edit-backdate]). So a Forgejo board trusts its
repositories' admins and owners as it trusts the operator; provisioning keeps
those to the operator and the bot, which the pass cannot check. The times are
whole seconds, so an edit within the second the comment was made is not seen
either; #515 measures whether a fresh comment's two times can differ. The pass
therefore never edits a record: where the GitHub pass edits in place (the
claim's outcome, the usage and hold snapshots, the planning request), a Forgejo
pass appends a new comment and reads the newest valid one. A writer replaces a
plan by replying with another, not by editing it. Run and Result reads now
check both the author id and matching creation/update timestamps.
The issue body has the same problem, and an issue's `updated_at` moves with
every comment and label too, so an edit of its body cannot be told apart:
direction (`direction.*`), which needs its body last edited by the operator or
the bot, and `bodyPlans` are refused.

A comment deleted by someone with write access takes its record with it, as on
GitHub; recovery reads what remains.

### Epics

Forgejo has no sub-issues or projects ([api.go][fj-api]). An epic is a live
one when it is an open issue labelled `epic` in `epics.repository` (or, with
`inWorkRepositories`, in a work repository) and the newest `epic` label event
in its whole [timeline][fj-timeline] added the label, by the operator's or the
bot's id. The timeline is read to its end, at most 10 pages of 50 events
(comments count too); a longer one makes the epic unreadable rather than
fall back to an older event. Forgejo lists every issue for a label name a
repository does not have, so each listed epic must carry the label.

Its children are the epic's own relationship comments: the bot's newest
comment whose first line is `<!-- agent-board-epic-children: N -->`, `N`
the epic's own number, followed by a line holding a JSON list of
`OWNER/REPO#N` in the work repositories, at most 50. It is appended with each
change, never edited. Each child carries a back-reference in its own newest
bot comment, `<!-- agent-board-epic-parent: OWNER/REPO#N -->`, and a child
counts only where both sides agree, so a person cannot attach work to an
epic by editing one issue. An edited relationship comment, as any edited
record, makes the epic unreadable rather than fall back to an older one.
Each child costs two reads a pass (its issue and its comments). Forgejo's
dependency links ([`/dependencies`, `/blocks`][fj-deps]) keep their meaning,
blocking, and are never used as parentage.

Stage 3 then applies the GitHub pass's [epic rules](pass.md#epic-planning-and-recovery)
to each live epic of `epics.repository`, in Priority order: the newest
accepted `agent-board/epic-plan/v1` is applied once, an apply cut short is
recovered from its receipts, and at most one due epic a pass is planned. The
operator and the bot are the plan writers, decided by id. The bot's planning
request is a triage job plan it posts on the epic, which is claimed and
started by stage 4's [claim and start path](#stage-4-apply) (leases, caps and
recovery included); the dispatch adapter accepts `epics.repository` for it.
These parts of the GitHub stage are left out: a planning request that got no
plan holds the epic for a person (`epic-unplanned`) rather than being retried
after six hours, a stale plan holds for a person rather than asking for a
new one, and an epic whose children are all closed is closed (with
`epics.close`, a comment then the state change, no close reason) or held for
the operator, without the question label or a board Why.

A plan is applied under the existing bounds: the work repositories, the
`priority/P0`..`priority/P3` options, `epics.maxAppliesPerPass`, and the
writes counted against `--max-writes`. Forgejo has a native mechanism only
for creating, linking, setting Priority and closing, so a plan with any other
action (`attach_sub_issue`, `rescope_sub_issue`, `close_epic`, a create with
`blocked_by` or `stacks_on`, or a new issue labelled in the `priority/`,
`turn/` or `status/` scope) is refused whole, before its claim, and held for
the operator; no part of it is applied. Applying claims the plan, reads the
epic again (still live, the plan unchanged, valid against the children now),
and then for each action:

* **create**: `POST /repos/{o}/{r}/issues` with the plan's labels and the
  board's membership label, read back; then a receipt naming the new issue;
* **link**: the child's parent comment, then the epic's new children
  comment, each read back;
* **Priority**: one `priority/` label write, read back ([labels](#labels-and-status)),
  for a new issue its plan's `set_priority` or `priority/P3`;
* **close**: the reason as a comment, then `PATCH` the state to closed,
  each read back; a child closed already is satisfied, as on GitHub.

A new issue's job plan is a further bot comment on it. A write that fails
stops the apply; its final receipt says `stopped` and what was confirmed.
A create whose reply is lost or cannot be read back is ambiguous: nothing
names the issue, so recovery cannot prove it and holds the epic for a
person, and the create is never sent again.

### Claims and recovery

The job-plan claim is unchanged in shape: before dispatch, the bot appends
`<!-- agent-board-dispatch: COMMENT-ID@TIME -->`, reads the comments again and
dispatches only if the plan is unchanged, unedited and no earlier valid record
names it. The run link or refusal is a second comment, never an edit of the
first. A pass that died between the two leaves a claim with no outcome: the
next pass looks for its run (below) and records it if found, and holds the
plan for a person if not; it never dispatches it again. An epic's planning
request is recovered the same way. An epic plan's claim is
`<!-- agent-board-epic-apply: COMMENT-ID@TIME -->` and its receipts further
comments, each with the whole `agent-board-epic-apply` detail of
[epic plans](epic-plans.md#apply): one after each new issue is created and one
when the apply ends. The claim's newest receipt by its author is its state,
as GitHub's one receipt, edited in place, would be. Epic receipts are
recovered as on GitHub, from the identities they confirmed and the issues as
read now, and a proved apply gets one more receipt saying `recovered`.

### Dispatch and runs

The caller is a Forgejo Actions workflow in `dispatchRepo` on the same
instance. A start is `POST /repos/{caller}/actions/workflows/{workflow}/dispatches`
with `{"ref", "inputs", "return_run_info": true}` ([workflow.go#L8-L18][fj-dispatch-body])
and the same string inputs as on GitHub: `task`, `repo`, `item`, `kind`,
`pool` and, for a stacked plan, `base` ([dispatch](dispatch.md#the-request)).
With `return_run_info`, Forgejo answers 201 with the run's `id`, `run_number`
and job names ([action.go#L862-L872][fj-dispatch-answer]). Forgejo has
created the run before it chooses between that and a bare 204, so a 204, or a
201 without an id, is a start with no handle: ambiguous, like a lost response,
never a refusal that would let the plan be dispatched again.

A 201 is not proof of the right start either: Forgejo creates the run even
when the workflow has no `workflow_dispatch` trigger, and drops inputs it does
not declare ([workflows.go#L100-L160][fj-dispatch-inputs]). So the pass reads
the new run (`GET …/actions/runs/{id}`) right after, and it is the start only
where its `trigger_user` is the bot's id, its `workflow_id` is the caller's
workflow, and its `event_payload`'s `inputs`, which hold only the inputs the
workflow declared, agree with those sent: each one sent non-empty is there with
its value. Forgejo fills an input sent empty or not sent with its declared
default, or drops it ([workflows.go#L55-L76][fj-dispatch-defaults]), so those
may be absent or anything; the run's title, below, still has to carry the pool
sent. Forgejo evaluates `run-name` when it
creates the run ([workflows.go#L251-L266][fj-run-name]), so the caller's
`run-name` is `KIND OWNER/REPO#N (POOL)` from its inputs, as on GitHub, for the
listings below; the title alone proves nothing, as anyone who may dispatch the
caller can choose it. A mismatch is recorded as a start that went wrong, the
run is cancelled (`POST …/runs/{id}/cancel`) and the item held for a person.

Runs in flight are the caller's runs with status `waiting`, `blocked` or
`running` (`unknown` is unreadable; [status.go#L17-L37][fj-status]), listed by
`workflow_id` and `status` ([action.go#L941-L969][fj-runs]). Pages hold at most
50 and the total is the body's `total_count`, not a header, so each status is
read whole, page by page to that total, then once more, as the GitHub
admission reads twice; a listing whose total moves, that does not fit 10 pages
a status, or that fails is unreadable and holds new starts. `waiting` is a job
queued for a runner, not yet on one: `actions/tasks` lists only picked-up jobs
and must not be used for WIP. `blocked` also covers a run waiting on
approval (`need_approval`), which holds a slot like any other.

A rerun is `POST …/actions/runs/{id}/rerun` ([rerun.go][fj-rerun]): it reuses
the run's id and resets it to `waiting`, and each job's `attempt` grows by
one; the run has no attempt of its own ([run.go#L284-L298][fj-rerun-run]). The
one rerun a failed run gets is therefore recorded as a comment naming the run
and the attempt seen in `…/runs/{id}/jobs`, and a run whose jobs already show
attempt 2 is never rerun again. A run still running refuses a rerun with 400.

An ambiguous POST (a timeout, a 5xx, a dropped connection, a start with no
handle) is recorded as ambiguous and never retried, as on GitHub. The next pass
lists the caller's runs titled for the item and created after the claim, and
checks each as above; exactly one that passes is recorded as found, and none
or several hold the plan for a person.

### Admission and release

Forgejo has no API that moves a git ref against an expected value: `git/refs`
is read-only and creating a branch fails only when it exists
([api.go#L1080-L1081][fj-refs], [branch.go#L253-L256][fj-branch]). The leases
are instead one file a slot, `leases/SLOT.json`, on a branch of the private
`dispatchRepo`, written through the contents API with the blob `sha` read
before: a stale `sha` is refused with 409, and an existing path refuses a
create with 422 ([update.go#L298-L321][fj-contents-sha], [update.go#L388-L391][fj-contents-create]).
The blob check alone is not CAS. In this pinned version `ChangeRepoFiles`
clones the old branch, checks its blob SHA, creates a commit with that snapshot
as parent, then [`TemporaryUploadRepository.Push`][fj-contents-push] performs a
**non-forced Git push**. The ref update decides the atomic winner: sibling
commits cannot both fast-forward the branch. A writer cloning after replacement
instead fails its blob check. The adapter supplies only `branch`, `sha`,
`content` and `message`: no `last_commit_id`, `new_branch` or force flag that
could change that argument. Refuse deployments without these guarantees;
never substitute an unguarded PATCH followed by read-back.
So of two admits racing for one slot exactly one writes it. A branch that moved
between the read and the commit fails as 500 ([file.go#L775-L781][fj-contents-errors]):
that is ambiguous, and the admit reads the slot again rather than assume either
outcome. Release and reap write the slot back to free with the `sha` they
read, so a stale reap cannot free a lease taken since. The `sha` names content,
not a version, so every lease body is unique: it names its run, claim and
`taken_at`, and a free slot names the run it freed. A lease's content then
never comes back for a slow writer to match; a free slot's may, which is
harmless, as a stale admit that read it free finds it still free. The rest of the
[lease rules](pass.md#leases) carry over: never delete, one lease a run, expiry
after 24 hours, a run that cannot be read keeps its lease until expiry, and the
send-boundary reservation with `run: 0` bound by the confirmed run id.
The library requires preprovisioned free slots and refuses missing ones; it
never creates a branch or deletes a slot. Unknown write outcomes hold without
retry, rather than treating read-back as proof of winning ownership. Race and
expiry tests use an offline conditional-write model; the container proof
remains #515.

### The caller

No agentic-job Forgejo caller exists. Audited on 30 October 2026: agentic-job
`a45f34a50bf58b5de70bd00a0881e8272f8c8d96` has no `.forgejo/` or `.gitea/`
workflows; its `dispatch.yml` is a GitHub workflow (inputs `task`, `repo`,
`item`, `item-repo`, `kind`, `status-comment`; no `pool` or `base`). What it has
for Forgejo is `agentic-job apply --forge forgejo` (comments, pull requests,
labels, issues, closing, statuses; agentic-job#2122, #2123), the prose of its
off-GitHub collect, check and apply flow, and a CI job that applies to a
Forgejo service container (agentic-job#2109): a test, not a caller. Tracker,
actions, agenthome, forge-infra and infra have no Forgejo workflow either, and
no deployed instance URL is recorded anywhere.

Before any Forgejo dispatch is enabled, these are needed, and none is in this
repository:

1. A caller workflow on Forgejo Actions taking the inputs above, with the
   `run-name` above, runner labels from its own configuration, and no
   `concurrency` group shared by its runs: Forgejo queues a group's runs one
   behind another ([workflows.go#L268-L302][fj-concurrency]), so with a fixed
   group every run but one would sit `waiting`, holding a slot without running.
   A group keyed by item,
   with `cancel-in-progress: false`, is allowed.
2. Its collect, check and apply jobs, with apply's token in a protected step the
   agent cannot reach, and fork pushes separate from upstream writes
   (agentic-job#2130, tracker#766).
3. The agent sandbox on a Forgejo runner (agentic-job#1347), and a registered,
   disposable runner for CI.
4. A bot user and its scoped token, the `recorders` ids, the exclusive labels
   and the private lease and publication repositories, provisioned by the
   operator, with admin and owner rights on the board's repositories kept to
   the operator and the bot. A run does not provision them.
