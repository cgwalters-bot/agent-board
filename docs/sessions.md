# Sessions

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

A session is one long run over one repository that decides in batch what
many cold, one-comment triages decided one item at a time
([agent-board#830](https://github.com/cgwalters-forge/agent-board/issues/830)).
In the 24 hours before that issue was filed, 59 triage runs each re-read the
same repositories to post at most one comment on one item, and many ended
with no change. A session reads the repository once: its open issues and
pull requests, the board's items and [holds](pass.md#what-is-built), the
poll's [maintainer report](poll.md#maintainer-report), recent CI and the
code. It is the per-repository maintainer's first job
([tracker#1356](https://github.com/cgwalters-forge/tracker/issues/1356)),
whose first duty the operator named as intake: every open issue either on
the board with a Priority or carrying a written reason.

A session answers with one **session batch**: a typed list of at most 20
actions in one comment on the issue its plan is on. Like an
[epic plan](epic-plans.md), the batch is a proposal. agent-board checks it
against bounds from the caller's configuration and a cap on each kind of
action; nothing in the batch grants authority. Per-item triage stays for
newly filed items and operator mentions.

## What is built

The first three slices of agent-board#830:

- `session` is a [job plan](job-plans.md) kind. A session plan names the
  issue it reports on, an open issue of the repository it triages, such as
  the repository's anchor issue for sessions; its brief says what to read
  and where to post. The pass starts an accepted session plan only with
  [`sessionPlans`](pass.md#one-configuration-file), off by default, through
  the same start path, pacing, WIP, leases and caps as a research plan;
  without it a session plan waits on the operator (`needs-operator`), and
  `agent-board dispatch` starts it by hand. A session plan for another issue
  than the one it is on stays manual, as a research plan does, and so does
  one on an epic, which stage 4 never starts anything on. The operator
  writes session plans: the pass starts a session plan only from a comment
  the operator wrote and, if it was edited, edited last. The planner's
  session plan, which any triage or session run could post, including a
  session proposing its own successor, waits on the operator (`hold
  OWNER/REPO#N: plan ID is a session plan the operator did not write; …`);
  so does one in an issue's body, whose `bodyPlans` copy would be the
  planner's; and an [epic plan](epic-plans.md) may not give a sub-issue
  one. So no agent starts a session.
- [Daily sessions](#daily-sessions): with the pass's `sessions` section,
  off by default, the pass itself writes and starts one session plan a day
  on each configured repository's anchor issue.
- The batch format below, its [schema](session-batch.schema.json), and
  `agent-board check session-batch`, which validates a candidate comment
  offline against bounds given as flags and prints the typed actions.
- [Applying a batch](#applying-a-batch): with `sessions.apply`, off by
  default, the pass applies the batch a daily session answers with, once,
  with a receipt on the anchor as [epic apply](epic-plans.md) leaves one
  (agent-board#845).
- A session's run is counted by [`agent-board cost`](cost.md) under its
  `dispatch-session-agent-run` artifact.

Not built yet, in order: a session due early when enough events
accumulate, rather than daily; and the pass log comparing triage counts
before and after.
Without `sessions.apply`, a session's actions are read by a person. A
session that also changes files opens a pull request through the ordinary
`create_pull_request` safe output; the batch carries no file change.

## Daily sessions

With `sessions` in the pass's [configuration](pass.md#one-configuration-file)
(off unless set), the pass starts one session a day on each repository it
names, from `sessions.hourUtc`:

```json
"sessions": {"hourUtc": 6, "issues": ["cgwalters-forge/agent-board#830"]}
```

`sessions.issues` names each repository's **anchor issue**, `OWNER/REPO#N`:
an open issue on the board in a work repository, one per repository, which
the session's plan is posted on and its batch is answered on. The caller
names it, not an issue's text, so no filed issue becomes an anchor. The
section needs `triagePools` or `planPools`, which the session's pool is
drawn from as a triage run's is.

Each pass, for each anchor in the configured order:

1. An anchor that is not an open issue on the board starts nothing
   (`session OWNER/REPO: its issue OWNER/REPO#N is not an open issue on the
   board; no session starts`), as does one with a run in flight (`session
   OWNER/REPO: its run is in flight, URL`).
2. The anchor's comments are read, up to the plan protocol's page bound
   (ten pages of 100; an anchor gains a plan, a record and a reply a day,
   so after about a year of sessions the read fails, `session OWNER/REPO
   error: …`, until the caller names a fresh anchor). With a newest plan
   there, it must be a `session` plan with a dispatch record. Anything
   else holds the anchor for the operator, a `hold OWNER/REPO#N: …` the
   [hold snapshot](pass.md#what-is-built) lists, since no later pass can
   get past it by itself: a session plan without a record (`its session
   plan ID has no dispatch record; a person dispatches it by hand or
   removes it, and its session waits`, which the operator's own plan on an
   anchor is too, as `agent-board dispatch` starts it and the pass does
   not), a plan of another kind (`its newest plan ID is for KIND, not a
   session; a person moves it, …`) or one that cannot be read (`its newest
   plan cannot be used: …; a person replaces it, …`). The bot's own
   unrecorded session plan, left where a start posted its plan but could
   not record the dispatch, holds the anchor the same way: a run posts as
   the bot too, and no agent starts a session. The record is the day's
   receipt: one at or after today's due time means today's session started
   (`session OWNER/REPO: today's started at T, URL; the next is due from
   T2`). The receipt is on the forge, not in a state file, so a pass every
   hour starts one session a day, not twenty-four, and a later pass on
   another machine reads the same one (two passes reading before either's
   record lands can both start, as with any start).
3. Else the session starts as stage 4 starts a triage run, within WIP,
   `--max-dispatch`, the weekly budget and pool pacing (`start session
   OWNER/REPO#N pool=P`; a preview posts nothing and counts it under
   `planned starts`), before the pass's per-item starts, since one session
   stands in for many of them. Its plan is posted as the bot's after `The
   board pass asks a session run to triage this repository as a whole
   today.` and recorded by the plan protocol. The anchor is left out of
   stage 4's candidates: it is the session's, so it is never triaged on its
   own, and the pass's own session plan there, the bot's, is not held as a
   planner's would be elsewhere. As for the sweep, a preview says `start
   session …` before the start's recheck of the anchor, which an apply
   makes: an anchor labelled `needs-human`, with a blocked Status or a
   trusted open pull request holds there instead.

The brief is written from the caller's configuration and the board alone:
the repository and anchor, what to read, that only the operator's own
comments are decisions, the batch format and its caps, and the
[bounds](#bounds) as the exact `agent-board check session-batch` command the
run must pass before posting (the work repositories, the board's Priority
options and the `operatorAsk` domains; with none, the brief says to ask the
operator nothing). A brief longer than a job plan allows fails the start
(`session OWNER/REPO error: its brief is N characters, …`) rather than
posting a plan the protocol would refuse. A session run in flight is a
dispatch run like any other: it holds its anchor and takes a WIP slot by
its run name, `session OWNER/REPO#N (POOL)`.

What this stops: without the section nothing starts; with it, each
repository costs at most one long run a day, started only on the caller's
named issue, and only by the pass. A run posts as the bot, so it can
forge a plan or a record on the anchor, but only one dated today: that
suppresses a session, as any plan it leaves there does, and never starts
one. Nothing the session proposes is applied unless the section also sets
`apply` ([below](#applying-a-batch)); without it, its batch is read by a
person.

A dry run from the recorded board of 2026-10-23
([replay](pass.md#replay-and-release-gate)), with
`"sessions": {"hourUtc": 0, "issues": ["cgwalters-forge/agent-board#40"]}`
and `"triagePools": ["claude"]` added to `fixtures/pass/config.json`, plans
`start session cgwalters-forge/agent-board#40 pool=claude` as its first
start and no triage of that issue; the CLI test
`pass_replay_previews_a_daily_session` keeps it so.

## Applying a batch

With `"apply": true` in the `sessions` section (off unless set), each pass
after today's session started reads the batch answering it and applies it
once:

```json
"sessions": {"hourUtc": 6, "issues": ["cgwalters-forge/agent-board#830"], "apply": true}
```

1. **Which batch.** The newest comment on the anchor holding an
   `agent-board-session` block, written by the bot (a session run posts as
   the bot) or the operator and, if edited, edited by one of them, whose
   comment id is after the day's dispatch record. Anyone else's comment is
   no batch, and a writer's comment edited by anyone else holds the anchor
   for the operator, as such a comment holds a plan. A batch before the
   record answered an earlier plan and is not applied; so a batch left
   unapplied when the next day's session starts is a person's to read.
   One batch is applied a day, the day being the configured `hourUtc`'s:
   once a receipt posted since the day's due time exists, whichever
   record it follows, a newer or edited batch (a new id) is held for the
   operator (`batch ID is not applied: URL claims batch ID2 for today
   already; …`) rather than spending the caps again. The receipts counted
   are the day's, not those after the record, because a run posting as
   the bot can post a new session plan, a record and a batch on the
   anchor the same day; it cannot move the due time.
2. **Bounds.** The batch is checked as [`check session-batch`](#check)
   checks it, against the [bounds](#bounds) the brief named, read from
   the caller's configuration and the board, never from the batch; its
   `repo` must be the anchor's repository; and no action may name the
   anchor itself, the session's own issue, whose close, new body or plan
   would take it from the pass's sessions. A refused batch holds the
   anchor (`hold OWNER/REPO#N: batch ID is refused: …; a person reads
   it`), which the hold snapshot lists, until the next session's record
   supersedes it: a session cannot stop its repository's sessions for good
   by posting a malformed batch, and a person sees every refusal.
3. **Receipt first.** The pass posts the receipt on the anchor as the
   claim before any write, reads the anchor's comments back, and writes
   nothing if the batch changed, if an earlier claim of the day exists
   (two passes racing: the oldest wins), or if the claim did not land as
   the bot's or the operator's. It then resolves every issue the actions
   name as a GitHub issue: the REST paths a close, a new body or a
   comment take address pull requests by the same numbers, so a number
   that is a pull request's, or no issue, or that GitHub resolves to
   another issue than named, stops the apply with nothing written. Then
   it makes each action's writes in the batch's order and updates the
   receipt with what was confirmed. A batch with a receipt is never
   applied again: later passes say `session OWNER/REPO: batch ID was
   applied at T, URL`. Deleting the receipt would allow a replay, as
   deleting a dispatch record would; that is repository write access.
4. **Partial failure.** The apply stops at the first failed request and
   keeps the claim; the receipt says `Stopped applying …` and lists what
   was confirmed, and the pass line says `apply session … failed: …`.
   Later passes hold the anchor for the operator (`the apply of batch ID
   was stopped after a failed request; it is never replayed: a person
   inspects URL`) rather than replay it; so does a receipt posted since
   the day's due time by the bot or the operator that cannot be read, or
   that anyone else edited, since it may claim any batch of the day.
   Earlier days' receipts are their own sessions', so each hold here lasts
   until the next session's record; and a writer's comment on the anchor
   that anyone else edited, which holds the anchor as it holds a plan, is
   weighed only while its edit is from today's due time on, so that hold
   too ends when the next day's session starts over it. No rollback is
   attempted.
5. **Caps.** The apply is one write step for the receipt and one for
   each writing action, taken whole or held whole by `--max-writes`
   (`held by --max-writes: apply session …`); a preview says what it
   would do under `apply session OWNER/REPO batch=ID: …` and writes
   nothing, counting the same steps. It waits where another pass is in
   progress or the pass's requests are nearly spent.

What each action writes, as the bot: `close_issue` comments the reason
and closes the issue as not planned; `rescope_issue` replaces the body
and comments the reason; `set_priority` puts the issue on the board,
where it may be already, and sets its Priority by the board's option id;
`attach_to_epic` links the issue as a sub-issue of the epic;
`post_plan` posts the job plan on its issue, which the pass then starts
as any plan of the bot's; `ask_operator` writes nothing of its own: the
receipt lists each question for the operator under `Questions for
@OPERATOR`. A reason or plan comment ends with `From [this session
batch](URL)`, so each change traces to the batch that asked for it.

The receipt is one comment on the anchor, readable first, then one fenced
`agent-board-session-apply` block with the machine detail:

````markdown
Applied [this session batch](https://github.com/OWNER/REPO/issues/40#issuecomment-11) at 2026-10-23T15:03:00Z.

- Closed OWNER/REPO#701 as not planned
- Set OWNER/REPO#691 to P1
- Asked a question (budget), below

Questions for @OPERATOR:
- (budget) May the claude pool's burst rise to 120 while sessions run daily?

```agent-board-session-apply
{
  "schema": "agent-board/session-apply/v1",
  "batch": "11@2026-10-23T06:30:00Z",
  "outcome": "applied",
  "actions": [
    {"action": 1, "type": "close_issue", "issue": "OWNER/REPO#701", "writes": ["comment", "patch"]},
    {"action": 2, "type": "set_priority", "issue": "OWNER/REPO#691", "detail": "P1", "writes": ["priority"]},
    {"action": 3, "type": "ask_operator", "detail": "budget", "writes": ["receipt"]}
  ]
}
```
````

`batch` is the batch comment's id and last change time, as a plan's id;
`outcome` is `claimed` (under way, or cut short before it could say),
`applied` or `stopped`; each action's `writes` names the requests
confirmed (`comment`, `patch`, `priority`, `link`, or `receipt` for a
question), so a stopped apply shows how far it got. Unknown fields are
ignored, so a later build's receipts still claim.

What this stops: off, nothing a session writes changes any issue. On, a
session changes only what its bounded batch names, in the configured
repositories, within the caps on each kind of action, once a day; a batch
posted twice is applied once (only the newest after the record counts),
a day with a receipt applies no second batch however many plans and
records a run posts as the bot, a refused batch is never applied, only
issues are written to (each is resolved as one before the first write,
so a pull request's number closes or rewrites nothing), and a run cannot
have the pass write where the caller did not allow, since the bounds come
from the configuration; and the receipt and every comment are written
under the bot's own login, which the batch's text checks keep from
carrying a plan, a record or a receipt.

Evidence that an accepted batch applies once: the pass test
`sessions_apply_an_accepted_batch_once` applies a batch of one action of
each writing kind on the recorded board, checks the claim is the first
write and the receipt's update the last, runs two more applying passes
and a preview over the same forge, and sees the receipt read and no write
made again; `sessions_apply_one_batch_a_day_whatever_the_record` then
posts a second session plan, record and batch as the bot the same day
and sees the new batch held on the day's receipt;
`sessions_stop_a_batch_naming_a_pull_request_before_any_write` sees a
batch naming a pull request's number claimed and stopped with no action
written; `session_apply`'s unit tests cover an earlier claim winning, a
claim that did not land as a claimer's, a pull request named by each
kind of action, and an apply stopped by a failed request with its claim
kept.

## Format

One fenced block with the info string `agent-board-session`, at the start of
a line, holding one JSON object:

````markdown
```agent-board-session
{
  "schema": "agent-board/session-batch/v1",
  "repo": "cgwalters-forge/agent-board",
  "actions": [
    {"type": "close_issue", "issue": "cgwalters-forge/agent-board#701", "reason": "..."},
    {"type": "rescope_issue", "issue": "cgwalters-forge/agent-board#683", "body": "...", "reason": "..."},
    {"type": "set_priority", "issue": "cgwalters-forge/agent-board#691", "value": "P1"},
    {"type": "attach_to_epic", "issue": "cgwalters-forge/agent-board#703", "epic": "cgwalters-forge/tracker#1356"},
    {"type": "post_plan", "issue": "cgwalters-forge/agent-board#830",
     "plan": {"schema": "agent-board/job-plan/v1", "kind": "implement", "runner": "hosted", "brief": "..."}},
    {"type": "ask_operator", "domain": "budget", "question": "..."}
  ]
}
```
````

`repo` is the repository the session ran on, `OWNER/NAME`, in the
configured repositories; the [apply](#applying-a-batch) checks it against
the anchor the batch is on. Each action names an issue as `OWNER/REPO#N`,
in `repo` itself, so a session on one repository cannot triage every
configured one; only an `epic` may be in another configured repository,
as epics live in the tracker; and the apply refuses an action on the
anchor itself. Each action is one of:

| `type` | Fields | What an applier would do | Most in one batch |
|---|---|---|---|
| `close_issue` | `issue`, `reason` | Comment the reason, close as not planned | 5 |
| `rescope_issue` | `issue`, `body`, `reason` | Replace the body, comment the reason | 5 |
| `set_priority` | `issue`, `value` | Set the board's Priority to one of its options | 10 |
| `attach_to_epic` | `issue`, `epic` | Link the issue as a sub-issue of the epic | 5 |
| `post_plan` | `issue`, `plan` | Post the job plan on the issue, for the pass to start as any plan | 5 |
| `ask_operator` | `domain`, `question` | One line for the operator, in a configured `operatorAsk` domain | 3 |

A batch has at most 20 actions in all, the cap the
[design](design.md#3-agentic-job-bounds-and-delegated-operations) puts on
one run's outputs. A `reason` has 1 to 4,000 characters, a `body` 1 to
60,000 and a `question` 1 to 500 on one line; none may hold an
`` ```agent-board `` fence or a `<!--` marker, which under the applier's
login would be a job plan (one the pass's `bodyPlans` takes, in a body), an
epic plan, a batch or a dispatch record.
A `plan` is a [job plan](job-plans.md) without `repo` and `item`, which are
the issue's, and without `stacks_on`; its `kind` is `implement`, `triage`
or `research`: a session may not start another session, and a fix needs
the pull request a session does not read.

An issue has at most one action of each type in a batch, and an issue the
batch closes has no other action, nor is it another action's `epic`: an
action after a close would act on a closed issue, and a close after one
would undo it. An empty `actions` list
is a valid batch saying the repository needs nothing. A batch with any
refused action is refused as a whole, and the error names every refused
action by position, so a session fixes them all at once. Unknown fields,
unknown action types and `null` values are refused.

The [schema](session-batch.schema.json) carries every static check above:
the shapes, lengths and kinds, the cap on each type of action (as
`maxContains` on `actions`) and the fence and marker refusal, so a schema
validator refuses what the checker refuses for them. The bounds below and
the relations between actions (one action of a type per issue, a closed
issue untouched otherwise) are the checker's alone; a batch a schema
validator accepts is not yet accepted.

## Bounds

The bounds come from the caller's configuration, never from a batch or a
dispatcher's inputs; empty bounds allow nothing. The offline check takes
them as flags; the pass's [apply](#applying-a-batch) reads them from the
sources named here:

| Bound | Meant to come from | Checked |
|---|---|---|
| Repositories | the caller's `workRepositories` | `repo` and every `epic`; every `issue` must be in `repo` |
| Priority options | the board's Priority field | every `set_priority` value |
| Ask domains | the caller's `operatorAsk.domains` | every `ask_operator` domain |

The concrete failures these stop: a session that misreads a repository
closes at most five issues and rewrites at most five before a person sees
its batch; a session cannot commit the pools to more than five runs, nor to
a session of its own; it cannot touch a repository the caller did not name,
nor set a Priority the board does not have; it cannot ask the operator
outside the subjects the caller delegated to them, nor more than three
questions; and nothing it writes can be read back as a job plan, an epic
plan or a dispatch record.

## Check

```sh
agent-board check session-batch --body comment.md \
  --allow-repo cgwalters-forge/agent-board --allow-repo cgwalters-forge/tracker \
  --priority-option P0 --priority-option P1 --priority-option P2 \
  --ask-domain budget --ask-domain credentials
```

reads a comment body (a file, or stdin without `--body`, at most 1 MiB),
needs no credentials or network, and exits 0 with one JSON object per
action on stdout, in the batch's order, and `Valid session batch for
OWNER/REPO with N actions; nothing was applied.` on stderr. A body without
a batch, a malformed batch, or a batch outside the bounds exits 1 with the
error on stderr and nothing on stdout. A session's brief should have it
check its batch this way before posting, as [epic plans](epic-plans.md) are
serialized and parsed before posting.

## Caller settings

A session plan runs only where the caller's dispatch workflow accepts
`session` as a `kind` and has a profile for it; the profile tells the run
what to read, that issue and pull request text is data, that only the
operator's own words decide, and to post one batch. The pass starts
accepted session plans only once the caller's pass configuration sets
`sessionPlans` to `true`, and its own [daily sessions](#daily-sessions)
only once it has a `sessions` section: in `cgwalters-forge/tracker`'s
`.github/pass.json`, `"sessions": {"hourUtc": 6, "issues":
["cgwalters-forge/agent-board#830"]}` gives agent-board one session a day
from 06:00 UTC, answered on agent-board#830. The pass applies those
batches only once the section also sets `"apply": true`
([applying a batch](#applying-a-batch)); until then they are read by a
person. Once its batches prove themselves, the caller can lower per-item
triage there: raise `triageFollowUpDays` and leave `idleReplan` off.
