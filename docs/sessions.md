# Sessions

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

A session is one long run over one repository that decides in batch what
many cold, one-comment triages decided one item at a time
([agent-board#830](https://github.com/cgwalters-forge/agent-board/issues/830)).
In the 24 hours before that issue was filed, 59 triage runs each re-read the
same repositories to post at most one comment on one item, and many ended
with no change. A session reads the repository once: its open issues and
pull requests, the board's items and [holds](pass.md#what-is-built), the
poll's [maintainer report](poll.md#maintainer-report), recent CI and the
code. It is the per-repository maintainer's first job
([tracker#1356](https://github.com/cgwalters-forge/tracker/issues/1356)),
whose first duty the operator named as intake: every open issue either on
the board with a Priority or carrying a written reason.

A session answers with one **session batch**: a typed list of at most 20
actions in one comment on the issue its plan is on. Like an
[epic plan](epic-plans.md), the batch is a proposal. agent-board checks it
against bounds from the caller's configuration and a cap on each kind of
action; nothing in the batch grants authority. Per-item triage stays for
newly filed items and operator mentions.

## What is built

This is the first slice of agent-board#830:

- `session` is a [job plan](job-plans.md) kind. A session plan names the
  issue it reports on, an open issue of the repository it triages, such as
  the repository's anchor issue for sessions; its brief says what to read
  and where to post. The pass starts an accepted session plan only with
  [`sessionPlans`](pass.md#one-configuration-file), off by default, through
  the same start path, pacing, WIP, leases and caps as a research plan;
  without it a session plan waits on the operator (`needs-operator`), and
  `agent-board dispatch` starts it by hand. A session plan for another issue
  than the one it is on stays manual, as a research plan does, and so does
  one on an epic, which stage 4 never starts anything on. The operator
  writes session plans: the pass starts a session plan only from a comment
  the operator wrote and, if it was edited, edited last. The planner's
  session plan, which any triage or session run could post, including a
  session proposing its own successor, waits on the operator (`hold
  OWNER/REPO#N: plan ID is a session plan the operator did not write; …`);
  so does one in an issue's body, whose `bodyPlans` copy would be the
  planner's; and an [epic plan](epic-plans.md) may not give a sub-issue
  one. So no agent starts a session.
- The batch format below, its [schema](session-batch.schema.json), and
  `agent-board check session-batch`, which validates a candidate comment
  offline against bounds given as flags and prints the typed actions.
- A session's run is counted by [`agent-board cost`](cost.md) under its
  `dispatch-session-agent-run` artifact.

Not built yet, in order: applying an accepted batch once, with a receipt on
its item as [epic apply](epic-plans.md) leaves one; the pass deciding when a
repository's session is due (daily, or when enough events accumulate) and
writing its plan; and the pass log comparing triage counts before and after.
Until a batch is applied, a session's actions are read by a person. A
session that also changes files opens a pull request through the ordinary
`create_pull_request` safe output; the batch carries no file change.

## Format

One fenced block with the info string `agent-board-session`, at the start of
a line, holding one JSON object:

````markdown
```agent-board-session
{
  "schema": "agent-board/session-batch/v1",
  "repo": "cgwalters-forge/agent-board",
  "actions": [
    {"type": "close_issue", "issue": "cgwalters-forge/agent-board#701", "reason": "..."},
    {"type": "rescope_issue", "issue": "cgwalters-forge/agent-board#683", "body": "...", "reason": "..."},
    {"type": "set_priority", "issue": "cgwalters-forge/agent-board#691", "value": "P1"},
    {"type": "attach_to_epic", "issue": "cgwalters-forge/agent-board#703", "epic": "cgwalters-forge/tracker#1356"},
    {"type": "post_plan", "issue": "cgwalters-forge/agent-board#830",
     "plan": {"schema": "agent-board/job-plan/v1", "kind": "implement", "runner": "hosted", "brief": "..."}},
    {"type": "ask_operator", "domain": "budget", "question": "..."}
  ]
}
```
````

`repo` is the repository the session ran on, `OWNER/NAME`, in the
configured repositories; an applier checks it against the item the batch is
on. Each action names an issue as `OWNER/REPO#N`, in `repo` itself, so a
session on one repository cannot triage every configured one; only an
`epic` may be in another configured repository, as epics live in the
tracker. Each action is one of:

| `type` | Fields | What an applier would do | Most in one batch |
|---|---|---|---|
| `close_issue` | `issue`, `reason` | Comment the reason, close as not planned | 5 |
| `rescope_issue` | `issue`, `body`, `reason` | Replace the body, comment the reason | 5 |
| `set_priority` | `issue`, `value` | Set the board's Priority to one of its options | 10 |
| `attach_to_epic` | `issue`, `epic` | Link the issue as a sub-issue of the epic | 5 |
| `post_plan` | `issue`, `plan` | Post the job plan on the issue, for the pass to start as any plan | 5 |
| `ask_operator` | `domain`, `question` | One line for the operator, in a configured `operatorAsk` domain | 3 |

A batch has at most 20 actions in all, the cap the
[design](design.md#3-agentic-job-bounds-and-delegated-operations) puts on
one run's outputs. A `reason` has 1 to 4,000 characters, a `body` 1 to
60,000 and a `question` 1 to 500 on one line; none may hold an
`` ```agent-board `` fence or a `<!--` marker, which under the applier's
login would be a job plan (one the pass's `bodyPlans` takes, in a body), an
epic plan, a batch or a dispatch record.
A `plan` is a [job plan](job-plans.md) without `repo` and `item`, which are
the issue's, and without `stacks_on`; its `kind` is `implement`, `triage`
or `research`: a session may not start another session, and a fix needs
the pull request a session does not read.

An issue has at most one action of each type in a batch, and an issue the
batch closes has no other action, nor is it another action's `epic`: an
action after a close would act on a closed issue, and a close after one
would undo it. An empty `actions` list
is a valid batch saying the repository needs nothing. A batch with any
refused action is refused as a whole, and the error names every refused
action by position, so a session fixes them all at once. Unknown fields,
unknown action types and `null` values are refused.

The [schema](session-batch.schema.json) carries every static check above:
the shapes, lengths and kinds, the cap on each type of action (as
`maxContains` on `actions`) and the fence and marker refusal, so a schema
validator refuses what the checker refuses for them. The bounds below and
the relations between actions (one action of a type per issue, a closed
issue untouched otherwise) are the checker's alone; a batch a schema
validator accepts is not yet accepted.

## Bounds

The bounds come from the caller's configuration, never from a batch or a
dispatcher's inputs; empty bounds allow nothing. The offline check takes
them as flags; the applier of a later slice is meant to read them from the
sources named here:

| Bound | Meant to come from | Checked |
|---|---|---|
| Repositories | the caller's `workRepositories` | `repo` and every `epic`; every `issue` must be in `repo` |
| Priority options | the board's Priority field | every `set_priority` value |
| Ask domains | the caller's `operatorAsk.domains` | every `ask_operator` domain |

The concrete failures these stop: a session that misreads a repository
closes at most five issues and rewrites at most five before a person sees
its batch; a session cannot commit the pools to more than five runs, nor to
a session of its own; it cannot touch a repository the caller did not name,
nor set a Priority the board does not have; it cannot ask the operator
outside the subjects the caller delegated to them, nor more than three
questions; and nothing it writes can be read back as a job plan, an epic
plan or a dispatch record.

## Check

```sh
agent-board check session-batch --body comment.md \
  --allow-repo cgwalters-forge/agent-board --allow-repo cgwalters-forge/tracker \
  --priority-option P0 --priority-option P1 --priority-option P2 \
  --ask-domain budget --ask-domain credentials
```

reads a comment body (a file, or stdin without `--body`, at most 1 MiB),
needs no credentials or network, and exits 0 with one JSON object per
action on stdout, in the batch's order, and `Valid session batch for
OWNER/REPO with N actions; nothing was applied.` on stderr. A body without
a batch, a malformed batch, or a batch outside the bounds exits 1 with the
error on stderr and nothing on stdout. A session's brief should have it
check its batch this way before posting, as [epic plans](epic-plans.md) are
serialized and parsed before posting.

## Caller settings

A session plan runs only where the caller's dispatch workflow accepts
`session` as a `kind` and has a profile for it; the profile tells the run
what to read, that issue and pull request text is data, that only the
operator's own words decide, and to post one batch. The pass starts
accepted session plans only once the caller's pass configuration sets
`sessionPlans` to `true`.
