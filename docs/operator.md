# Operator interaction

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

How a person answers the board and acts on it. Each of these prints a proposal
by default and writes only with `--apply` and the operator's own token; none is
delegated to an agent.

## Questions as issues

`ask create` opens a question issue, labelled `question` and assigned to the
operator, with lettered options and a recommendation, and sets it and the item it
blocks to Needs human; `ask list` shows open asks on the board; `ask resolve` comments
the answer, closes the ask and sets it Done. Like `item edit` they print
proposals unless the operator passes `--apply` with their own token. The label
and the Status option must already exist; neither is created, and the operator
must be assignable in the ask's repository. Resolving leaves the blocked item's
Status to whoever acts on the answer. Asks on pull requests, sub-issue links and
copying the blocked item's Priority are not implemented.

## One decisions document

The caller opts in by supplying `decisions` in its trusted default-branch
`agent-board.json`. There is no default repository or issue, and dispatch inputs
must not supply this configuration. The issue must already exist; it may be
private. These commands need issue read access, and `--apply` additionally needs
issue write access. They do not need a project or change board fields.

```json
{"decisions":{"repository":"example/coordination","issue":42}}
```

```sh
agent-board ask add 'Turn on the scheduler?' --context 'The trial passed.' \
  --option 'Yes, now' --option 'Not yet' --recommend 'The trial passed' \
  --item example/work#7 --priority P0 --config agent-board.json
agent-board ask read --config agent-board.json
agent-board ask resolve D1 'Enable after approval.' --config agent-board.json
```

Add and resolve print the proposed body without writing by default. Supply
`--apply` explicitly to write with your token. The older `ask create`, `ask list`
and issue-identity `ask resolve` retain their issue-per-question behavior.
`--snapshot` and `--json` are not supported by the document commands: their
stdout is already JSON. Tests inject an offline GraphQL transport.

The issue body is the interface, without hidden markers:

```markdown
### D1 Turn on the scheduler? (P0, blocks example/work#7)
The trial passed.
- [ ] A) Yes, now ← recommended: The trial passed
- [ ] B) Not yet

Reply:

## Done
```

The operator edits checkboxes, question/context/options, or text after `Reply:`.
Keep the `### D<n>` headings and `## Done` section structurally intact. New
entries go before Done; resolve moves the original entry bytes into Done and
adds `Outcome: TEXT`. It does not rewrite the operator's words. Resolution text
is one line; context cannot contain headings or fences. There are 2–10 options.
IDs are positive, canonical decimal numbers and never intentionally reused:
the next ID exceeds both the current document and the saved high-water mark.

After a successful write, the bot saves a **fenced JSON state file** beside the
configuration: `agent-board.decisions-state.md` (derived by replacing the config
file extension with `.decisions-state.md`). It contains the target identity,
last written body and highest ID observed. This is bot-owned state, not an
operator-editable part of the interface. Persist it between runs. **It contains
the issue body: keep it private, outside public artifacts and source control.**
On Unix, newly published state files are owner-readable/writable only; the
temporary file is created exclusively to refuse existing files or symlinks.
A stale `.md.tmp` file aborts publication; inspect it before removing it.
A read or preview never advances this baseline. `ask read` reports each changed
ID with its before/after text, current ticked lines and exact reply suffix,
including rewordings and deletions. It reports document-only edits as
`other_edits` when there are no changed entries. These are text deltas, not
authenticated attribution or authority to execute the selected option.

When state is absent, the newest 100 `userContentEdits` provide a fallback: the
`diff` of the newest edit by the authenticated bot is its last written version.
GitHub serves edits newest-first; history in any other order is refused. Use
the same dedicated bot account between runs; another writer with that identity
is indistinguishable. A missing/redacted baseline fails closed rather than
guessing. An empty issue can be initialized. Writes without local state require
complete, unredacted history to avoid recycling deleted IDs; otherwise restore
the state. Corrected malformed historical structure does not block operation;
history recovery conservatively counts valid ID headings in old versions.
The body and every examined history version are limited to 60,000 bytes.
Malformed headings, duplicate IDs/Done sections and unclosed fences abort.

Writes always merge into the body read from GitHub, not the saved baseline.
Immediately before updating, a second read must match the issue ID, body and
timestamp; a mismatch aborts without retry. This stops an operator edit made
during the merge from being overwritten. **GitHub's `updateIssue` has no atomic
conditional write:** an edit between that final read and the mutation can still
race. Serialize bot writers and avoid simultaneous human edits during apply;
this command does not claim atomic compare-and-swap. A confirmed write is
followed by atomic local state replacement. If state persistence fails after
the issue write, the command reports failure; inspect the issue before retrying.
No scheduler, workflow, or automatic answering is enabled.

## Operator actions

An operator action is a proposal, not permission to write. The schema in
`operator-actions.schema.json` is shared with the review site; the Rust checker
also enforces configured repository scope and comment provenance. This implements
the schema half of tracker#582, not its execution UI.

One unquoted, unindented `agent-board-action` fence holds one object. Its
`schema` is `agent-board/operator-action/v1`, `title` is one line (200 characters),
`why` is a nonblank reason (4,000 characters), and `actions` holds 1–50 mutations
in execution order. Unknown fields and nulls are refused. Numbers are positive
JavaScript-safe integers. Text lengths count Unicode characters.

Every mutation has `type`, `repo` (`OWNER/NAME`) and `number`. The types are:

| Type | Additional required fields | Intended mutation |
|---|---|---|
| `close_issue` | `reason` | Post the reason comment, then close the issue |
| `reopen_issue` | none | Reopen the issue |
| `add_label`, `remove_label` | `label` | Add or remove this exact label |
| `set_project_field` | `project`, `field`, `value` | Set Priority or Status on the item's GitHub project URL |
| `add_sub_issue` | `parent_repo`, `parent_number` | Attach the issue to this parent |
| `move_sub_issue` | `parent_repo`, `parent_number`, `previous_parent_repo`, `previous_parent_number` | Remove from the named old parent, then attach to the new one |
| `approve_pull_request` | `head_sha` | Approve exactly this 40-character lowercase hex head |
| `merge_pull_request` | `head_sha`, `method` | Merge exactly this head using merge, squash or rebase |

Labels and field values are nonblank, at most 200 characters; reasons are at
most 4,000. Project URLs use the existing GitHub project identity rules.
Project numbers have at most 15 decimal digits, without leading zeroes. Integer
numbers accept equivalent JSON spellings such as `1.0` and `1e0`, as JSON Schema
and JavaScript do. Each parent repository must also be on the allowlist. These are typed mutations,
not arbitrary API requests; a consumer must not infer an issue is a PR or vice
versa from its number.

### Check

```sh
agent-board action check "$ISSUE" --config /trusted-checkout/operator-actions.json
```

The repository-owned file, read from a protected default-branch checkout, has
exactly `writers` (operator and bot logins) and `repositories` (explicit allowed
repositories), both nonempty arrays of at most 100 strings. There is no implicit
organisation allowlist, no default configuration and no execution switch. Do not
source this file or its path from proposal content or dispatcher workflow inputs.
To widen repository scope, the operator changes that file through normal review.

The checker reads at most 1,000 issue comments using the job-plan reader and
applies the same newest-writer and foreign-edit rules as [job plans](job-plans.md).
This stops a visitor's copied proposal or a collaborator's edit being accepted
as the operator's proposal; a foreign edit that removes the fence still blocks
fallback. It prints each validated mutation as JSON Lines, preserving order,
and identifies the source comment on stderr. No writes occur.

Checking does not inspect current target state, project membership/options, old
parent relationships or PR heads. The review site must check these before acting,
flag stale actions, use the viewer's credentials, stop on the first failure and
record execution once. Project scope is not write authority: repository scope
alone does not authorize changes to any project. Execution and result markers
are deliberately left to that separate implementation.

`fixtures/operator-actions.json` contains shared accepted/rejected schema cases
and configuration. Both validators should run every case; provenance checks are
separate because they require GitHub comment metadata.

Run `just test-action-schema` with Ajv 8 available on `NODE_PATH` for the
JavaScript schema fixture check, and `cargo test --locked -p board-forge action::`
for the Rust contract and provenance tests.

## Project status updates

`agent-board project status-update --owner my-org --project 7 --status on-track`
publishes one update using the operator's project-write token. Status is required:
`on-track`, `at-risk`, or `off-track`. Nothing schedules or enables automatic
publication. This is an explicit operator write, not delegated output application.

Pass `--body FILE` to publish a UTF-8 body verbatim. Without it, the command reads
the project's status history and reports issue and pull request activity strictly
after the latest update's creation time. The first report covers all current
members. Each changed member appears once, sorted by repository, number and kind,
as closed, created, or updated (in that precedence). Titles and bodies are not
included. No activity still produces an explicit empty report.

The summary describes current members' content timestamps, not a historical board
diff: removed members and field-only changes cannot be recovered from these facts.
Incomplete reads, draft/redacted members and invalid timestamps fail rather than
publish a misleading summary. Reads use the existing pagination request limit.
Bodies must be nonempty and at most 4,000 Unicode characters; oversized summaries
fail rather than silently drop activity. Use a concise body file in that case.

The command rejects offline snapshots and JSON rendering and prints the created
update node ID. It requires project write permission, checks the requested project
identity before writing, and checks the returned body/status receipt. It does not
add a reporting-interval gate, retry a failed mutation, or prevent concurrent
operator publications. No workflow, credential store or delegated authority is
introduced.
