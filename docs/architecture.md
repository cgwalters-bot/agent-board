agent-board has two loops over the forge: one follows fixed rules, and the other
uses judgment. The [pass](pass.md) specifies the first in full. This page records
the decisions both follow. Where an older page disagrees, this one wins.

```text
  cron --> agent-board pass ---dispatch---> dispatcher ---> agent job
           (usage, follow PRs, epics,       (agentic-job        |
            Status, schedule)                or another)        |
                |          ^                                    |
         writes |          | reads                              |
                v          |                                    |
        forge: board, issues, PRs <--- pull requests, comments -+
                |
                | reads pass's output and the work it audits
                v
           supervisor <------ talks with ------> operator
```

## Two loops

`agent-board pass` is the heartbeat: a cron runs it, it finishes once, and the
same facts give the same decisions. One pass refreshes usage, follows pull
requests (the standalone `poll` becomes this stage of pass rather than a
separate command), plans epics, derives Status and schedules new work (see
[what is built](pass.md#what-is-built)).

The supervisor is an agent that answers "is the system working?". It audits
individual pieces of work from time to time and is who the operator talks to.
It does not schedule and has no health engine of its own: it reads pass's
output and the forge.

After a deployment moves its pinned agent-board revision, the supervisor's
next audit reads what changed between the pins, exercises it with a
`pass --record` preview against the previous recording (and, for new writes,
one apply with `--max-dispatch 1` and a small `--max-writes`), and reports what it
saw to the operator, recommending a rollback of the pin if it misbehaves.

Why: a scheduler should be boring and replayable, and judgment should not
compete with it for the same decisions.

### Proposed read-only persistent consumer

tracker#1456 proposes a persistent deployment reading the same deterministic
preview decisions. `board-forge::pass::decision::preview` is the bounded library
seam: it invokes `pass::run` in `Mode::Preview`, reuses holds/needs-you (including
Act now and next context) and work projections, and exports `agent-board/decision/v1`.
It does not parse `Report.lines`, create a scheduler or change CLI/publication
output. Needs-you extensions remain caller-configured; an unavailable projection
is null, not an empty inbox. Existing pass reads may consult forge receipts and
carried evidence; the library never scrapes rendered comments to recover decisions.

The concrete threat addressed by its read-only transport is an accidental apply
path in a persistent preview consumer. REST methods other than GET (dispatch and
rerun POSTs included), GraphQL documents with a `mutation` token, and accounting
callbacks are not forwarded. Both synchronous and asynchronous GraphQL are
guarded. This conservative check also refuses that token in a comment or literal;
it is for library-owned documents, not arbitrary GraphQL passthrough. Deploy with
read-only credentials too; this adapter does not constrain an independently
supplied transport's implementation of reads.

Observation time is not source validation time. The snapshot preserves needs-you's
validation clock, usage's computation clock separately from per-pool observation
clocks and stale/missing/partial evidence status, carried hold
provenance, per-repository coverage, nullable candidate/WIP counts, preview starts
and separate confirmed effects. WIP retains the pass's preview semantics (including
would-start slots), not a count of confirmed new runs. Issue work coverage remains
incomplete because admission may stop at caps without reading all plans. The
existing 200-item work bound counts omitted entries per repository. Holds/needs
reuse the 60,000-character single-comment fitting bound and its omission counts;
pools are limited to 16 with an explicit omitted count. These are bounded sections,
not a new total wire-size contract. Missing sections or incomplete coverage must
never be rendered as proof of no work.

This is a library capability, not deployment approval or a daemon switch. Forge
records remain authoritative, caches disposable, and the applying pass remains
the one writer. #794 owns cache changes; #788 owns coordinating generic policy
work. Caller configuration and deployment prompts stay outside this public API.
Phase 3's credential decision remains unresolved. Bot comments describing the
proposal do not resolve it or constitute operator approval.

### Phase-3 proposal boundary (specification only)

The concrete threats are a modified or old preview authorizing a start, merge or
label change, and two controllers writing when a service outage starts the fallback.
The following is an **offline contract**, not a supported input to `pass --apply`,
an executor implementation or a deployment decision. Nothing enables it by default
or by configuration today. The executable reference model is test-only in
`crates/board-core/tests/executor_contract.rs`; its shared wire fixture is
[`executor-proposal.json`](../fixtures/executor-proposal.json). It tests admission
and recovery rules, not live forge atomicity or the existing pass's policy engine.

#### Proposal v1

`agent-board/executor-proposal/v1` is separate from `agent-board/decision/v1`:
display snapshots and candidates are never executable authority. Its initial typed
intent vocabulary is deliberately incomplete: start an accepted issue plan by
comment ID/revision, merge a PR at an exact head, or derive one status label while
preserving unrelated labels. No API method, URL, workflow, credential, prompt or
arbitrary request body can be supplied. A future implementation must lower through
the existing pass/dispatch/poll/status paths, not add a second policy engine.

All fields are required; unknown fields, duplicate fields, unsupported schemas or
intent kinds and null facts are rejected. Bounds are 64 KiB before parsing, 1–20
intents, and a validity interval of at most 300 seconds. The executor may impose
smaller bounds; these do not increase existing `--max-writes`, `--max-dispatch`,
request/time limits, WIP or pool caps. Attempted claims, receipts and ambiguous POSTs
still consume the existing caps/reserves. A proposal is not a reservation.

The fixture uses integer UTC Unix seconds for `observed_at`, `created_at` and
`expires_at`; require `observed_at <= created_at <= now < expires_at` and
`expires_at - observed_at <= 300`. Cache reads cannot advance observation time.
`config_digest` binds the complete reviewed caller configuration, including scope,
policy, referenced pools/bounds files and pinned lowering revision, not merely a
path or mutable branch. `producer_revision` is the exact reviewed 40-hex commit.
Each action carries an evidence fingerprint (SHA-256 of the relevant complete
observations); absent/partial facts cannot be encoded as a successful observation.

Plan identity is lowercase SHA-256 of compact serde JSON serialization of the
typed proposal in declared field order (arrays retain order; no maps, whitespace
or optional fields). The schema version fixes this encoding. It is external to
the payload: the caller pins the identity of the immutable bytes it selected,
and the executor recomputes it. A replacement is a new plan, never an edit under
the old identity. **A digest is integrity, not authentication.** Neither a
self-declared digest nor an authenticated producer authorizes effects. The caller
selects the proposal through a trusted channel, loads its own reviewed config and
revision, and checks all three bindings; proposal text cannot select those values.
The fixture tests a trusted baseline identity, not a producer-supplied checksum.

Immediately before *each* effect, with the writer gate held, reread complete forge
facts and run the existing decision/admission code. Starts recheck accepted plan
author/editor/revision, Issue identity, scope, dependencies, open PRs/runs, leases,
WIP, usage/budget and pool room. Merges recheck exact head, author, draft/base,
operator approval where required, authenticated review, required checks and queue
policy. Labels rederive Status from current issue/PR/run facts and reread current
labels; never replace unrelated labels from a stale snapshot. A changed head,
source revision, relevant evidence or intended operation requires a new preview;
incomplete/denied facts hold. Passing schema/digest checks alone never reaches a
write. The test model compares against injected freshly rederived actions; it does
not pretend to implement these forge reads. External forge changes still have
their existing read/write race; use exact-head conditional merge and available
conditional writes, and never claim a cross-API transaction.

#### One writer, claims and outage recovery

Use **one caller-owned serialized writer gate**, not a service lock plus a separate
fallback lock. For an Actions executor this means the same caller repository,
workflow-level concurrency group, `cancel-in-progress: false`, and all mutation
steps inside that job's lifetime. Both proposal execution and standalone full-pass
fallback must enter it. Preview producers stay outside and cannot mint write
tokens. The gate's owner run ID is the fencing epoch recorded with every claim;
an old owner cannot resume under a new epoch. Gate ownership must be verified
before credentials are issued and before each mutation. A timestamp lease alone
does not fence GitHub writes: GitHub does not enforce an epoch on arbitrary POSTs.

Do not steal a gate on timeout or mere absence of a heartbeat. Before handoff,
the old writer must terminate, credentials must no longer be usable and in-flight
requests must be drained/reconciled. Cancellation or an unknown writer outcome
requires recovery/explicit intervention, not automatic timeout takeover. This is
a requirement on the later caller implementation, **not a guarantee provided by
Actions concurrency alone**. If direct service writes are selected, they too must
enter this same gate with a bounded writer lifetime; otherwise an independently
verified forge-enforced fencing primitive is a prerequisite, not a second lock.

Inside the gate, reuse existing forge-authored claims and receipts. The semantic
effect key is SHA-256 of the typed intent, excluding proposal identity, clocks and
observation fingerprint. Thus a fresh preview of the same accepted plan revision
or PR head cannot bypass a claim. Claims bind key, immutable plan ID, owner epoch,
target/source revision and status. Only verified bot recorder/editor identities in
the configured forge scope count; copied markers and local cache entries do not.
Read claims before action; write pending before submission; then bind the returned
run/merge/label result in a confirmed receipt. Confirmed start/merge keys are
terminal no-ops. Labels are repeatable reconciliation: an old confirmation is
not proof that the desired label is still present. A **new** proposal (or a new
standalone pass invocation identified by its gate run) may rederive and apply that
status again after an intervening transition. Keep completed `(plan ID, effect
key)` receipts so replaying an already consumed proposal cannot reapply a label,
even after later transitions. A pending semantic key still holds every caller
until reconciled, regardless of plan ID or expiry. These records live on the forge,
not in service state; do not replace receipt history with just the latest status.

On a lost response or a successful effect whose receipt failed, inspect existing
forge runs and their dispatch correlation, exact-head merge/queue state, or current
derived labels under the existing recovery protocol. Record confirmation only
with matching evidence. Proven refusal/no submission can release a claim within
the existing retry policy; elapsed time or an absent search hit is not proof.
Ambiguous results remain pending for reconciliation, never blindly resubmitted.
Receipt recovery may continue after plan expiry, but cannot authorize a new effect
from an expired plan. Claims are not garbage-collected just because a plan expired.
The serialized gate is essential: comment creation itself is not compare-and-swap.

If the preview service is down, fallback acquires that same gate and runs the
existing full `pass --apply` from trusted config, fresh forge reads and durable
claims/receipts. It does not fetch a service plan, consult service memory, reset
receipts, or wait for the service to acknowledge ownership. It can skip an
ambiguous item and safely handle other work within caps. Restart and cache loss
reconstruct ownership/effect history from Actions and the forge; they never erase
pending claims. An unavailable forge/gate fails closed; independence from the
preview service does not mean independence from forge authority.

## Writes

`agent-board pass --apply` makes its own writes directly; agentic-job's
independent check and apply is for what an agent produces. Guards and
caps are in [order and effects](pass.md#order-and-effects).

Why: the pass's writes follow from forge facts by fixed rules, so a second
checker would re-derive the same answer at the cost of another moving part.

## Status

Status is derived and written each pass from live facts: Done, Needs human
and In Progress are never set by hand; Todo, Backlog and Priority are a
person's choice, and Blocked and Backlog are holds that only Done replaces.
The rules are pass's [stage 5](pass.md#order-and-effects). Any open pull
request for an item makes it In Progress, draft or not, in any repository
and by any author, so an upstream issue with a fork's pull request is In
Progress; an issue a person marked Done that is still open goes back to
Todo, since open means not done.

The live Status set is Todo, Backlog, Blocked, In Progress, Needs human and
Done. The others (Triage, Draft, In Review, Cancelled) are legacy statuses that
the derived rules override. Remove them from the board once the pass has run
for a while, not now.

Why: a status someone has to remember to change goes stale, and a stale board
misleads both the operator and the scheduler.

## One marker for the operator

The `needs-human` label is the single marker that the operator must act. The
board's Needs human status comes from it. Question issues and the decisions
document fold into it: a question is an ordinary issue or pull request with
the label, and answering it means acting and taking the label off. `agent-board
ask create` labels its question and the item it blocks, and `ask resolve` takes
the label off that item once no other open ask names it; neither writes Status.

Why: several ways to say "waiting on you" mean several places to check, and
one of them is always forgotten.

## Bookkeeping

Where the tool keeps its state depends on whose repository the work is in.

* **External or upstream repositories:** minimal noise. No claim or status
  comments. Any state the tool needs lives in one hidden comment it edits in
  place.
* **First-party repositories:** state lives on the issue or pull request
  itself, readable by people and machines alike: a short human line, with the
  machine detail alongside it. Not in a separate store, and not as scattered
  hidden markers.

Why: upstream maintainers did not ask for a bot's ledger in their threads,
while on our own issues the record is most useful where people already look,
and a person should be able to read what the machine read.

## Promote

A fork pull request the operator requests be promoted is evaluated by standalone
`agent-board promote --config FILE` (#308). The newer
[decision context](https://github.com/cgwalters-forge/agent-board/issues/308#issuecomment-6606946679)
supersedes the old pass-stage and review-only plan. The command previews
command/head evidence and candidate read gates by default. Explicit publication
uses no inference pool or dispatch slot. The pass's stage 4b reports selected
candidates and their first held gate through the same read-only evaluator; it
never publishes, even with `pass --apply` and `promote.publish` set. This makes
approved work visible without granting the pass upstream write authority.

* **Permission.** An exact operator-authored `/promote` or
  `/promote --human-text` conversation command after the observed push
  establishing the current head is a trigger. This preview accepts only a
  complete plain command comment, with optional surrounding newlines, not prose
  containing a command. REST comment identity/creation must agree with GraphQL
  metadata; missing edit metadata or any operator-comment edit holds, even when
  REST creation/update timestamps match to the second. The only other trigger
  is opt-in: with `promote.onApproval` (default `false`), drafts are candidates,
  since a midstream's pull requests stay drafts, and on a draft with no such
  command the operator's latest deciding review, approving the current head
  and submitted after the push establishing it, is the trigger (never
  `--human-text`; agent-board#743). Its URL stands in the `command=` evidence.
  Approving a ready fork PR never triggers: that may mean merging it into the
  fork alone. So the approval must also follow the PR timeline's latest
  `convert_to_draft`, or a later conversion to draft would turn it into one.
  Quoted examples, another author's command and a command before the latest
  push grant nothing. Later operator change requests or dismissals cancel the
  command; approvals and comment-only reviews cannot restore it, as a cancelled
  command stays the one selected. The concrete
  threat is publishing a changed head using stale permission, including after a
  force-push back to an old oid. Complete authenticated branch activity, not
  commit author/committer dates, proves the push. Missing, truncated, edited
  with unverifiable authorship, ambiguous or out-of-order evidence holds.
* **Where it goes.** `promote.forks` in the configuration, never the pull
  request's body, which anyone can edit. At run time the fork's GitHub parent
  or network root must be the configured upstream. A fork may also be in
  `follow` only when `midstream` owns it; stage 2 must then verify its topic
  membership before following it with midstream's no-merge policy. Otherwise
  it refuses, so a missing topic cannot permit a merge into the fork's main.
* **Candidate read gates.** Only after command/head evidence passes, read in
  order: all upstream PRs for the head repository owner's branch (same open
  head is already promoted; different, closed or merged holds); upstream-base
  comparison (zero ahead holds; preview reports behind heads as needing a
  publication rebase); the issue's accepted plan's `stacks_on`; DCO facts from required
  base-branch checks or base-head check runs; and unchanged title/body text.
  This prevents duplicate publication, stale bases, unmerged dependencies,
  unsafe sign-off rewrites and references changing meaning upstream. Only a
  unique closing or `Part of` reference to an issue in the fork ties a PR to
  its plan; ambiguous/missing linkage holds. No plan or no `stacks_on` means
  unstacked. A parent's open fork PR, open upstream PR or closed-unmerged PR
  holds; only its matching-head upstream PR merged into the configured base
  passes. Accepted-plan comments require complete edit metadata. DCO never comes from CONTRIBUTING.
  When required, report missing operator sign-offs; commits needing a sign-off
  that are merges or by neither bot nor operator hold. Empty bodies, bare
  `#N` references and closing references to the fork hold, never get rewritten.
  All reads use the existing budget and complete bounded pagination (ten
  100-row pages); unreadable/incomplete evidence holds.
* **Policy gate.** Only a candidate that passed every read gate above reads
  its upstream's record, once per run, from
  `policyRepository/policyPath/OWNER/REPO.md` on that repository's default
  branch; promote never writes one. The record is homegit's format: `---`
  front matter with `verdict`, `ai-trailer`, `dco`, `sources` (`repo`, `path`,
  `sha`), `checked` and optional `rebase`, then a non-empty body. A 404 holds
  as `policy missing`; a version that is not a regular file in its commit's
  Git tree (the contents API serves a symlink's target as a file at the
  link's path, and the target's edits are outside the record's history),
  unknown key or malformed record as `policy invalid`. It
  holds as `policy stale` unless every source is still a file or directory
  (a symlink's id names its target, not its text) with its recorded blob or
  tree id on its repository's default branch and the top level, `.github`,
  `docs` and `doc` of the upstream and its owner's `.github` repository hold
  no unrecorded file named like homegit's set (contribution guides, agent
  instructions, PR templates, DCO texts, AI/LLM as a word); a 404 directory
  is absent, any other unreadable or truncated listing holds. Homegit's
  loosening rule is ported over the record's default-branch commit list
  (complete, bounded; per version, one tree read per path segment and its
  content, which must be its tree's blob): a looser verdict counts only
  from a GitHub-verified commit the operator both authored and committed
  (GitHub verifies the committer; anyone can set an author), or a merged
  pull request whose merged head the operator last approved and whose merged
  tree is that head's; otherwise `policy loosened by LOGIN at SHA`. As in
  homegit, a record's first version sets the baseline unvouched, since the
  policy-check agent creates records. GitHub's path history does not follow
  renames, unlike homegit's. `bot-ok` passes; `human-text` requires the per-PR
  provenance gate below; `human-only` and `no-go` hold naming the record's sources.
  The threat is the bot publishing where maintainers refuse it, on a record
  that no longer describes the upstream, or one someone else loosened.
  Passing prints `would promote ... (policy bot-ok)`, not publication
  permission: publication still remains. No
  bot-fork staging success is implied.
* **Human-text provenance.** The threat is passing bot-written or changed text
  off as the operator's merely because the operator posted a command. Only a
  fresh, unloosened `human-text` policy invokes this gate; `bot-ok` needs none
  of these proofs. The selected exact command must be `/promote --human-text`,
  and authenticated branch activity must name the operator as the actor of the
  latest push establishing this head, including a force-push back to an old oid.
  Commit authorship, committer identity and the command author are not push proof.
  A separate GraphQL read must agree with REST on PR identity, head, title and
  body. Its complete `userContentEdits` history and body's `editor`/`lastEditedAt`
  must agree on an operator last edit; its complete `RENAMED_TITLE_EVENT`
  timeline must chain to the current title with an operator last renamer.
  No edit or rename on a bot-authored PR is not operator authorship. Deleted or
  unnamed editors, ambiguous order, missing metadata or pagination holds as
  `needs-text`, naming the failed proof. A single bounded read accepts fewer
  than 100 edits and rename events, with `hasNextPage=false`; larger histories
  hold, within the shared request/time budget. GitHub's filtered timeline
  `totalCount` includes other event types, so it is not a rename count.
  The observed API exposes edit actors/times, not a signed text-version digest;
  the current GraphQL body and matching last-edit metadata bind the proof, not
  a timestamp alone. Both last text changes must strictly predate the selected
  command; equal-second or later changes require a fresh command. A body still
  containing `Generated-by:` holds. Only upstream policy results are cached:
  every PR's provenance is independently evaluated. Passing reports `(policy
  human-text; provenance verified)`, not live publication. No labels or notices
  are written, and title/body text is never altered or supplemented.
* **Kept.** The upstream contribution-policy gate; the operator's sign-off
  added to every promoted commit, whether or not upstream checks DCO; the stacked wait (a pull
  request whose dependency is not yet upstream waits); one notice per reason
  on the fork pull request; and `--human-text`, the one marker that the
  operator wrote the text, in the `/promote --human-text` command. That marker
  alone is not proof of text provenance.
* **Dropped.** The advisory comment quoting the upstream's rules, unless the
  policy blocks the promotion: then the blocking notice says the verdict and
  what it rests on, once. Also homegit's `--include-others` and
  `--no-signoff`, which become refusals, its `--why`, its policy-cache issue
  and its attempts cache.
* **Commits.** Their existing trailers stay; no commit is rewritten to change
  an older generated-by trailer. The only allowed rewrite adds the
  operator's sign-off and cleanly rebases onto the current upstream base.
  A behind approved head needs no fresh approval after a clean rebase; a
  conflict holds without publishing. Rewriting requires a linear chain of
  commits by the bot or operator; other authors and merge commits hold.
  Original authors, author dates and existing trailers are preserved.
* **Noise.** The upstream repository gets the pull request and nothing else.
  The fork pull request, first-party, gets readable state with its machine
  detail alongside ([bookkeeping](#bookkeeping)).
* **Publication.** The concrete threat is an existing preview caller unexpectedly
  writing upstream, or a command publishing a head the operator never approved.
  `promote.publish` defaults to `false`. Publication needs that caller setting,
  `--apply --max-writes N`, the existing authenticated command, and the operator's
  latest deciding review approving the exact current head. A comment-only review
  does not cancel approval. Before the first write it re-reads the PR and every
  gate, including uncached policy and human-text provenance; changed command,
  title/body, readiness, labels or head refuses. It reserves three writes (four
  when creating a rebase/sign-off branch) as a
  whole step and handles at most one candidate per invocation, in repository/PR
  number order, within the existing request/time budget. Record/replay remains
  preview-only; apply uses the caller's `GH_TOKEN` through the existing transport.
  Git preparation uses an isolated bare repository: no candidate code, hooks,
  filters or configuration is executed. Fetches use the configured repositories
  and exact object ids, depth 1001, with one 120-second Git deadline. Git must
  be installed. The existing `GH_TOKEN` (or `GITHUB_TOKEN`) is passed to Git
  through its environment, never a URL, argument or persisted credential.
  To prevent orphaned receipts and edited operator comments blocking recovery,
  `/user` must identify the configured bot before any publication reads/writes.
* **Publication effects.** Create a **draft** upstream PR from `OWNER:BRANCH`,
  or update the title/body of the unique open same-head upstream PR. Send the
  fork title/body bytes unchanged, including for human-text; add no attribution
  or sign-off paragraph. Existing readiness is unchanged. There is no ready,
  merge, reopen or approved-ref update operation. If any commit lacks the
  configured operator trailer, or the head is behind, Git replays every commit
  onto the observed upstream base and adds the trailer wherever missing,
  regardless of detected DCO checks. It creates a deterministic
  `bot/promote/APPROVED_OID` branch in the same head repository,
  never overwriting an existing ref. The approved fork branch remains untouched;
  approval and human-text provenance stay bound to that original head. The
  branch name has only the approved head, so a rebuild after upstream advanced
  would be a different head on the same name: a retry reads the fork PR's
  receipt before rebuilding anything (below). Without a receipt for this head,
  a publication branch already at another head holds for inspection before any
  write, never overwritten, and a rebuild needs its upstream PR to be at the
  rebuilt head. An existing upstream PR on the original branch that needs
  rewriting holds for manual migration, rather than creating a duplicate PR.
  The upstream base and approved head are checked again before pushing the new
  branch.
  Draft creation is deliberate:
  GitHub's branch-based POST can race a push, so it must not mark an unapproved
  head ready. Verify the branch immediately before publication and verify the
  returned head, branch, base, repository and text before recording success.
  A mismatch records no success and closes nothing; a draft may have been
  created and needs inspection. This is not atomic snapshot publication.
* **Recovery and noise.** A single bot-authored status comment on the fork PR
  is the receipt. Before the first write it records the approved head and the
  head and branch about to be published, as an `agent-board-promoting` machine
  record; it is then edited to the success record (or the uncertain publication
  error, keeping the pending record). On retries edit it to pending first;
  multiple receipts refuse. A retry reads the receipt before any rebuild, and
  a receipt with a machine record counts only when the forge's edit evidence
  shows the bot alone wrote and edited it, as the handoff's. A success record
  for the current approved head whose upstream PR is open at the recorded head
  and branch is skipped without writes, or has its text updated from that head,
  so later candidates progress and nothing is rebuilt on a later base. A
  pending record whose branch is at the recorded head resumes from it: the
  upstream PR is created or updated without a Git run. A pending record whose
  branch was never pushed publishes again under a new receipt; a branch at
  another head holds. A receipt without a machine record is replaced without
  edit evidence: it steers nothing, and the bot's edit makes the bot its last
  editor again. One
  candidate's hold is one line, and the next candidate is read; only the write
  step's failure ends the invocation, as its writes were the one slot. An
  ambiguous POST failure is not retried in the same invocation: the next
  invocation observes existing upstream PRs first, and never creates a second
  one intentionally. Concurrent invocations still need caller serialization;
  GitHub does not offer an atomic create-if-absent status comment. Nothing
  except the PR is posted upstream. Fork PRs remain open: capped, recoverable
  fork closure requires separate acceptance after the handoff replay proof.
  No unsigned head is published: sign-off completeness is checked independently
  of DCO detection before publication. Live publication and bot-fork staging
  verification remain unverified by the offline fixtures.

   before selecting or counting receipts.
   REST comment identity/times must agree with complete GraphQL bot authorship
   and bot last-edit evidence. Network/base mapping, unique source linkage,
   fork head and the live upstream PR/head must all match. A verified open
   upstream supplies In Progress and the existing scheduler open-PR hold even
   if the fork is closed or stale. A matching verified closing merge supplies Done
   under normal Status precedence; person holds remain until Done. Missing,
   malformed, foreign-edited, conflicting, closed-unmerged or unreadable handoff
   evidence refuses the board read rather than releasing work. An ordinary
   open bot fork without a receipt still holds as an open PR; a closed one
   without any first-party publication marker is an abandoned attempt, not
   an error or completion. A verified merged `Part of` slice does not complete
   its source or conflict with the next slice. This conservative
   whole-board failure is deliberate, not a new state store. Start rechecks
   use the same verifier. Fork closure is **not delivered**: it needs its own
   capped, recoverable acceptance after replay proof. Caller rollout and
   staging acceptance remain tracker#1464, separately approved; no live
   promotion or bot-fork acceptance is claimed by edited response scenarios.
2. **`--human-text`.** Only the operator's command carries the marker; the
   read-only provenance gate checks the current-head pusher and title/body editors.
3. **Policy records.** Read from the configured repository's default
   branch, using homegit's rule that only the operator can loosen a verdict;
   never written.
4. **Stacks.** The plan's `stacks_on` is the source; a pull request with none
   is not stacked.
5. **Drafts.** A draft fork pull request is never promoted, unless
   `promote.onApproval` is set; it is then published as an upstream draft.
6. **Behind upstream.** Refused, with one notice, even where it would merge
   cleanly: the command-bound head would go upstream untested against the new
   base, and rebasing needs `git`.
7. **A head in the bot's fork.** Whether an upstream takes a pull request
   whose head is in the bot's fork is verified with one recorded call in a
   staging organisation, not assumed. If it does not, the branch is pushed
   into the midstream first, as a counted write.

Three rules learned from reviewing the first attempt (agent-board#312):

* **Re-read the decision.** Immediately before any future first mutation,
  re-read the command, its authorship/edit evidence, cancellations, PR head,
  branch push evidence and readiness/labels; hold unless it is still the same
  command bound to the same observed head and no `needs-human` was added.
  Revalidate policy and all human-text provenance too, including the exact
  title/body version predating that command. Future human-text publication must
  send those unchanged title/body bytes, with no attribution or sign-off note.
* **Move a ref only by compare-and-swap.** The branch ref is moved only by
  an update that names the expected old object id (GraphQL `updateRefs`),
  never by a read, a REST `PATCH` and a second read. That sequence can lose a
  push that lands between them.
* **Check the head published.** The upstream pull request is created from a
  mutable `OWNER:BRANCH` head, so the job checks the head sha in the
  response against the command-bound one; on a mismatch it refuses, records no
  success and closes nothing.

The preview reports candidates only; apply additionally requires current-head
review approval and refuses missing DCO sign-offs. Sign-off semantics/proof and
rewrites, recoverable fork closure and the caller's independent 10–15 minute
tracker schedule remain follow-up slices. The known recording limitations for
typed absence and policy tree projection remain separate work; edited mock
scenarios are not successful live recordings. Creation sends
`maintainer_can_modify: false`, so upstream writers get no push access to the
bot fork's branch, its workflows or its secrets. Bot-fork acceptance still
requires the recorded staging call before deployment; no staging or live
promotion is claimed here.

Why: the authenticated operator command is bound to a head by observed forge
push evidence, not by the content's claim about itself. Configuration and read
facts determine where it may go. An upstream sees only the pull request, as a
person would have opened it.

## Async forge I/O

Forge I/O moves to async in slices (#300). The first is in: the GitHub board
snapshot reads through `board-forge`'s async client, on the one
current-thread tokio runtime the CLI's `main` builds. That covers every
command that loads a live GitHub board (`item list`, `project view`,
`reconcile plan` and the others that take `--owner` and `--project`), the
pass's Status stage and the live fixture's readback. The client holds its
limits in one place: at most `MAX_IN_FLIGHT` requests at once, and a
request GitHub refuses under a rate limit retried at most
`RATE_LIMIT_RETRIES` times, waiting at most `RATE_LIMIT_WAIT` in all for
that request and never past its deadline (a pass's time bound). A refusal
is a 429; a 403 with `Retry-After`, no requests remaining or a message
naming a rate limit; or GraphQL `RATE_LIMIT` errors without data, which is
how GitHub answers a secondary limit, with HTTP 200 and no `Retry-After`.
Each retry waits what `Retry-After` or `x-ratelimit-reset` asks, or else
`SECONDARY_WAIT` (a minute) doubled for each retry before, as GitHub asks.
The sync paths below retry by the same policy, and one given up on is a
typed `RateLimited` error. The snapshot's request budget is passed per read,
`SNAPSHOT_REQUEST_LIMIT` (1,000) by default; running out is an error, never
a partial snapshot.

Every other forge request is still sync on ureq: the poll's and `status`'s
own reads (the board they load is the snapshot), the project schema read
before a write, dispatch, epics, the rest of the pass, the writes, and
Forgejo. They share the snapshot's paging through an adapter
whose reads never wait. The conditional-request cache comes later, as client
middleware; a forge crate is extracted then. A Forgejo write side and
dispatch, when built, extend Forgejo's sync transport and do not wait for
this migration ([forges](forges.md#io)).

Why: a pass reads many independent things, and sequential requests make its
time grow with the board. Slices keep each change small, with its tests green.

The client is reqwest (rustls with ring, as ureq's, and the platform's trust
store) under a thin layer of our own, not octocrab. Octocrab's GraphQL is
untyped JSON, like ours, and its typed Projects v2 models are for the REST
endpoints, which the snapshot does not read. Its rate-limit retry bounds the
number of retries but not the total wait, and it has no cap on requests in
flight. So we would write both limits either way, on top of about 40 direct
dependencies (hyper, tower, jsonwebtoken, chrono and more). Its
conditional-request cache layer is for REST; that slice can look at it
again.

## Reruns and the drop list

One automatic rerun of a run that failed for an infrastructure reason is
kept ([scheduling](pass.md#scheduling)); everything else on the
[drop list](pass.md#drop-list) is dropped.

Why: an infrastructure failure says nothing about the task, so one retry is
cheap and usually right; retrying an agent's failure spends the budget again
on the same outcome.

## Open questions

These are not decided; the pass spec leaves them as they are today or open.

* **Backlog as a hold?** If Todo and Backlog are a person's ready/not-ready
  choice, should the pass refuse to start Backlog items? Today it holds on
  board Blocked instead.
* **When a derived status stops holding.** Today an item whose Needs human,
  In Progress or Done no longer holds goes back to Todo, not to what a
  person set before.
* **What counts as an infrastructure failure.** The rerun needs a fixed
  rule that uses the facts a run leaves to distinguish a runner, broker or
  forge failure from a failure in the agent's own work.
* **Cap numbers.** A pass takes `--max-dispatch` and `--max-writes`, unset
  by default; what the scheduled pass should pass is not set yet. The Status
  stage's first-run guard, `--max-status-changes`, is 50 by default.
* **First-party bookkeeping for PR follow-up.** What poll's hidden fix-claim
  and round markers become in first-party repositories, where state should
  be a readable line with machine detail alongside.
* **Retire the supervisor's own engine?** `supervise health`, the
  check-driven start in `supervise trigger` and the executor's dispatches are
  built and unchanged; should they go once the supervisor reads pass's output?
* **The `question` exclusion (code follow-up).** The pass's candidate set
  still excludes `question`-labelled issues in code; with question issues
  folded into `needs-human`, that exclusion should go.
