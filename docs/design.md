# Design

## 1. Scope and durable model

Pull requests use the [agentic-job review recipe](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/review.md#another-repository), called at `@main`: the base owns the workflow, task and bounds, and the admitted head is data inside the sandbox. Non-draft PRs from owners, members and collaborators start automatically; other authors need `/review` from someone with write access (bots are not admitted). This inherited gate prevents unauthenticated events draining the shared inference cap; each run has 150 requests, a 500 AIC budget (only conventional under plain broker registration), and 75 minutes, not an aggregate per-author limit. No PAT is forwarded; the reusable jobs separate read-only agent access, checked comment publication and commit-status writes, with OIDC for the tailnet and inference broker. The repository variables configure the runner/model; the broker and tailnet must admit the called workflow. Our own (cgwalters-forge) workflows and actions follow `main` until they publish tagged immutable releases ([tracker#544](https://github.com/cgwalters-forge/tracker/issues/544)); third-party actions stay pinned by commit, and Dependabot checks those under `.github/workflows` daily. Until then the `review` status and comment are only as trustworthy as agentic-job's `main`: the called workflow holds `statuses: write` and `pull-requests: write`, so a change merged there could report success without running the reviewer, and the operator accepted that dependency in tracker#544. CI runs specs and Rust on PRs and `merge_group`, and its always-running `ci` sentinel fails for failed, cancelled or skipped dependencies. Queue enforcement remains off until the coordinator configures the ruleset to require only `ci`; do not require `review`, which reports only on PR heads, not merge groups. An agent verdict is not merge authorization: an outside contributor's change still needs a human with write access to approve it.

Build a new Rust project, not a homegit migration. agent-board is a typed interface and controller for a forge-hosted work board. Deterministic reconciliation repairs bookkeeping and admits eligible work; short-lived agentic jobs supply triage, prioritization and synthesis. GitHub Projects v2, issues, comments, PRs and Actions remain the records people inspect and edit. There is no application server, private task database, new chat system or credential-bearing coordinator agent. Code push, PR close/merge and upstream promotion belong to separately bounded jobs. Leave homegit v1 untouched, and never give both controllers write ownership of the experimental board.

Start with one new organization project and an explicit issue-write repository allowlist. All issues in a dedicated intake repository are enrolled; other repositories require a configured inclusion label or existing membership. This catches work opened outside the tool without claiming every upstream issue. A separate read allowlist may include upstream repositories. Only public work is in scope initially; do not copy private context into public tracking issues.

Each item has one canonical issue and one project membership, keyed by native identity rather than title. PRs are results, not a second task queue. Read-only upstream issues can be canonical items; work requiring issue writes outside our authority gets a local tracking issue linking upstream. Do not create project draft items, including hidden drafts used as a key-value store.

| Concept | Authoritative forge representation | Meaning / writer |
|---|---|---|
| Item | Issue title/body and native identity; project membership | Acceptance criteria live in the body. Membership defines managed work; enrollment repairs omissions. |
| Epic and children | Issue with an existing epic label; native sub-issue relation | Decomposition is not a dependency or permission. Unclassified work need not have a parent. |
| Status | Project single-select: Triage, Backlog, Todo, In Progress, Draft, In Review, Blocked, Needs human, Done, Cancelled | Triage replaces null. Draft means a result awaits operator review, not a GitHub draft item. Needs human marks an open ask and the items it blocks. Terminal status requires evidence. |
| Priority | Project single-select: P0, P1, P2 | P0 blocks current work; P1 active focus; P2 parked. No mirrored priority labels. |
| Whose turn | Project single-select Turn: Coordinator, Worker, Operator, External, None | Canonical coordination signal. Native assignees remain human ownership, not a second turn field. |
| Operator ask | One issue per decision, with question, lettered alternatives and blocked URLs; Ask text field links it | Operator answers on the issue. Existing PR review threads can be linked instead of creating duplicate asks. |
| Results and blockers | Project text fields Result, Blocked by, Next, News | URL lists are parsed as typed references. Next is explanation, never executable input. |
| Run | Actions run ID plus attempt, workflow identity/ref and URL; Run field; trusted executor receipt on its request issue | Actions determines queued/running/finished, not model prose. Artifacts hold details, not indispensable state. |
| Numbered slot | Project number field Slot on a claimed item | Slots 1…N are logical capacity, not forge accounts. Unset means unclaimed. One admitted run per item and slot. |
| Budget | Budget tokens and Spent tokens number fields; trusted per-run reservation/usage receipts | Runner enforces per-run limits. Board values support planning; agents cannot raise hard ceilings. Unknown usage is not zero. |
| Request and receipt | Request field links a typed request issue; trusted executor comments record admission/result | Visible forge work request, not a private queue; one outstanding request per item/action generation. |

Reviewed configuration on the protected default branch holds project identity, repositories, operator identities, field/options schema, enrollment, slot count, spending ceilings and fixed workflow routes. This is policy, not a second live board. The project is authoritative for work intent; issue/PR/run objects are authoritative for facts. Reconciliation explains and repairs disagreement rather than overwriting reality. A dedicated control issue carries period accounting checkpoints, outstanding reservations and full-census health; it is updated only by the trusted controller, with verifiable receipts linked. Ordinary project views exclude this control record.

Off-forge storage is limited to disposable snapshots, caches, temporary artifacts and within-scan cursors. Losing these must not lose an ask, authorize a run, reset spending or repeat an irreversible operation. Summarize accounting and action receipts onto the forge before artifact expiry. Credentials remain in CI secret storage, never board fields.

## 2. Agent interface and the Paperclip comparison

### Verified source facts

Paperclip is more than a kanban UI. Its commit-pinned [core skill](https://github.com/paperclipai/paperclip/blob/378e6d95e1fbd52298f56ffcd5e261f80965b6b8/skills/paperclip/SKILL.md) describes short heartbeat windows, injected agent/company/run identity, API access, inbox selection, checkout before work and final disposition. The injected context includes PAPERCLIP_AGENT_ID, PAPERCLIP_COMPANY_ID, PAPERCLIP_API_URL and PAPERCLIP_RUN_ID; local adapters supply a short-lived run JWT through PAPERCLIP_API_KEY. The skill uses /api/agents/me and /api/agents/me/inbox-lite. A mention alone does not authorize taking somebody else's assignment. States include backlog, todo, in_progress, in_review, done, blocked and cancelled. Task documents support revision-aware PUT /api/issues/{issueId}/documents/{key}.

Its [company-skills reference at the same commit](https://github.com/paperclipai/paperclip/blob/378e6d95e1fbd52298f56ffcd5e261f80965b6b8/skills/paperclip/references/company-skills.md) separates the skill catalog/library from agent assignment: installation does not attach a skill to an agent. Names and descriptions support discovery, then the full SKILL.md and supporting references are loaded as needed. Same-company reads and policy-controlled mutation are distinct capabilities; ordinary skill mutation is open unless policy restricts it, while team installation requires agents:create. These are source observations, not results of running Paperclip.

### Point-by-point design response

**Skills and discovery.** Adopt concise descriptions, explicit loading and reference files. Ship board-work, board-coordinate and board-report skills at reviewed commits. Advertise their names/descriptions and paths, preload board-work, and load the other two only for that role. Reject runtime self-installation of privileged instructions: a task comment cannot change the skill revision or policy.

**Identity and context.** Adopt scoped wake context, not an unbounded board dump for every worker. Replace Paperclip's authenticated application API with a credential-free snapshot. The trusted prepare stage supplies forge-attributed actors and events, item/ancestor/blocker context, policy digest and capabilities. A worker cannot claim operator identity by writing it in JSON.

**Task discovery and assignment.** Adopt explicit inbox selection and checkout semantics, not opportunistic work stealing based on mentions. The coordinator sees actionable board items; workers receive one admitted item. Paperclip has a checkout endpoint backed by its service. Projects v2 does not offer equivalent atomic checkout: serialize admission through one trusted job and record the claim before launching work. An agent changing Status to In Progress is not a claim.

**Lifecycle and reporting.** Retain explicit disposition and evidence at the end of a short run. Forge status and result links replace application issue state; ordinary issue/PR comments and linked artifacts replace a second task-document service. A worker reports its own result and proposed disposition, not arbitrary parent completion. Cancelled blockers do not count as successful completion.

**Agent-to-agent communication.** Preserve task-scoped handoff rather than chat-driven implicit assignment. Use request issues, native parentage, explicit blockers and attributed result receipts. Load only relevant comment deltas where possible, but retain a complete-record fallback. A quoted comment, mention or copied marker never authorizes downstream action.

**Heartbeat and continuation.** Adopt short execution windows that act and exit. Every nonterminal item must name a real continuation: admitted run, pending request, operator ask, external dependency or next reconciliation. Prose promising that a watcher will resume work is not a scheduler. Actions run facts and level-triggered scans replace an always-running application coordinator and synthetic heartbeat comments.

**Approvals.** Paperclip's broader approval/organizational model is useful inspiration, not an API to clone. Initially use forge-attributed operator answers and exact-head PR reviews. A response resolves the question it answers; it does not grant unrelated push/merge/promotion authority. Do not introduce hiring, org charts or a general approval service.

**Budgets.** Retain explicit run and period limits, reservations and actual usage. Enforce them in the broker/runner and trusted admission job, not through a model's cost estimate. Do not claim semantic parity with Paperclip budget enforcement without testing its implementation; our proposed guarantee is explicit and independent.

**Security boundary.** Paperclip authenticates agents to an application API. agent-board authenticates the CI job and applier, never gives the model forge credentials, and treats every output as a proposal until independently checked. Agent security is CI security: protect refs, environments, artifacts, dependencies, tokens and dispatch inputs. Prompts are not an access-control mechanism.

### Proposed read/write contract

The prepare stage emits board-snapshot/v1: native project/repository/item identities, schema/options, relationships, facts with timestamps and provenance, compact comments plus operator events, slots/budgets/runs, completeness flags and an injected clock. Large bodies are separately bounded files. Missing/redacted data stays unknown. The coordinator receives the normalized board and intake inventory; workers get the relevant subset.

`gh agent-board … --snapshot FILE` reads offline with no token or network. The binary also runs directly as `agent-board`, without authenticated gh. There is no arbitrary GraphQL/REST passthrough in an agent job. Missing context produces missing_data rather than guessed state. A later read-only gateway is optional.

Mutation commands with --emit print JSONL safe-output proposals. Local validation helps the agent, but only independent check/apply establishes authority. Workers receive item-scoped capabilities; the coordinator receives the configured project/intake scope. Until a trusted apply receipt exists, the agent says proposed, not updated.

## 3. Agentic-job bounds and delegated operations

Use agentic-job from the first PR: policy → agent → check → apply on separate machines. Pin workflow, binary, skills and gh-aw handlers to reviewed commits, except that our own workflow and action references follow `main` for now (tracker#544). Only apply receives a narrowly scoped write credential; prepare may use separate read access, but the model receives neither. Disable incidental notification/conclusion writes unless separately bounded. Never inherit all secrets or forward caller-selected bounds paths, runners, environments, output repositories or workflow refs.

**Current support differs from the proposal.** The inspected [workflow documentation](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/workflow.md), [event contract](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/events.md), [sample bounds](https://github.com/cgwalters-forge/agentic-job/blob/main/.github/agentic-job/allow.toml) and [issue 113](https://github.com/cgwalters-forge/agentic-job/issues/113) must be read together. The sample enables create_pull_request/add_comment/noop/missing_tool/missing_data. create_issue is also collector/check-tested when allowed, but its apply handler has not been exercised by that workflow; labels and assignees have no bounds yet, and parent/blocked_by are refused. The docs explicitly mark real-agent execution, cross-repository calling, analysis mode and several apply configurations untried. Issue 113 is an integration gap, not evidence that its requested expansion already works.

### Proposed exact launch profile

The bounds extension must name a resolved project node ID AND canonical URL, exact issue-write repositories, permissible content identities, field IDs/options and per-type limits. This is a new validation contract, not TOML today's parser already accepts. Retain the existing outer hosts/repos/bases/output/trigger limits. Select analysis/no-patch mode and reject every patch.

Allow at most 20 outputs per run, with these individual maxima:

* **update_project: 10.** Only this project, issue-backed items in the enrollment scope, and existing fields/options. Permit Status, Priority, Turn, Ask, Result, Blocked by, Next and News; at most eight field changes per output. Text fields max 2 KiB; Next/News max 500 characters. No draft/PR content, field/view creation, project creation/settings changes, item deletion or implicit schema extension. Run, Slot, Request and accounting fields are trusted-controller-only.
* **create_issue: 3.** Exact allowlisted repositories; title max 200 characters, body 20–8,000 characters. No agent-supplied labels, assignees, parent, blockers or arbitrary metadata. Disable expiration, auto-close-older and automatic event-parent linking. Creation gets trusted provenance and an idempotency key. Subsequent enrollment failure leaves an issue the census will recover.
* **close_issue: 5.** Exact allowlisted repository and managed item, verified to be an Issue rather than a PR sharing its number namespace. Permit completed/not_planned only, require current completion/cancellation evidence, and disable optional closing comments or relationship side effects. Already closed is a no-op.
* **create_project_status_update: 1.** This exact project, max 4,000 characters, no more than once per reporting interval, and only when material change exists. It is a project edit, not permission to comment anywhere.
* **noop, missing_tool, missing_data: 1 each**, also counted in the total; diagnostic text max 2 KiB.

These are proposed coordinator limits, not gh-aw defaults. Its [safe-output reference](https://github.github.com/gh-aw/reference/safe-outputs/) uses hyphenated configuration names and underscored emitted types. It documents update-project with default max 10, project and cross-repository resolution options. The configured project is not itself an enforcement boundary: the message must explicitly supply the project. Require exact identity before invoking the handler. Disable create_if_missing and reject draft/create_fields/create_view modes; pre-create the schema. The [update_project handler](https://github.com/github/gh-aw/blob/main/actions/setup/js/update_project.cjs) is more permissive than this design. Treat skipped/warned field writes as incomplete until a post-read confirms each requested value. Handler success alone is insufficient.

Map enrollment and board-field edits to update_project; new tasks, asks and request issues to create_issue; accepted completion to close_issue plus update_project; narrative board reporting to create_project_status_update. Labels and assignees are issue properties, not project custom fields. gh-aw's add_labels/remove_labels/assign_to_user/unassign_from_user/add_comment and sub-issue support do not imply agentic-job bounds for them. None is enabled in the strict board-agent profile. Preserve existing assignment; humans establish native parentage initially. An explicitly approved metadata job may later set fixed labels, two configured assignees and same-owner sub-issue links. Until then missing parentage is visible triage debt, not a invented native relation.

No generic update_issue, create_project, dispatch_workflow, PR mutation, repository dispatch or workflow editing capability is granted to the board agent. No project-deletion safe-output was established by this research. Provisioning/deletion is trusted human/CI work. Controller receipts use a separate tightly scoped trusted profile; they are not extra model permissions. Apply integrations must also suppress handlers' implicit event comments and issue creation side effects that would escape this strict profile.

Until these bounds exist in agentic-job, run the board caller in preview: publish artifacts or a separately authorized review comment, not board mutations. Land the narrow bounds/handler integration as an explicit prerequisite. Never work around it with agent-side gh credentials or a generic custom output that executes arbitrary APIs.

### Typed dispatch without a confused deputy

The agent creates a normal issue in the bounded request repository containing fenced board-request/v1 JSON: kind, source_item, target, expected_revision, evidence_urls and reason. Kinds are run_task, close_pr, merge_pr, push_patch and promote_pr. There is no command string, free-form workflow filename/ref or credential input. A trusted checker derives a stable request key from source identity, operation, target revision and canonical payload, and binds provenance to the actual originating run. A copied body marker or asserted author is not proof.

A separate deterministic dispatcher polls or receives trusted issue events, reads the request, then selects from a committed enum-to-workflow map. Its own bounds permit at most three dispatches per pass to exact workflow files at a trusted ref, passing only request identity and payload digest. gh-aw dispatch-workflow may implement this when agentic-job supports that profile; initially use a trusted non-agent dispatcher with fixed routes. Cross-repository operations use fixed wrapper workflows, not arbitrary repository-dispatch targets.

The receiver independently verifies issuer/run provenance, payload digest, target identity and authorization. Being requested by the board bot does not authorize merging. close_pr requires cancellation policy or operator authorization for that PR/head. merge_pr requires current-head reviews, required checks and branch rules. push_patch accepts only the named bot branch, expected old head and validated patch artifact. promote_pr binds source head, destination/base, operator approval and upstream contribution policy. No admin bypass, unexpected-head force push or manufactured sign-off. Each executor has only its operation's credential and emits an attributed result receipt; a PR executor has no project token. Reconciliation then reflects its result.

Use one admission authority and concurrency group per project, plus per-item execution groups with cancel-in-progress disabled. GitHub concurrency is not a durable FIFO: replaced pending events are recovered by the next level-triggered scan. Reserve slot and budget on the forge before launch, correlate request key to run, and read existing receipts on reruns. There is no transaction spanning issue creation, project updates and dispatch. Resume explicit phases and verify by readback. After an ambiguous response, hold the reservation and search for the correlated run; do not immediately repeat the dispatch. If the result cannot be resolved, stop for operator recovery. This is conservative duplicate suppression, not a claim of exactly-once delivery.

Issue creation has the same ambiguity: serialize appliers, use trusted creation keys, and enumerate direct repository records after a timeout rather than relying only on eventually consistent search. If uncertainty persists, stop rather than create another ask/request. Every executor must independently deduplicate request keys.

## 4. Pure rules, judgment and drift repair

`reconcile(snapshot, policy, now) -> plan` is pure. Plans contain stable action keys, prerequisites, reason codes, evidence references and expected relevant values; the same input yields byte-stable sorted output. Plans lower through the same independent check/apply boundary. A model cannot obtain controller-only permissions merely by naming a deterministic rule.

Run a deterministic pass every ten minutes and on relevant issue/comment/PR/run events. Events are wake hints, not the ledger. A daily full census enumerates all board items, including terminal/archived items, all intake issues in all states, linked PRs, asks, requests and runs. Paginate every connection, including nested field values/comments/relationships. Do not use search as a complete inventory. A partial or redacted response blocks actions depending on missing facts; 404 is unknown, not proof of completion. Honor rate limits and expose stale coverage. No cursor can permanently exempt an invariant.

The five tracker#405 drift cases become explicit construction/repair contracts:

1. **Missing status and never-triaged work.** Every enrollment plan includes Triage and Turn=Coordinator. Adding a project item and setting fields are separate API steps, so null is temporarily possible; the null rule repairs it on every pass. Triage older than 24 hours generates a health alert, never automatic execution. Agent failure does not turn Triage into Todo.
2. **Done with an open issue.** Accepted completion produces closure and terminal status as resumable actions. Done alone is not permission to close: require designated accepted results or an authenticated completion/cancellation decision. Unsupported Done is returned to an evidence-derived nonterminal state with an alert. Failed closure remains visible; archiving does not hide it.
3. **Draft whose PR merged.** Inspect designated result reality independently of prior status. A merged resolving PR, with no remaining acceptance criteria or required results, produces issue closure and Done even from Draft or Blocked. Closed-unmerged is not success; a closed fork with an open promoted PR stays In Review. Reopened issues return to Triage unless an explicit resume authorization exists.
4. **Issues opened outside the tool never added.** Enumerate the intake repository and configured enrollment selectors, subtract membership by native identity, then add omissions. Already-closed issues get terminal classification, not a new execution. Only explicit, auditable exclusions remain outside the board.
5. **No full-board recheck.** The scheduled census is mandatory and records coverage/time/counts on the control issue. Monitor failure and stale coverage. Every complete census checks contradictions, duplicate slots, vanished runs, orphan asks and invalid schema, including terminal items.

Turn follows facts: active run → Worker; unresolved ask → Operator; a newer authenticated operator reply → Coordinator for interpretation; external review/dependency → External; terminal → None. A reply is consumed by exact comment identity/revision, not unrelated updated_at changes. It is not automatically approval. A cancelled blocker requires replacement or explicit waiver. An epic does not consume a slot because its children are active, nor complete merely because all children closed if parent criteria remain.

The [GitHub work queue comparison](github-workqueue-comparison.md) records the operator's 2026-10-09 choice of option (b): finish the narrow one-slot approval→run→checked result seam toward a somewhat hardened functional PoC, with agentic-job the more important primitive. Multi-worker fairness, batching and general dependency scheduling are out of near-term scope per that decision; the broader scheduling ideas below are not near-term requirements.

Scheduling starts with one operator-approved worker slot and a bounded coordinator allowance, rather than a fair multi-worker selector. Execution eligibility is independent of editable Status: record an authenticated admission authorization or an explicitly permitted low-risk policy classification. Before dispatch, reserve the full bounded run allowance; available = period ceiling minus trusted spend minus outstanding reservations. Missing usage holds new admission. Runner/broker enforce token/request/time limits during execution; later board observation cannot be the hard stop. Implement this seam incrementally, not by front-loading a general inventory/accounting system.

The model judges whether an issue is actionable, proposes decomposition/priority/estimates, interprets substantive replies and writes reports. It does not decide whether a PR merged, a run exists, an actor is the operator, a budget fits or a workflow is permitted. Apply revalidates irreversible-action evidence on fresh state. Projects lacks general compare-and-swap: serialize tool writes and re-read before/after, but acknowledge concurrent human UI edits can still race. Invalidate stale plans; never derive irreversible authority solely from a project field transition. The guarantee is repair after API/scheduler recovery, not prevention of all human-induced drift.

### What to retain from homegit

Use [PR 170's pinned proposal](https://github.com/cgwalters-bot/homegit/blob/96b0634d3298f0e7ca6fd4cdb8b90dc2d35bf04f/docs/scheduled-dispatcher.md) as prior design, not an adopted implementation. Retain operator/coordinator/worker separation, task-in/safe-outputs-out, pure snapshot rules, one writer and neutral forge types. Current [bot-reconcile](https://github.com/cgwalters-bot/homegit/blob/main/bin/bot-reconcile), [lib/reconcile.js](https://github.com/cgwalters-bot/homegit/blob/main/lib/reconcile.js), [workstream skill](https://github.com/cgwalters-bot/homegit/blob/main/dotfiles/.agents/skills/workstream/SKILL.md) and [coordinator skill](https://github.com/cgwalters-bot/homegit/blob/main/dotfiles/.agents/skills/coordinator/SKILL.md) provide useful semantics, but use local sweep/heartbeat/cache state and directly privileged operations. Port invariants and table tests, not that process topology.

The new repository replaces workstation installation and migration concerns. Native run history plus durable accounting replaces synthetic heartbeat state. This rollout does not require a v1 cutover or deleting homegit tools. Do not import duplicated priority labels, null-as-triage, prose-parsed action instructions, credentialed local workers or an open-ended coordinator session. Fallback representations for other forges must remain visible forge records, never hidden draft items or a private database.

## 5. CLI: gh agent-board

Ship binary gh-agent-board, also invokable as agent-board. A conventional gh extension distribution repository must be gh-prefixed: recommend a release-only cgwalters-forge/gh-agent-board repository while source stays here, or rename this repository. Do not claim `gh extension install cgwalters-forge/agent-board` follows the extension naming convention. Publish platform-specific precompiled releases from trusted CI with checksums and pin installations. No substantial shell installer.

Commands use noun-verb structure; H = human, A = agent, C = CI/controller:

```text
gh agent-board project view               Board schema, health and summary [H,A]
gh agent-board project init               Plan/setup fields on an existing project [H]
gh agent-board item list                  Filter by status, priority and turn [H,A]
gh agent-board item view ITEM             Issue, results, asks, run and evidence [H,A]
gh agent-board item add URL               Enroll an issue as Triage [H,A]
gh agent-board item create                New task with acceptance criteria [H,A]
gh agent-board item edit ITEM             Typed project-field changes [H,A]
gh agent-board item close ITEM            Evidenced completion/cancellation [H,A]
gh agent-board ask create --item ITEM     Question and lettered options [H,A]
gh agent-board ask list                   Unresolved asks/new replies [H,A]
gh agent-board run list                   Admitted executions and accounting [H,A,C]
gh agent-board run view RUN               Trusted outcome and links [H,A,C]
gh agent-board request create --item ITEM Typed downstream request [H,A]
gh agent-board request view ISSUE         Admission, authorization and receipt [H,A,C]
gh agent-board snapshot create            Complete normalized snapshot [H,C]
gh agent-board reconcile plan             Deterministic repairs/admission [H,C]
gh agent-board output check               Validate JSONL against bounds [A,C]
gh agent-board output apply               Revalidate live; pinned handlers [C]
gh agent-board request dispatch           Admit requests to fixed executors [C]
gh agent-board test project               Isolated live fixture lifecycle [C]
```

Reuse -R/--repo, --owner, --project NUMBER, --hostname, -L/--limit, --state, --title, --body-file -, --web, --json fields and --jq expression. --status means board status, distinct from issue --state. ITEM accepts URL or OWNER/REPO#N; bare numbers require -R. --snapshot is offline; --emit writes proposals, never network mutations. Mutation commands default to preview with an explicit not-applied message. Human --apply goes through the same policy checks; the protected CI applier uses its own profile. An agent cannot gain mutation authority by omitting --emit: it has neither credentials nor an allowed mutation network path.

Human live reads can use gh as authenticated API transport through argv/stdin, not shell interpolation or another credential store. Offline reads never invoke it. Implement --json field selection and --jq with a tested Rust jq engine; defer --template with an explicit unsupported error rather than silently offer something different from gh's Go templates. Human output is concise; diagnostics go to stderr; machine schemas are versioned. Follow gh exit codes: 0 success, 1 failure/invalid invocation, 2 cancelled, 4 authentication required. Structured diagnostics distinguish stale_plan, rate_limited and unsupported_capability. A successful plan that finds drift still exits 0.

Five examples below illustrate proposed UX, not executed results:

```console
$ gh agent-board item list --owner EXAMPLE --project 7 --status Triage
ITEM        PRIORITY  TURN         TITLE
tracker#42  P2        Coordinator  Repair flaky integration test

$ gh agent-board item view EXAMPLE/tracker#42 --snapshot board.json --json status,turn --jq .turn
Coordinator

$ gh agent-board item edit EXAMPLE/tracker#42 --snapshot board.json --status Backlog --emit
{"type":"update_project","project":"https://github.com/orgs/EXAMPLE/projects/7","content_type":"issue","content_number":42,"target_repo":"EXAMPLE/tracker","fields":{"Status":"Backlog"}}

$ gh agent-board ask create --item EXAMPLE/tracker#42 --title 'Which compatibility target?' --body-file question.md --snapshot board.json --emit
{"type":"create_issue","title":"Which compatibility target?","body":"Blocks: EXAMPLE/tracker#42\n\nA. Current stable (recommended).\nB. Both supported releases."}

$ gh agent-board reconcile plan --snapshot census.json --json actions --jq '.actions[].reason'
missing_status

```

The trusted create-issue route fixes the repository from policy; omitted targets must not silently select an unrelated checkout. `project init` creates only the dispatch join's missing fields; other project provisioning/deletion reuses existing gh project commands rather than duplicating the whole CLI. References: [gh command reference](https://cli.github.com/manual/gh_help_reference), [extensions](https://cli.github.com/manual/gh_extension), [exit codes](https://cli.github.com/manual/gh_help_exit-codes).

## 6. Day-one live CI and credential-free tests

Every privileged test run creates a disposable organization Project v2 named agent-board-ci-<run-id>-<attempt>-<random128>, exercises it, and deletes it. The workflow's own GITHUB_TOKEN is insufficient for Projects v2. Recommended credential: a dedicated GitHub App installed only on sandbox repositories, with Organization Projects read/write, repository Issues read/write and Metadata read; add Contents read only where project linkage requires it. Store its private key in a protected board-ci environment, identifiers in environment variables, and mint short-lived installation tokens only in trusted fixture/apply/cleanup jobs. Organization project permission is broader than one board: use a dedicated test organization and enforce the returned project ID in software. Production uses a separate App/environment.

A bootstrap alternative is a fine-grained PAT with organization Projects read/write and sandbox Issues read/write, subject to owner/token support. User-owned projects need a compatible user credential, typically a classic PAT with project scope and public_repo for public issue writes (repo for private access). Do not assume an organization App installation covers a user's project. Confirm the chosen endpoint/token combination in the first fixture; [GitHub Projects API guidance](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects) distinguishes project scopes and permissions. The operator configures secrets in CI; no credential value belongs in agent context.

Day-one CI has two lanes. Unprivileged PR CI runs formatting, clippy, unit/fixture/property tests, CLI golden tests and malicious-output cases. A trusted-ref protected dispatch runs a random-project fixture and a scripted agent through agentic-job policy/agent/check/apply. Initially exercise the already-supported comment/preview path and trusted project lifecycle, without claiming board mutation support. After the prerequisite bounds land, the same fixture must apply actual project/issue outputs and verify convergence. Add a real-model smoke only after broker admission exists; it is not the deterministic correctness oracle.

Never run arbitrary fork/PR code with the project token. Candidate code may produce proposals in an unprivileged job; a trusted applier validates them independently. Testing candidate applier code live requires approval of that exact commit, protected environment and isolated owner. Never use pull_request_target to checkout and execute an unreviewed head. Verify source commit, workflow identity and run/attempt for artifacts; do not share writable caches across the agent/validator boundary.

The Rust fixture runner provisions existing fields/options and a few issues in a pre-created sandbox repository. It records returned identities, nonce, run URL and expiry in a cleanup artifact and project description. Test reads, enrollment, fields, asks, accepted closure, terminal reconciliation and no-op replay. Seed all five drift cases, interrupt between enrollment and status, and verify the second complete pass converges. Simulate delayed visibility, rate limits, stale plans, ambiguous dispatch and concurrent edits offline rather than disrupting GitHub.

Negative cases must refuse wrong project URL/node ID, a PR number where an issue is required, unlisted repository, unknown field/option, excess outputs, nested target escape, labels/assignees, broad dispatch refs and copied approval markers before mutation. Keep a forbidden canary project and verify it remains unchanged. Assert exact repository/project isolation, no PR mutations, slot/budget limits, sanitized text and complete pagination. Fixture provisioning/deletion authority is never board-agent authority.

Cleanup runs under always(), deletes only recorded project IDs after owner/name/nonce checks, and closes only marked fixture issues: deleting a project does not delete its issues. A trusted scheduled sweeper enumerates projects in the test owner, verifies prefix PLUS provenance/age, excludes active runs and deletes leftovers older than 24 hours. A prefix alone is not proof of ownership. Cleanup failure fails/reports the run; cancellation can skip cleanup, so the sweeper is mandatory. Retain enough identity in the project itself to recover even if the artifact upload failed.

Offline fixtures cover pagination, redacted/null nodes, permissions, rate limits, schema rename, every status/turn transition, native relationships, request validation and accounting. Data-driven and property tests check deterministic ordering, idempotent convergence and absence of unauthorized actions. Required future commands are `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, and a separately opt-in live fixture command. No model or credential is required for the first three. None was run for this analysis.

## 7. Rust boundaries and the first six PRs

### Current implementation limits

The workspace currently implements offline snapshots, missing-status and
issue/status terminal-drift rules, preview-only GitHub proposal lowering, and
paginated GitHub schema/membership/issue/PR reads, live read commands, and a staging
fixture that seeds an issue and text field, reads a snapshot and plans drift before
cleanup. `live/board-test.yml` supplies the protected staging workflow template.
It does not complete step 1's scheduled
sweeper or agentic-job caller requirements. No live execution or pinned
external handler/bounds contract has been verified here.

Label, user, linked-PR and reviewer field values are not GraphQL nodes. The reader
fetches their nested connections inline (at most 100 entries each); additional
pages or redacted/missing connection data mark the item and snapshot incomplete,
blocking reconciliation rather than treating a partial list as complete.

`agent-board poll` is the tracker's pull request poll (#40), one pass a run:
it prints the operator's and the bot's activity from the events of every
repository on the board (given by `--owner`/`--project` or `--snapshot`) and of
`--watch`/`--follow`, a step for each of the bot's open pull requests in the
`--follow` repositories (keyed on the latest submitted review of the head by the
operator, not a status and a VERDICT comment), and when the next pass is due
(five minutes while anything changed or a pull request is in flight, doubling
while idle, at most six hours apart). GETs are conditional against a disposable
state file; the pull request query is GraphQL and is not. `--dry-run` takes no
step. `--apply` takes poll.cjs's steps with the bot's `GH_TOKEN` (checked to be
`--bot`'s, as only the bot's markers and claims are read back): mark ready,
merge an operator-approved green head at once (pinned to the head that was
read; never auto-merge or the merge queue, which stay pending where a later
push could ride on the approval), label `needs-human` with the marker comment, and start a fix run
through the caller's `--dispatch-workflow` with `DISPATCH_TOKEN`, at most three
a pass as the dispatcher above is bounded. A pass claims each fix round with a
comment naming the marker comment it decided from, and only the earliest claim on
that comment, while that marker is still the newest, starts a run. Markers are only added: each round and each
`needs-human` stop is a new comment, and the one later write is a round's run
id, into its own comment. Readers use the newest marker by creation id, so a
late result cannot roll back a newer round or stop, and each removal of the
label is claimed from a stop of its own. A stop is added after its label, and
`--apply` reads the comments before the label and without the response cache,
so a stop another pass is still writing is not taken for a reset. Steps are taken in `--follow`
repositories only; the board widens what is read, not what is changed. The
workflow, its bounds and the tokens stay in the tracker, whose poll.yml still
runs poll.cjs. Promoting operator-approved fork pull requests upstream is not
implemented. Authenticated review-job verdicts are deferred: the shared
Actions bot identity does not establish which workflow submitted a review.
Job-only approvals and change requests therefore wait for an operator verdict,
unlike poll.cjs; recorded job-only cases test this limitation separately from
synthetic operator-verdict decisions. Activity is printed, not yet handed to a controller pass, and
the events API serves one page of 100 a pass, so a busier gap is reported as
such. A pull request with more labels, reviews, commits or checks than its one
query reads waits rather than being decided on part of them. Required checks come from the base branch's rulesets and its classic
protection; a required check that never reported is pending, and a protected
branch whose requirements cannot be read is an error. It has been exercised against recorded responses only.

Terminal-drift plans leave Done/open issues for review, never proposing closure
from Status alone, so a person's reopen is not undone. Closed issues get Done
only for `COMPLETED`, Cancelled for `NOT_PLANNED`; an unknown reason blocks repair.
Every target status must exist unambiguously in the snapshot schema. The plans
do not authorize writes:
the independent checker/applier must verify that the target is an issue and
that authenticated completion evidence exists, as required in section 4. Both
the observed status and issue state, plus the closure reason, are captured as
preconditions. Incomplete
snapshot coverage blocks all repairs; incomplete item fields block that item's
repairs. Closed issues are classified before the missing-status rule, avoiding
an intermediate Triage proposal. No live reads or live terminal repair have
been verified against GitHub. Recorded responses exercise the lifecycle and its
failure cleanup without credentials.

`test project --sweep` fails before authentication or network access. Editable
project descriptions and completed Actions runs cannot prove who created a
project. Re-enabling sweeping requires an independently authenticated creation
receipt binding the returned project ID, nonce, run ID/attempt and approved
workflow identity; missing proof must leave a project untouched. Immediate cleanup
retains its trust anchor in memory: the ID returned by creation and the locally
generated nonce. Crashes require manual recovery until the trusted receipt store
and protected sweeper are implemented.

The current `board-snapshot/v1` reader rejects unknown fields at every nested
record boundary. Status, Priority and Turn must be present, with explicit JSON
null for an observed unset value; omission is a schema error, not null. Evidence
may be omitted and defaults to an empty list. Unknown schema versions are rejected
by validation. This is a deliberately strict input policy, not forward-compatible
field discovery. GitHub issue/project URL grammar belongs to board-forge; core
validates only generic identities and canonical HTTPS project URLs. The GitHub
adapter supplies the default hostname.

Use three crates: board-core for domain types, versioned snapshots/plans, pure rules and budget arithmetic; board-forge for GitHub reads, capability discovery and safe-output lowering; agent-board for CLI, orchestration and the Rust integration-fixture driver. Keep skills, schemas, fixtures and rule tables in normal repository directories. No shell program longer than ten lines. Nontrivial fixture logic belongs in Rust; a small standard-library Node wrapper may call pinned gh-aw handlers without duplicating their sanitization.

Core types include ItemRef, ChangeRef, RunRef, Actor, BoardField, Evidence, Snapshot, Intent, Precondition and Capability, not GraphQL IDs or handler JSON fields. A read Forge trait exposes board schema/membership, repository issue inventory, issue/thread/relationship facts, PR state/reviews and runs, each with completeness/freshness. A separate OutputBackend lowers typed intentions to the bounded write protocol or returns unsupported capability; it does not grant a model a mutation client. Native identity includes host.

GitHub uses GraphQL for Projects and REST where appropriate for issues/comments/relationships and Actions. Discover field/option IDs; adding membership and setting fields are separate steps. The [sub-issues API](https://docs.github.com/en/rest/issues/sub-issues) is a native relationship surface, but API availability is not safe-output permission. Cross-repository parentage requires platform and policy checks.

Dependencies: serde/serde_json, clap, toml, thiserror/anyhow, url, time, ureq with TLS, a SHA-256 implementation, and a jq-compatible Rust engine for --jq. Use assert_cmd, HTTP fixtures and proptest for testing. Begin with synchronous networking and no SQL service or speculative async framework.

Portability is capability negotiation, not spelling substitutions. [GitLab boards](https://docs.gitlab.com/api/boards/) are generally lists over issues/labels, with assignments, notes, links and pipelines; some epic/board features vary by tier. A GitLab project is a repository, not GitHub Projects v2. [Forgejo's API](https://forgejo.org/docs/latest/user/api/usage/) is versioned REST/OpenAPI; board, hierarchy and Actions coverage must be checked against the target server version. Do not assume custom fields, token scopes or approval semantics match. A future adapter can use visible labels/comments for missing fields, but must report unsupported guarantees instead of weakening them. Prove second-forge read normalization first; replacement write appliers come later.

## 8. Operator decisions

### Dispatch preview integration seam

`request dispatch` and `run record` implement an operator-driven preview join to
agentic-job's `examples/dispatch/dispatch.yml`. Both support offline snapshots;
neither mutates the forge. Routing comes from explicit operator flags, not item
prose. Eligibility rejects incomplete or non-issue inputs to avoid launching work
from unknown state. URL grammar excludes unrelated result targets, but is not
evidence of authorship or success. The operator must verify run/item correlation
and applied results; independent apply must re-read state and validate proposals.
An editable snapshot is never write authority.

The dispatch target preflight now embeds the fetched issue title/body as task
data, and upstream supports update_project proposals. Remaining integration: the caller
should expose applied PR/comment URLs and refusal reasons as trusted reusable
workflow outputs, with run identity/attempt. This allows a post-run controller to
correlate results without parsing model prose or choosing the latest run by title.
Independently bounded `update_project` application must be configured
for the exact project, issue, fields and values. Only that separate apply job may
receive organization Projects write permission; GITHUB_TOKEN does not grant it.

No scheduled admission, automatic Run/Result recording, run listing, refusal-to-Blocked
conversion or stuck-run recovery is implemented yet. Do not retry an ambiguous
dispatch automatically. `project init` creates missing Turn/Run/Result
fields with the operator's own token and never edits existing fields or options. No workflow permissions, token
placement or action pins are changed in this patch.

`dispatch ISSUE --dry-run` prints the workflow_dispatch request for the newest
accepted [job plan](job-plans.md) on an issue; `--apply` sends it once per plan,
recorded by a comment on the issue that is posted and read back first.

`ask create` opens a question issue, labelled `question` and assigned to the
operator, with lettered options and a recommendation, and sets it and the item it
blocks to Needs human; `ask list` shows open asks on the board; `ask resolve` comments
the answer, closes the ask and sets it Done. They replace homegit's `bot-board
question` and `resolve`, and like `item edit` print proposals unless the operator
passes `--apply` with their own token. The label and the Status option must already
exist; neither is created, and the operator must be assignable in the ask's repository.
Resolving leaves the blocked item's Status to whoever acts on the answer. Asks on pull requests (homegit's review asks), sub-issue
links and copying the blocked item's Priority are not implemented.

For read-only setup, `project init --snapshot FILE` retains its field table on
stdout and prints copyable `gh project field-create` commands for missing fields
on stderr. It does not execute them; review the saved schema against the live
project first. Existing fields and optional Status options are not provisioned.

## Operator decisions (cgwalters, 2026-10-07)

- **A, distribution:** decide later. Build the binary as `agent-board`, usable as a gh extension locally; pick how it is distributed when there is something to install.
- **B, authority:** the strict four mutation types: project field edits, creating issues, closing issues, and typed requests to other jobs. Whose turn it is lives in a project field. No comments, assignees or sub-issue links from the agent yet.
- **C, test credential:** a fine-grained token for the bot account that reaches only the staging organization, https://github.com/cgwalters-forge-stage, stored by cgwalters as an Actions environment secret. - **D, autonomy:** one worker slot, finite per-run and per-period ceilings, missing usage data blocks new work, and his approval before each run starts and before any destructive downstream request.
