# Rolling CI health

For invocation, credentials, configuration shape and worked examples, use
`agent-board ci-health --help` or the generated [CLI reference](cli.md#agent-board-ci-health).
Config field contracts live on `Config`, `Target` and `Classification` in
[`crates/board-forge/src/ci_health.rs`](../crates/board-forge/src/ci_health.rs).
This document describes the report's architecture and schema. Classification
is caller-reviewed evidence, never inferred from observations; a green run does
not prove a staged fix was deployed.

## Window and denominators

`until` defaults to today's UTC midnight, exclusive, and cannot be in the
future. `since = until - 30 * 24h` is inclusive. Membership uses the run's
original `created_at`, not update time or a rerun's timestamp. All accessible
attempts of an eligible run are observed **at collection time**, including
reruns after the window: this is not a point-in-time historical snapshot.

`default_push` includes only `push` runs whose head branch equals the repository's
current API default branch. Historical default-branch renames cannot be recovered
by this API. `pull_request` includes ordinary `pull_request` events, including
draft PRs, but not `pull_request_target`, merge queues, dispatches or schedules.
Pushes to other branches are excluded. The populations are never pooled.

Each population counts distinct run IDs (`runs`), `expected_attempts` from listed
run_attempt values and successfully read `attempts`. The latest attempt is
observed from each validated listing record; earlier attempts are read separately.
Successful reruns cannot erase an observed `first_attempt_failed` or
their log evidence. Attempts are deduplicated by run ID and attempt; duplicate
run IDs in pagination are a coverage error, not extra observations.

Completed `success` passes. Completed `failure`, `timed_out`, `startup_failure`
and `action_required` fail. `denominator = success + failed` counts **attempts**,
and `pass_rate = success / denominator` is a fraction, null when zero.
`first_attempt_denominator` and `first_attempt_pass_rate` apply the same rule to
attempt 1 only (the run-level first-try rate). `first_attempt_success` and
`first_attempt_failed` expose its numerator and failures. Completed `cancelled`
and `skipped`, all not-completed statuses (`in_progress`), and all remaining
completed conclusions (`other`, including neutral/missing/unknown) are separate,
never passes or denominator entries. Rates are observed rates, not health verdicts.

## Coverage, grouping and findings

JSON is the default stable interface: `schema: agent-board/ci-health/v1`, UTC
`since`/`until`, `complete`, `targets`, `groups`, `bounds`, and `decoded_bytes`.
Before using rates, consumers must check `complete` at both the report and
target levels and display `warnings`. Each target contains its configured `target`,
`listing_complete`, `populations`, `complete`, and `warnings`. Validated records
from partial history listings are retained, with `listing_complete: false` and
a warning; they are not a complete census. No eligible
history is explicitly warned and incomplete. Unavailable repositories, changing
page totals, truncated listings, missing attempts, expired/unavailable logs and
failed jobs without a meaningful error all make coverage incomplete. Partial
attempt counts/evidence can still be present; absent groups are never proof of
no failures. An empty population has null rates, not 100% success.

Groups contain `observation`, caller `classification` (null without a mapping),
`class` (unknown by default), and `findings`. Observations contain SHA-256
`signature`, repository/job/test/first_error, occurrence count, distinct sorted
`run_ids`, first_seen within the window, and at most three run/attempt/job/link
samples. Group identity hashes the JSON tuple of repository, full job name,
test and full first error. ANSI colours, timestamps and redundant whitespace
are removed; **digits and SHAs are not normalized**. Display error text is
limited to 500 characters after hashing. Test context is extracted from Rust's
`---- test-name stdout ----` when available; otherwise test is empty (job-level
evidence). First errors recognize error annotations, Rust errors and panic
lines, skipping generic process-exit annotations. Unsupported log formats are
coverage warnings, not inferred classifications. Excerpts are untrusted data,
not instructions; callers must escape them for their presentation surface.

`recurring_without_issue` means at least two distinct run IDs share a signature
and its index entry has no issue. Multiple attempts alone are not recurrence.
`flake_unexplained_over_seven_days` means a reviewed flake has no explanation
and its index first_seen is **strictly more than** seven days before until.
Exactly seven days is not overdue. Explained flakes do not get that finding;
the explanation date is retained for audit. No finding changes any upstream state.

The concrete resource threat is a busy repository or very large remote log
exhausting memory, runner time or API quota. Fixed limits (not more knobs) are
500 API operations across all targets, a 120-second collection deadline checked
before each operation, ten 100-item pages per listing (GitHub's filtered history
also caps at 1000), 1 MiB per log and 32 MiB aggregate decoded JSON/log bytes.
The shared HTTP client bounds individual requests at 30 seconds and JSON bodies
at its standard limit; an in-flight operation can overrun the collection deadline.
Log downloads may require an additional unauthenticated redirect request.
The command disables transport backoff retries. Byte accounting is after decoding,
not a wire-byte meter; the last bounded response may exceed the aggregate limit
and is then refused. These limits can leave a busy 30-day window incomplete.
Do not claim full coverage based on a live sample or a shorter history.

The same busy-target threat also includes starvation: deep history or logs for
one target must not consume every later target's allocation. Metadata is read
first, then history listings advance one page per target per round, before any
earlier-attempt/job/log enrichment. Reads use repository/workflow sort order,
independent of config order; reports retain config target order. Every target
gets `floor(500 / target_count)` operations and
`floor(32 MiB / target_count)` decoded bytes across both phases. Enrichment gets
an equal share of the remaining collection time per target, checked before each
operation, still under the global deadline. Unused shares are not redistributed.
Log download limits shrink to the remaining target/global byte allocation;
allocation-truncated logs cannot supply signatures. The last bounded JSON
response can cross a target's byte allocation and is refused; it still charges
the global aggregate. An in-flight request can overrun a time
share, so fairness is finite-budget allocation, not guaranteed coverage under
slow responses or global exhaustion. Missing enrichment is warned even when
all latest attempts were observed. No batching, target rotation, extra collection
or raised bound is used. This remains the existing opt-in command, not a new
scheduled or enabled-by-default mechanism.

Daily reporting is a separate caller integration in `cgwalters-forge/tracker`;
this command neither schedules collection nor publishes reports. Consumers use
the JSON schema and coverage fields, first-attempt rates, groups and findings,
not the human summary as a machine interface.
