# Dispatch

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

agent-board decides what job to start; something else runs it. The runner of
agent jobs is meant to be pluggable: [agentic-job](https://github.com/cgwalters-forge/agentic-job)
on a CI runner is one backend, and any tooling that can run an agent job for an
issue should be able to take its place. In code, every caller below starts a
job through one interface (`board_forge::dispatch`): a start request (target
repository, item, kind, brief, pool, runner, optional base) and a trusted route
from configuration, answered with a run handle, a start without one, a refusal
that started nothing, or an unknown outcome. Existing callers use GitHub
Actions `workflow_dispatch`. Native Forgejo library adapters are also available
but not wired to any CLI or scheduler (see below); closed
[agent-board#295](https://github.com/cgwalters-forge/agent-board/issues/295)
delivered only the start request.
This page describes the interface as it exists.

## Who dispatches

- `dispatch ISSUE --apply` starts the job the issue's newest accepted
  [job plan](job-plans.md#dispatch) describes. The caller repository, workflow
  and ref come from `--caller`, `--workflow` and `--ref` (default `main`).
- `poll --apply` starts fix, rebase, continuation and diagnostic rounds on the
  bot's pull requests, and triage or research runs for operator comments and
  notifications ([pull request follow-up](poll.md)). It uses `dispatchRepo` and
  `dispatchWorkflow` from the caller's `agent-board.json`, at `main`.
- `supervise execute` starts the triage, research and implement runs the
  [supervisor](supervisor-requests.md) requests, with the same two settings.
- [Pass](pass.md) uses the same settings plus `dispatchRef`.

Every route, identity and pool allowlist comes from the caller's trusted
configuration, never from a plan, an issue or a dispatcher's inputs.

## Opt-in operator routing (first slice)

`dispatch ISSUE --dispatch-routing FILE` adds **one** trusted namespace route
to operator plan dispatch, in both `--dry-run` and `--apply`. Without the flag,
behavior is unchanged. This is not a production cutover or complete bootc-dev
routing. The file must be deployment-owned, not supplied by an agent or taken
from the target checkout. The [test fixture](../fixtures/dispatch-routing.json)
shows the current sandbox contract; it is not loaded automatically.

The concrete threats and the corresponding bounds are:

* A plan targeting a different repository than its tracking issue could choose
  the wrong caller. Selection uses the plan's actual `repo`, not `ISSUE`.
* A namespace match could accidentally grant every repository in an organization.
  The route also requires an exact, case-insensitive `repositories` allowlist
  (1–10 entries), kept within the selected `namespace`. Deployment must keep it
  no broader than the caller's independently enforced bounds.
* Agent text could choose an expensive runner or unsupported caller inputs.
  Only trusted JSON supplies `target` (`caller`, `workflow`, `gitRef`),
  `runnerConfig` and `cores`. Cores defaults to **4** and only 4 is accepted in
  this slice, even though the sandbox also offers 16 and 64. Supported kinds are
  research/triage/implement; fix/review, stacked/base and batched work are refused
  rather than sent to tracker. Routed pools are openai/claude/mistral; an omitted
  plan pool becomes openai. Nonmatching namespaces keep their existing route
  and pool behavior. Job-plan fields and admission are not expanded.
* A new caller could hide old active work and start overlapping jobs. Before a
  routed dispatch, and again before each POST, read both the legacy and selected
  workflow's active runs. Any active run targeting the same repository holds the
  dispatch, conservatively including other items and kinds. The sandbox title
  suffix `(openai, 4c)` is accepted. Each check lists one page of up to 100
  runs for each active status (requested, pending, waiting, queued,
  in_progress), in that order and then again: ten listings per workflow,
  whatever the length of its history. Neither paging the whole history nor
  GitHub's filtered `total_count`, which stops at 2500, bounds a busy caller
  such as the tracker. A run that only moves forward between the reads is
  listed by the first pass, and one that moves back once (a gate taking it
  from queued or in_progress to waiting) by the second; one that moves back twice
  during the reads, or that GitHub's run index has not listed yet, can be
  missed. Completed runs do not hold work, judged by each run's current
  status. An unavailable or malformed listing, an unknown status, or more
  than 100 runs in one active status fails closed. Active runs are identified
  by their title's second word, `OWNER/NAME#N`, as both callers' `run-name`
  writes it today; changing that format needs this check changed with it.
  This is a bounded admission check, **not an atomic cross-workflow
  lock**: the operator must serialize invocations across both callers. The
  caller must keep `cancel-in-progress: false`.

The existing plan claim/read-back protocol still records an ambiguous or failed
POST and never automatically retries it. The selected caller's repository is
used in the returned run URL and dispatch receipt. Subsequent invocations poll
both workflows for active work; no cancellation, migration or redispatch is
performed. A receipt remains a receipt when routing configuration changes.
For manual board joins use `run record --run URL` with the selected receipt;
automatic `run record --caller` discovery still assumes `dispatch.yml` and is
not supported for the sandbox's `agent.yml`.

## The request

Each of them sends `POST /repos/{caller}/actions/workflows/{workflow}/dispatches`
with a `ref` and these string inputs, which the caller workflow must accept:

| Input | Meaning |
|---|---|
| `task` | The brief: a plan's `brief`, or the task agent-board writes for a fix or triage round |
| `repo` | Target repository, `OWNER/NAME`; the caller's bounds must allow it |
| `item` | Issue or pull request number in `repo` |
| `kind` | `implement`, `triage`, `research` or `fix`: the profile the run gets |
| `pool` | Inference pool, or empty to leave it to the caller |
| `base` | Only for a [stacked](job-plans.md#stacking) plan: the branch to start from |

A plan's `runner` is checked (only `hosted` is accepted) but not sent: the
caller workflow has one runner. Batched plans add their briefs to `task`.

## What comes back

- **Run handle.** The request asks for `return_run_details`; where GitHub
  answers with a `workflow_run_id`, agent-board records the run's Actions URL
  on the issue (the dispatch record) or in the pull request's round marker.
  Where the API refuses that field (HTTP 422) it asks again without it, and
  there is no handle.
- **Status.** There is no status call on a handle. Runs in flight are found by
  listing the caller workflow's queued and in-progress runs and matching their
  title, `KIND OWNER/REPO#N`, optionally followed by ` (POOL)`. The caller
  workflow must set its `run-name` that way. The overlap hold, the supervisor's
  in-flight check, `status` and `run record --caller` all read runs like this;
  the poll reads a round's run by the id in its marker.
- **Ambiguity.** A request whose outcome is unknown is recorded and never
  retried automatically; a writer edits or replaces the plan to try again.

agentic-job's [dispatch caller](https://github.com/cgwalters-forge/agentic-job/blob/main/docs/dispatch.md)
is a workflow of this shape.

### Native Forgejo adapters (not activated)

`board_forge::dispatch::Forgejo` sits alongside `GitHub`. No existing caller
selects it and no pass option enables it. Construction takes the trusted
instance `forgejo::Config`, `dispatch::Target`, accepted input names and bot
recorder id; `/user` must confirm that id. No response supplies routing or
credentials. Unsupported kinds (including PR follow-up), runners and inputs
refuse before dispatch. The client refuses redirects and requests outside the
configured API root, including port and subpath, and never uses GitHub tokens.

The concrete threat is duplicate or wrongly attributed work after an uncertain
start. One POST sends `return_run_info`, never `return_run_details`; 204,
missing ids, lost replies and server errors hold without retry. A 201's id is
read and checked against the [identity protocol](forges.md#dispatch-and-runs),
including the explicit workflow-dispatch trigger, the configured ref (the
run's `prettyref`), nonempty sent inputs and exact title/pool. A start is
refused before admission while the workflow's history already fills the
500-run listing cap, since its confirmation could not list it. A named mismatch
gets best-effort cancellation and stays held; a status or transport read error
stays ambiguous without cancellation. Creation time is compared at whole-second
precision, matching Forgejo's timestamp. Confirmation requires exactly one
verified match in two complete inventories with the same ids, then a fresh run
read. Read-only recovery uses
the same protocol; zero or duplicate verified matches never authorize POST.
Run URLs use `index_in_repo`, not the global API id.
Concurrent starts can change those inventories and turn even verified starts
ambiguous, so the caller must serialize starts.

Active inventory uses `/actions/runs`, never `/actions/tasks`: `waiting` is
queued, `blocked` includes approval and `running` is active. Each active status
is paged twice in lifecycle order. Terminal states are success, failure,
cancelled and skipped; unknown statuses hold. Pages use `limit=50`, body
`total_count`, and at most ten pages per listing. Moving totals, duplicate ids,
empty incomplete pages and oversized inventories hold. One backend shares
500 requests and 15 minutes, including mutations and lease I/O. Two sweeps
are bounded observation, not a lock or protection against arbitrary backward
transitions or indexing delays. Rerun accepts only a verified failed run with
a complete nonempty array of at most 500 terminal jobs, all at attempt 1.
Forgejo reuses its id; jobs, not runs, supply attempts.

The other concrete threat is two schedulers spending one capacity slot, or a
late release freeing a replacement owner. Admission uses one contents-file
protocol ([atomicity evidence](forges.md#admission-and-release)), not
read-PATCH-read. Slots must already exist on a dedicated branch in the private
caller repository: `leases/SLOT.json`, initially `{"free":"initial"}`.
The ceiling is 100 slots, as for GitHub WIP. Admit takes a free observed slot;
bind attaches a returned run id to its `run: 0` reservation; release requires
the observed claim/run and a terminal run or expiry. Unreadable runs hold
until expiry. Leases last exactly 24 hours and serialize to at most 1 KiB, so
every write stays readable. Admit reads the caller's privacy before its final
callback, leaving only the write after it. Writes carry the observed blob
SHA; stale ownership loses with 409. Lost write replies and other failures
hold, even if read-back shows the proposed value. Free markers retain the old
owner, and claims must be globally unique and never reused, preventing ABA.
Slots sharing a branch can fail each other's non-forced push even when updating
different files. Such failures hold the reservation: this affects liveness,
not ownership safety, and is another reason for the caller to serialize starts.

These are primitives, not a scheduler or durable journal. Final admission
callbacks must preserve WIP, pool pacing, dispatch/write caps, one lease per
run, unexpired ownership and durable plan/rerun claims immediately before POST.
A lost rerun reply holds even if jobs still show attempt 1. Ambiguous
reservations must not be released or reused. Missing slots, unsupported
transports and deployments without the pinned contents-write guarantees
refuse, with no GitHub fallback. The [caller and live CI prerequisites](forges.md#the-caller)
remain. Offline source-shaped fixtures validate the pinned API contract, not
a deployed server, runner or production activation.

## Recording a run on the board

`request dispatch` and `run record` are an operator-driven join for a board
with Run and Result fields (`project init` creates them). Both read offline
snapshots. `request dispatch` prints the `gh workflow run` argv for an item and
never writes. `run record` proposes the Run/Result update, and `--apply` writes
the validated update with the operator's `GH_TOKEN`. Routing comes from explicit
operator flags, not item prose. Eligibility rejects incomplete or non-issue
inputs to avoid launching work from unknown state. URL grammar excludes
unrelated result targets, but is not evidence of authorship or success: the
operator verifies run/item correlation and the applied result, and an editable
snapshot is never write authority.

When no Run is recorded, `run record --caller` searches one page of at most 100
of the caller's `dispatch.yml` runs for the single one titled `KIND OWNER/REPO#N`
and needs `--yes` (or an explicit `--run`) to use it. No scheduled admission,
automatic Run/Result recording, refusal-to-Blocked conversion or stuck-run
recovery is implemented. Agent output reaches the board only through
independent check and apply; the pass's own writes are direct
([architecture](architecture.md#writes)).

A post-run controller would need the caller to expose applied pull request and
comment URLs and refusal reasons as trusted workflow outputs, with run identity
and attempt, so it can correlate results without parsing model prose or picking
the latest run by title.
