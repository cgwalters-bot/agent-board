## Supported interfaces

These are what v1 would ask callers to rely on; which of them are frozen, and
how, is the `config-contract` gate's decision, not this page's.

- **Binaries:** `agent-board` and `gh-agent-board` (the same CLI, run as
  `gh agent-board`), with the commands and flags of the
  [CLI reference](cli.md), which a test keeps equal to the binary's help.
  Writes preview unless `--apply`, within `--max-dispatch` and
  `--max-writes`. Exit codes: 0 success, 1 failure or invalid invocation,
  3 an epic plan's precondition failed ([epic plans](epic-plans.md)), 4
  authentication required, as gh's where they overlap.
- **Configuration:** the pass's one file ([pass](pass.md#one-configuration-file)),
  the poll's ([poll](poll.md)), the supervisor's
  ([supervisor](supervisor-requests.md#configuration)), the release train's
  ([release train](release-train.md#configuration)) and the board's
  `agent-board.json` (`--board-config`). Unknown keys are refused.
- **Records on the forge**, each versioned by its `schema`:
  `agent-board/job-plan/v1` ([job plans](job-plans.md)),
  `agent-board/epic-plan/v1` and `agent-board/epic-apply/v1`
  ([epic plans](epic-plans.md)), `agent-board/operator-action/v1`
  ([operator](operator.md)), `agent-board/holds/v1`,
  `agent-board/maintain-plan/v2`, `agent-board/maintain-digest/v1`,
  `agent-board/sweep/v1` and `agent-board/sweep-verdicts/v1` ([pass](pass.md)), `agent-board/supervisor-ledger/v1`
  ([supervisor](supervisor-requests.md)), `agent-board/cost-day/v1`
  ([cost](cost.md)), and the snapshot and plan files `board-snapshot/v1` and
  `board-plan/v1`.
- **Forges:** GitHub fully, Forgejo read-only, GitLab not at all
  ([forges](forges.md)).

Not supported, and not part of v1 unless a later decision adds them:
`output check` and `output apply` (agentic-job's independent check is the
path for agent output), sweeping of the test projects and scratch issues
the CLI creates, Forgejo writes and dispatch, and GitLab.

## Install and build today

Users install from the repository with `cargo install --locked --git`
([setup](setup.md#install)). A deployment pins a reviewed 40-character commit
and builds it with `cargo install --locked --rev`
([pinned callers](setup.md#pinned-callers)); tracker's workflows do so
through `just build-agent-board` with `AGENT_BOARD_REV`, and its
`agent-board-pin` workflow proposes moving that pin. CI's `rust` job runs
`just check` and the CLI against the fixture on every pull request and on
main. There are no release binaries, so there are no checksums to verify.

The release path to reuse rather than build: the [release train](release-train.md)
already bumps a Rust workspace's version and dispatches the release
repository's `release.yml` with `version`, and agentic-job's `release.yml`
tags main's commit and publishes static binaries with SHA-256 checksums and
an attested manifest. Adding such a workflow here, and pointing the train at
agent-board, changes release policy and needs the operator's decision first.

## Beyond the release

epic's measure, not a gate of this release. agentic-job's own release work is
[tracker#596](https://github.com/cgwalters-forge/tracker/issues/596).
