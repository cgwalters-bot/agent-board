## Commit prereleases

[Issue #614](https://github.com/cgwalters-forge/agent-board/issues/614)'s producer
merged in [#615](https://github.com/cgwalters-forge/agent-board/pull/615),
[`6b2d361`](https://github.com/cgwalters-forge/agent-board/commit/6b2d36182b4e53cf5b9c74771e87b86c5ad65939).
For example, the observed source snapshot has a
[published commit prerelease](https://github.com/cgwalters-forge/agent-board/releases/tag/build-c343eae54bf4ddb8bc60e870c5509040b043f45a)
with the five assets below. This is artifact delivery, not v1 or live stage evidence.

[CI](../.github/workflows/ci.yml) publishes `build-<full 40-character commit>`
after its `ci` sentinel succeeds on a push to main: specs, Rust, workflow lint,
static build and Forgejo must all pass. PR and merge-group runs never publish.
Each main commit has its own concurrency group so a newer push does not cancel
an older green commit's publication. No extra build or version bump is needed;
`release.yml` remains the manual path for versioned releases.

CI passes the commit tag to [build.yml](../.github/workflows/build.yml), then a
separate job attests its `release.json` manifest and verifies the bundle without
a token. Only the publishing job has `contents: write`; neither it nor the OIDC
job checks out or executes project code. It creates the tag explicitly at the
tested SHA and publishes the two static binaries, `SHA256SUMS`, `release.json`
and `provenance.jsonl` as a prerelease with `--latest=false`. This avoids giving
PR code publishing credentials or mistaking a moving main ref for the tested
commit. The [caller verification recipe](setup.md#download-and-verify-a-commit-prerelease)
binds the manifest to CI on main and an independently pinned commit before
checking the binary digests; checksums alone do not establish authenticity.

Existing tags/releases are never overwritten: rerunning publication fails if
the tag already exists. If a failure leaves a tag or draft, a maintainer must
inspect it and remove the incomplete release/tag before rerunning. Restrict
`build-*` tag creation with a ruleset to limit who can impersonate this naming
scheme; caller attestation verification remains necessary.

There is **no automatic pruning** of these prereleases or their tags. They stay
available for pinned callers even after Actions artifacts expire. Manual removal
can break those callers; check deployed pins before removing any. Commits before
this workflow was installed, failed/cancelled CI runs and failed publication do
not gain a release. No backfill or cleanup job is added here.

## Manual release path

[release.yml](../.github/workflows/release.yml) and the shared static
[build.yml](../.github/workflows/build.yml) adapt cgwalters-forge/agentic-job's
workflows, without its secure-host image steps. #568 merged this manual path;
the successful v0.1.0 dispatch is linked in the gate table. No new dispatch,
schedule, version bump or release-train enrollment is proposed here.

After a reviewed workspace version change reaches main, dispatch `release.yml`
on `main` with `version=MAJOR.MINOR.PATCH`. `just release-check VERSION` reads
the checkout's `v*` tags, refuses malformed versions/tags, workspace mismatch,
and versions not newer than every existing version tag, and prints the previous
tag for release notes (empty for the first release). This checker is adapted
from agentic-job's Rust checker, including its 1 MiB tag-input bound; its fixture
tests run in `just check`. `cargo test --locked -p agent-board --bin release-check`
and `cargo test --locked -p agent-board --test release` run the two release checklists.

One release runs at a time. Read-only jobs validate and build the dispatched
commit with `just build-static` for `x86_64-unknown-linux-musl`, using no build
cache. A separate job attests `release.json` and verifies its bundle against the
workflow on main and the dispatched commit without a token. Only the publish
job has `contents: write`; it executes no project code. It rechecks the tag
inventory, creates `vVERSION` explicitly at the dispatched SHA (never reuses an
existing tag), and publishes `agent-board-x86_64-unknown-linux-musl`,
`gh-agent-board-x86_64-unknown-linux-musl`, `SHA256SUMS`, `release.json` and
`provenance.jsonl`. The manifest records the repository, commit, tag, target and
both binary checksums. Every action is pinned by full SHA.

These checks stop accidental off-main releases, stale/ambiguous version upgrades,
tag reuse and substitution of release assets. They do not protect against a
maintainer editing the workflow on another branch: restrict creation of `v*`
tags with a repository ruleset. If tagging succeeds but publication fails, a
maintainer must inspect and clean up that tag/draft before retrying; no force
replacement is attempted. v0.1.0 is publication evidence for that version only.
The [release train](release-train.md) can dispatch this interface, but enrolling
agent-board is a separate operator decision and is not configured here.

## Beyond the release

tracker#939's goal, four weeks running with at least 80% of public agent
spend on upstream work and a board healthy without the operator's hands, is
the epic's measure, not a gate of this release. agentic-job's own release work is
[tracker#596](https://github.com/cgwalters-forge/tracker/issues/596).

[#476](https://github.com/cgwalters-forge/agent-board/pull/476)
([`71ac97e`](https://github.com/cgwalters-forge/agent-board/commit/71ac97e7a136bc551314c77f3cfe99420dd3571e))
closed #467 with a read-only report of the last four complete UTC
Monday-to-Monday weeks ([pass](pass.md#budget-tree)):

```sh
agent-board budget --config FILE --four-weeks --until TIME
```

It needs `budget.harnessRepositories` in the pass's configuration, which
tracker's `pass.json` does not set yet; which repositories count as harness
is the caller's choice. To collect it repeatably, run it with that
configuration and a fixed RFC 3339 `--until`, and keep its output with that
time and the agent-board commit that produced it. A failed or bounded-out
read refuses the whole report with a nonzero exit, so only an exit-0 output
is evidence. The same `--until` gives the same four weeks, but the live reads
can still change between runs, so a saved output is the evidence, not a
rerun. It publishes nothing and is not scheduled.

Each week is compared with 80% unrounded, so 79.9% shown as 80% is not met.
A week with no known cost, an unpriced run or partial costs is unknown. The
criterion needs every week at 80% or more, not a pooled average: one week
below it makes the criterion not met, and otherwise any unknown week leaves
it unknown. Even four weeks met covers only list prices of marked public runs,
not complete spend, so the report leaves the overall criterion unknown.
Its pass-health line stays unknown until the operator defines health; no
link or report here defines it.
