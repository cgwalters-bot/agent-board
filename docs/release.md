agent-board has never been released: the workspace version is `0.1.0`, the
repository has no tags and no release workflow, and its one deployment
builds a reviewed commit from source. v1.0 is criterion 3 of
[tracker#939](https://github.com/cgwalters-forge/tracker/issues/939), and
[#466](https://github.com/cgwalters-forge/agent-board/issues/466) prepares it.
This page is the checklist the release waits on, and the
[changelog](../CHANGELOG.md) is where its notes collect.

A merged implementation, a successful live run and a satisfied criterion are
different evidence, and a closed issue is none of them. A gate is `met` only
when its row links the merged implementation and the live evidence (or
says `n/a` where there is nothing live to show); otherwise it is `blocked`,
with what is missing. The test below only sees that a link is there;
whether it proves the gate is the reviewer's call.

The rows keep four kinds of evidence apart. **Source** is a merged pull
request, linked with its merge commit. **Offline tests** run that source in
CI against fixtures and fake transports, with no credentials. A **live trial**
is one recorded run against real GitHub with its report linked. **Installed
recurrence** is a caller that is installed and has run on its schedule. Each
kind proves only itself: a closed issue or merged source never makes a live
or recurrence column met.

## Supported interfaces

These are what v1 would ask callers to rely on; the `config-contract` gate's
baselines say how configuration may change compatibly.

- **Binaries:** `agent-board` and `gh-agent-board` (the same CLI, run as
  `gh agent-board`), with the commands and flags of the
  [CLI reference](cli.md), which a test keeps equal to the binary's help.
  Writes preview unless `--apply`, within `--max-dispatch` and
  `--max-writes`. Exit codes: 0 success, 1 failure or invalid invocation,
  3 an epic plan's precondition failed ([epic plans](epic-plans.md)), 4
  authentication required, as gh's where they overlap.
- **Configuration:** the pass's one file ([pass](pass.md#one-configuration-file)),
  the poll's ([poll](poll.md)), the supervisor's
  ([supervisor](supervisor-requests.md#configuration)), the release train's
  ([release train](release-train.md#configuration)) and the board's
  `agent-board.json` (`--board-config`). Unknown keys are refused.
- **Records on the forge**, each versioned by its `schema`:
  `agent-board/job-plan/v1` ([job plans](job-plans.md)),
  `agent-board/epic-plan/v1` and `agent-board/epic-apply/v1`
  ([epic plans](epic-plans.md)), `agent-board/operator-action/v1`
  ([operator](operator.md)), `agent-board/holds/v1`,
  `agent-board/maintain-plan/v2`, `agent-board/maintain-digest/v1`,
  `agent-board/sweep/v1` and `agent-board/sweep-verdicts/v1` ([pass](pass.md)), `agent-board/supervisor-ledger/v1`
  ([supervisor](supervisor-requests.md)), `agent-board/cost-day/v1`
  ([cost](cost.md)), and the snapshot and plan files `board-snapshot/v1` and
  `board-plan/v1`.
- **Forges:** GitHub fully, Forgejo read-only, GitLab not at all
  ([forges](forges.md)).

Not supported, and not part of v1 unless a later decision adds them:
`output check` and `output apply` (agentic-job's independent check is the
path for agent output), sweeping of the test projects and scratch issues
the CLI creates, Forgejo writes and dispatch, and GitLab.

## Install and build today

Users install from the repository with `cargo install --locked --git`
([setup](setup.md#install)). A deployment pins a reviewed 40-character commit
and builds it with `cargo install --locked --rev`
([pinned callers](setup.md#pinned-callers)); tracker's workflows do so
through `just build-agent-board` with `AGENT_BOARD_REV`, and its
`agent-board-pin` workflow proposes moving that pin. CI's `rust` job runs
`just check` and the CLI against the fixture on every pull request and on
main. There are no release binaries, so there are no checksums to verify.

The release path to reuse rather than build: the [release train](release-train.md)
already bumps a Rust workspace's version and dispatches the release
repository's `release.yml` with `version`, and agentic-job's `release.yml`
tags main's commit and publishes static binaries with SHA-256 checksums and
an attested manifest. Adding such a workflow here, and pointing the train at
agent-board, changes release policy and needs the operator's decision first.

## Beyond the release

tracker#939's goal, four weeks running with at least 80% of public agent
spend on upstream work and a board healthy without the operator's hands, is
the epic's measure, not a gate of this release. agentic-job's own release work is
[tracker#596](https://github.com/cgwalters-forge/tracker/issues/596).

[#476](https://github.com/cgwalters-forge/agent-board/pull/476)
([`71ac97e`](https://github.com/cgwalters-forge/agent-board/commit/71ac97e7a136bc551314c77f3cfe99420dd3571e))
closed #467 with a read-only report of the last four complete UTC
Monday-to-Monday weeks ([pass](pass.md#budget-tree)):

```sh
agent-board budget --config FILE --four-weeks --until TIME
```

It needs `budget.harnessRepositories` in the pass's configuration, which
tracker's `pass.json` does not set yet; which repositories count as harness
is the caller's choice. To collect it repeatably, run it with that
configuration and a fixed RFC 3339 `--until`, and keep its output with that
time and the agent-board commit that produced it. A failed or bounded-out
read refuses the whole report with a nonzero exit, so only an exit-0 output
is evidence. The same `--until` gives the same four weeks, but the live reads
can still change between runs, so a saved output is the evidence, not a
rerun. It publishes nothing and is not scheduled.

Each week is compared with 80% unrounded, so 79.9% shown as 80% is not met.
A week with no known cost, an unpriced run or partial costs is unknown. The
criterion needs every week at 80% or more, not a pooled average: one week
below it makes the criterion not met, and otherwise any unknown week leaves
it unknown. Even four weeks met covers only list prices of marked public runs,
not complete spend, so the report leaves the overall criterion unknown.
Its pass-health line stays unknown until the operator defines health; no
link or report here defines it.
