# One pass

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

This is the proposed contract for `agent-board pass`; the operator reviews it
on the pull request that changes it, and the [architecture](architecture.md)
records the decisions it follows. A pass
finishes once; it is not a daemon, a second planner, or a JavaScript compatibility
layer. Existing [PR follow-up](poll.md),
[job-plan](job-plans.md) and [epic-plan](epic-plans.md) protocols remain the
authority for their operations. The differences below are intentional.

## What is built

The pass implements the configuration below and stages 1 to 5, except
that the one rerun is the plain [`reruns`](#reruns) rather than one only of
infrastructure failures, and stage 2 still writes poll's claim
and marker comments in every followed repository, external ones included.
The [maintain](#maintain) digest is dispatched only where its repository is
public; elsewhere it is planned and recorded but not dispatched.

Stage 1 reads `usage.url`, the broker's `/usage`, without the forge token or
an environment proxy (plain HTTP is allowed for a broker on a private network
that encrypts it, such as a tailnet), and paces each configured pool it reads
(claude from Anthropic's windows, openai from Codex's) as tracker's
[`usage.cjs`][meters] does. Its line is
`usage: claude: 18% used, pace allows 50%, resets T, read T; openai: …`, and
stages 2 to 4 pace by it, pull requests' fix and continuation runs included.
A preview then prints
`usage: publish to OWNER/REPO#N; a preview paces by it unpublished`; an
applying pass edits the bot's comment
there (or adds one, as the bot), only in a private repository, and prints
`usage: published URL`. That is one write step, and the pass's first,
so `--max-writes 1` spends it there. A failed read is one line,
`usage error: reading the broker: …`, counted as a failure, and pacing falls
back to the published snapshot under the staleness rules below. Without
`usage.url` the line says pacing reads the published snapshot. Unlike
`usage.cjs`, a pool the broker has no current week for (after a broker
restart) is held (`no-reading`), not carried from the previous snapshot; and
the snapshot has no `windows`, `workers` or Mistral allowance (the review app
reads that from the pools file). Every pool's entry carries the pass's
decision, `hold` and a `reason` (null unless held), and a paced one its
`limit_percent`, `min(allowed_percent + burst, target_percent)`, past which it
holds, so the review app shows that rather than its own. A recording keeps the
broker's answer under no address.

The broker learns a pool's windows only from the responses to requests made
through it, so after a restart a held pool would never get a reading. With
`usage.probe`, a pool with no reading whose count of requests in the broker's
answer (`anthropic.counts`, `codex.counts`, as `mistral.counts`) is zero, and
with no run in flight named for it, takes one run in stage 4, within
`--max-dispatch`: `probe: claude has no reading; one run to take one` before
its start. Its requests give the next pass a reading. A pool with requests and
still no reading, or without a count, stays held, and the published snapshot
holds it either way (`no-reading`).

With `holds` set (off unless set; agent-board#307), the pass also publishes
the holds of stages 3 and 4, so that the review app renders the pass's
verdicts rather than deriving its own from labels. Each hold is decided as a
typed value, a kind, a reason and whether it waits on the operator, and its
`hold …` line is made from that
value, so the line and the snapshot cannot say different things. Each
candidate stage 4 holds (`hold OWNER/REPO#N: R`), each epic stage 3 holds
(`hold epic OWNER/REPO#N: R`) and each hold of every new run (`hold
wip|pools|budget: R`) is one entry:

```json
{"item":"cgwalters-forge/tracker#596","url":"https://github.com/cgwalters-forge/tracker/issues/596","epic":true,"kind":"epic-unplanned","reason":"its planning request URL got no plan, nor did URL0 before it; a person comments on the epic to plan it again; label needs-human, Why Q: Planning this epic got no plan twice (its run 77 ended failure). What should change?","operator":true,"priority":"P1","question":null}
```

`reason` is the text after `hold …: ` on its line, `priority` the item's board
Priority and `question` what its board Why asks after a leading `Q:`, each null
where there is none; a hold of every new run has a null `item`, `url`,
`priority` and `question`. `operator` is true for the kinds only the operator
releases: `needs-human` (labelled so, by a person or a triage verdict),
`epic-unplanned` (an epic's planning request got no plan) and
`needs-operator` (an invalid or refused plan, an apply cut short and not
proved, a plan dispatched by hand, no plan with triage off, or a run that
failed again after its [rerun](#reruns)), and `pr-open` on an issue labelled
`needs-operator-approval` (below). The one
exception the other way is an epic whose first planning request got no plan and that the
pass retries once by itself after the cooldown (`… got no plan; planned once
more from T`): `epic-unplanned` with `operator` false. When the retry gets no
plan either, the hold is `epic-unplanned` with `operator` true; once its
`needs-human` label is on, it is `needs-human`, its Why's question in
`question`.
A candidate whose parent is not a live epic (see [Scheduling](#scheduling))
is held `epic-not-live` with a line of its own after the `candidates:` line
(`hold OWNER/REPO#N: its parent OWNER/REPO#E is not a live epic …`), but the
snapshot has one entry per such parent instead of one per child: the
parent's `item` and `url`, `epic` true, the highest Priority among its held
children, a reason that counts them and names up to three at the board's
first two Priority options (P0 and P1), and `operator` true only where there
is one, so that the review app asks the operator once to label the epic.
The other kinds are `closed`, `needs-design` (labelled so: a parked design,
which still blocks dispatch but asks the operator nothing), `blocked`
(board Blocked), `waiting-on` (open
dependencies, or a lower stacked slice not yet open), `pr-open` (the bot's or
the operator's; on an issue labelled `needs-operator-approval`, read
case-insensitively, its reason is `approve pull request REPO#N to merge` and
`operator` is true, since the poll merges the bot's pull request for it only
on the operator's approval; the pass reads the issue's labels, not the pull
request's, nor whether the review job has approved yet),
`in-flight`, `dispatched` (its plan's run has ended, or an
epic's planning request waits for its plan), `triage-cooldown` (triaged or
planned too recently to ask again), `outside-epics` (no triage under the
triage scope `epics`, see [Scheduling](#scheduling)), `overlap`, `overlap-ignored` (not a hold:
an overlap the `overlap` setting let start, see [Scheduling](#scheduling)),
`unreadable` (labels, pull
requests, a parent epic, a plan's target or the runs not read whole), `wip`,
`pools`, `budget` (the week's spend reached `budget.weeklyUsd`, or has no
reading; see below) and `other`; a reader shows a kind it does not know as
`other`. Entries are sorted by repository and number, the holds of every new
run first. A candidate whose consideration failed (`fail …`) or that the pass
did not reach has none.
After stage 5, unless stage 3 or 4 failed or stopped early (`epics error: …`,
`schedule error: …`, `epics: the pass's request or time budget is low`), the
snapshot `{"schema": "agent-board/holds/v1", "at": T, "truncated": N,
"wip": {…}, "pass": {…}, "holds": […]}`, T the clock of the pass that last
changed them, goes to the bot's own comment on
`holds.repository`'s issue `holds.issue`, found again by its first line
`<!-- agent-board-holds v1 -->`, under the same checks as the usage
comment's: a private repository, and a new comment only as the bot. It is one
write step within `--max-writes` (`holds: published URL`); where the comment
already has the same holds the line is `holds: unchanged` and nothing is
written, and a preview prints
`holds: publish to OWNER/REPO#N; a preview does not write it`. An applying
pass that waited for another in progress, or that has spent its request
budget or time bound, publishes nothing (`holds: not published; why`). A
failure is one line, `holds error: …`, counted as a failure, and the pass
goes on. The holds issue, like the usage issue, is never a candidate.

`wip` is `{"limit", "in_flight"}`: the `wip` setting, and the runs holding
a slot once stage 4 counted them, its own starts included (null where it
did not get that far). `pass` is `{"mode", "candidates", "started",
"live_epics"}`: `preview`, `actions` or `local`; stage 4's
`candidates: N …`; the runs stages 2 to 4 started, or in a preview would
start; and the sum of stage 3's `epics: N live …`. `candidates` and
`live_epics` are null where their stage did not get that far. With
`revisit` set, `pass` also has `revisited`, the [revisits](#revisits) among
`started` (null where stage 4 did not get that far); without it the key is
absent, so a pass without it publishes what it did before. `wip` and
`pass` were added to v1 later, so a reader treats them as absent in an
older comment, and a change in either publishes as a change of the holds
does. With `leases` set, the snapshot also has `leases`, after `pass`: the
live [leases](#leases) the pass read, each `{"slot", "run", "item", "pool",
"taken_at", "expires_at"}` and `"override": true` where the operator took
it so; absent otherwise, and where stage 3 or 4 did not get as far as
reading them. It too was added to v1 later, and a reader treats
it as absent in an older comment.

The JSON is compact, one entry a line, so that a board of a few hundred holds
fits GitHub's 65,536-character comment. The comment is also capped at 60,000
characters: past that, item holds that do not wait on the operator are left
out until it fits, those without a Priority first, then the lowest Priority
(`P3` before `P0`), then the newest (the highest number), and `truncated`
counts them (otherwise 0). The operator's holds and the holds of every new
run are always kept; should they alone not fit, nothing is published and the
line is `holds error: …`.

With `budget.weeklyUsd` set (agent-board#281), stage 1 also records the
broker's `spend.runs`, the trailing week's cost of runs' requests at API list
prices in dollars ([praxis-credential-broker#38][spend]), in the snapshot's
`budget` (`weekly_usd`, `spent_usd`, `prices`, `unpriced_requests`, and the
broker's `since` and `unmetered_requests` where it gives them), and its line
ends `budget: $412 of $1000 this week at list prices`. Spend in another
currency, basis or window is no reading, and so is a broker without `runs`, a
total that leaves runs' requests unpriced
(`budget: $1000 a week, 3 request(s) unpriced (held)`) or does not say how many
it does, and a snapshot without it: never $0. Operators' interactive use
neither counts nor, unpriced, holds. A `since` under a week old does not hold
either: the broker's spend restarts with it until praxis-credential-broker#35,
so the week may read low after a deploy. Once the week's spend reaches the budget,
stages 3 and 4 start no new run (`hold budget: weekly budget reached; new runs
wait`, and `…; budget: weekly budget reached` on an epic stage 3 would plan);
pull requests' fix and continuation rounds go on until it is 10% past,
so that work in flight can land, then wait too (`budget: weekly budget
reached; pull requests' fix rounds wait`). A missing or stale spend reading
holds both, as missing usage does (`hold budget: the usage snapshot has no
spend reading; new runs wait`). Stage 4's stop is a `budget` hold of every
new run in the hold snapshot above, and counts as one in the summary's
`held`. Its reason names no dollar amount, so that what the pass publishes
does not either; the `usage:` line has the figures. It gives no resume time:
the broker's spend is a trailing week with no reset, so new runs go again on
the first pass whose reading is under the budget.
Without `budget` nothing holds on spend.

With `budget.source: "broker"` (agent-board#341), the budget is instead the
broker's grant for this board, `praxis-broker-grant/v1` from `budget.url`
([praxis-credential-broker#41][grant]): a share of each grant pool that the
operator's private policy sets and the broker has already paced, in
percentages, with no dollar amounts. `budget.pools` maps each of `pools` to the
grant pool it draws on (`claude` and `fable` to `anthropic`, `openai` to
`codex`). Stage 1 then writes each pool's entry from the grant, not the
broker's windows: its line reads `claude: 18% used of 32% granted on anthropic
unified_7d, read T`, the window with the least room, which ranks the pools. A
pool is held (`; holds new work (grant)`) when its grant pool or any window
says `hold`, or a window has used what it allows or gives no figures, however
old the grant. A grant that holds, a pool missing from it (no share), a pool
not marked stale without windows, a window used up or without figures, stale
or not, a grant without `observed_at` or observed in the future, and an
unreadable grant
(`usage error: reading the grant: …; every pool holds`, a failure) hold
outright (`claude: held by the grant (grant)`), and are never probed. A pool
the grant marks stale, whose holds are then the staleness, and an otherwise
unheld pool of a grant not observed in the last five hours are no reading,
which `usage.probe` may probe as above, once after a broker restart: one run
for each grant pool, none while a run is in flight on any pool drawing on it.
When `/usage` cannot be read, the pass
paces by the grant alone (`usage error: reading the broker: …; pacing reads
the grant`), never by the published snapshot. Pull requests' fix rounds pace by
the same entries. A `weeklyUsd`, or a pool's `target` or `burst`, beside it
is refused: the grant replaces them.

Stage 3 reads the open `epic` issues of `epics.repository` with their
sub-issues (20 epics a request), the board's Priority options, and each live
epic's comments, and takes the live epics in Priority order. Its first line
counts them, such as `epics: 7 live of 17 open in example/tracker`, then
one line an epic:

* `apply epic OWNER/REPO#N plan=ID: Create a sub-issue in example/work (P0);
  Close example/work#9 as not planned` where the newest accepted plan has no
  receipt, applied with `epic apply`'s checks, its comment and change time
  pinned. A new sub-issue gets its final Priority with its create: the plan's
  `set_priority` of it, else the board's last option. An applying pass ends
  the line with what the [receipt](epic-plans.md#apply) says and
  `receipt=URL`. Its receipt and each action that writes are one write step
  each, held whole by `--max-writes`; one epic is applied a pass.
* `recover epic …` where the receipt was cut short (`claimed` or `stopped`)
  and every action's effect is proved by the identities it confirmed and the
  epic now; an applying pass rewrites the receipt as `recovered`, one write.
  Writes after a create that the receipt did not confirm are observed: the
  sub-issue's link, its board Priority and its job plan. One that is not
  proved is held for a person with the actions it cannot prove, and never
  replayed; so is an epic with a receipt that cannot be read.
* `start planning OWNER/REPO#N pool=P: why` for the first due epic: a
  triage run on the epic, started as stage 4 starts one, from `planPools`,
  whose brief asks for an epic plan. It takes a slot from stage 4 and counts
  against `--max-dispatch`; one epic is planned a pass. Its plan comment is
  the bot's last planning request on the epic, edited in place where there
  is one the bot wrote and only the bot edited (agent-board#429): its new
  change time makes it a new plan. Read again just before the edit, a
  comment changed since the pass read it is left as it is, and the epic
  held to the next pass. Its dispatch record is still a comment
  of its own, since the claim protocol orders records by comment.
* Where every sub-issue of a due epic is closed (it has at least one),
  it is not planned: no plan is needed to say it is done. With
  `epics.close`, `close epic OWNER/REPO#N: every sub-issue is closed; why`
  comments so and closes it as completed, two write steps held whole by
  `--max-writes`; else `hold epic …: every sub-issue is closed; why; label
  needs-human, Why Q: …` asks the operator, setting the question in its
  board Why, then commenting and labelling it `needs-human`, three. Either
  comment's hidden first line, `<!-- agent-board-epic-done: HASH -->`,
  hashes the sub-issues and their states, so it is said once for them
  (`epic …: every sub-issue is closed, as URL says`), the bot's alone
  counting; a write that failed before the comment is made again by the
  next pass. An applying pass lists the epics again just before these
  writes, and holds an epic whose sub-issues or holds changed since
  (`…; not yet: why; the next pass reads it again`). A new sub-issue plans it again once no label holds it. The
  operator's comment after the ask, with no planning request since,
  answers it: where the label is the epic's only hold, `release epic …:
  the operator answered URL; unlabel needs-human` takes it off, one write
  step, and the epic is planned.
* `epic OWNER/REPO#N: plan ID applied; nothing changed since T`, or
  `hold epic OWNER/REPO#N: why`: a planning run in flight, a request waiting
  for its plan, or for its retry six hours after its run ended, an invalid
  newest plan, or a person's hold (`needs-human`, `needs-design`, board
  Blocked), which also says what the epic would otherwise come to.
* A request that got no plan is planned once more (`start planning …: its
  planning request URL got no plan, retried once`), its plan's comment
  naming the request it retries. When the retry gets no plan either, the
  epic is held for the operator: `hold epic …; label needs-human, Why Q: …`
  labels it `needs-human` and sets its board Why to a question with what
  the planner said (the first line of the bot's newest comment since the
  request, else how the run ended), two write steps held whole by
  `--max-writes`. A person takes the label off and comments to plan it
  again; without a comment it is labelled again.

An applied plan is recognised from its receipt, older receipts (the hidden
claim and fingerprint comment) included, never from titles: a sub-issue
retitled, closed or reprioritised since is not missing. An epic is due when
it has no plan or request; on the operator's comment since its last plan
(for a plan that cannot be applied or recovered, since its last request too,
so a run that answers nothing is not started again);
otherwise, once a day has passed since its last request (its record, or for
an epic planned before this stage, its plan), when a sub-issue was added,
removed, closed or reopened against the receipt's fingerprint; a merged
pull request counts through the issue it closes. That wait doubles for each
applied plan in a row that had no actions, up to `triageFollowUpDays`. So
a plan with nothing to do ends planning until a sub-issue changes, and an
unchanged epic is not planned again (agent-board#383). Not noticed
(agent-board#429): edits of the epic's or a sub-issue's text, label and
Priority churn, and a comment by anyone but the operator, whose word alone
decides an epic's plan.

Stage 5 reads the whole board (closed issues and pull requests included, in
about one request per hundred items) besides the runs and open issues that
scheduling reads, and reuses those where scheduling read them. Its first
line counts the changes, such as
`status: 39 change(s) of 46 item(s) read; 2 kept, their own facts not read whole`
(draft issues and redacted items, which the whole-board read cannot see,
are not counted and keep their Status),
then one line per change, `status OWNER/REPO#N: OLD -> NEW (why)`, for
example `status example/work#12: Todo -> In Progress (pull request
example/work#14 is open)`. Each change is one write step; one that
`--max-writes` holds starts `held by --max-writes: `. An applying pass
reads the item's Status again just before writing it, and leaves one a
person changed since (`changed to X since the board was read`); that read
and the write are two of the pass's 500 requests, so once the budget or the
time bound is spent the rest wait for the next pass, on one line. The stage
is not serialized by the hold that keeps two passes from starting work: two
overlapping passes derive the same values, and the read before each write
leaves what the other wrote. More changes than `--max-status-changes` (50
unless given) refuse the stage whole: it writes none, prints each as
`refused: status …`, and fails the pass, a preview too, so that a first
pass over a board that drifted is looked at first and then let through
once with a higher number.

Each decision is one line: `start triage|implement|planning|revisit OWNER/REPO#N … pool=P`,
`revisit: …` and `revisit OWNER/REPO#N: why`, `maintain: …`,
`apply|recover epic OWNER/REPO#N …`, `epic OWNER/REPO#N: …`, `usage: …`, `holds: …`,
`hold [epic] OWNER/REPO#N: why`, `hold wip|pools|budget: why`,
`review rerun|check rerun|run rerun OWNER/REPO#N …`,
`held by --max-dispatch: start …`, `status OWNER/REPO#N: …`, `fail …` or
`… error: …`; a pull request's
step that a cap held ends `-> held by --max-dispatch` or
`-> held by --max-writes`. With `--apply`, a started line also names its
dispatch record and run. The last line is a summary such as
`summary: dispatched 1/1, writes 3/5, held 12, requests 80, points ~95`, which
counts what a preview plans and what an apply did (an uncapped kind has no
`/N`), the steps the caps held plus stage 4's stop on the weekly budget, and the pass's budgeted requests and GraphQL
points; `~` marks points estimated as 1 a query and 5 a mutation where the
response reads no `rateLimit { cost }`.
A request GitHub still refuses under a rate limit after the client's
retries stops the pass from sending anything more, as more requests only
prolong a secondary limit: the refused operation fails as usual, the
requests not sent are left out, and one `rate-limited: …` line says why,
before the summary, which then ends `, rate-limited`. The next pass carries on.
`--record FILE` previews live and saves every read as a new fixture. Add
`--replay SEED` to answer reads the token cannot make, such as a private usage
snapshot or the broker's `/usage`. A preview counts only the PR runs that stage 2 actually starts, so it
can show more free slots than an applying pass would.

A triage run is started by posting the bot's `triage` job plan on the issue and
dispatching it with the job-plan protocol, so the dispatch record is the claim.
A pass interrupted between that post and its dispatch leaves a triage plan,
which is a manual dispatch; a person dispatches or replaces it.

In a GitHub Actions run, stage 4 of an `--apply` pass starts nothing while
another run of the same workflow is in progress (`hold wip: another pass is in
progress`): two passes that both saw a free slot could otherwise both take it.
Give the caller's workflow a `concurrency` group, so that passes queue rather
than hold each other. Outside Actions, `--apply` is refused unless both
`--max-dispatch` and `--max-writes` are given, and the pass prints a warning
that it is not serialized against the scheduled workflow: a capped local apply
is how a person tries new write behavior on a live board one step at a time,
for example `--max-dispatch 1 --max-writes 3`, and the caps bound what a race
with the scheduled pass can cost. Both stages start runs from `dispatchRef`, or the caller's
default branch. Past 15 minutes no new request is sent; writes, and a start that
passed its last check in time, have two minutes more to finish, after which
what was written is observed by the next pass.

## Order and effects

`agent-board pass --config FILE` previews by default. Only `--apply` permits
writes, and then pass makes them itself with the bot's token: Status, labels,
comments, closes, merges and dispatches. These are deterministic consequences
of forge facts, not agent output, so they do not go through agentic-job's
check and apply; that boundary is for what agents produce. Their guards are
preview by default, caps per pass, and the replay gate below. The caps are
two flags, unset by default: `--max-dispatch N` bounds the agent runs a pass
starts, stage 2's fix, rebase, continuation and answer rounds and their
reruns and its [review](#reviews) starts, stage 3's planning run and stage 4's starts and reruns together, and `--max-writes N` bounds its
other write steps, forge writes such as comments, labels and merges (stage
1's usage comment, stage 2's comments, labels, retitles, retargets, enqueues,
merges, branch updates, review reruns and required-check reruns, stage 3's
epic apply, a step for its receipt and each action that writes, taken whole,
and its recovery, stage 4's released records and alarm issues
([start failures](#start-failures)), and stage 5's Status changes).
The unit is a step, not a request: a fix round's claim, marker and dispatch
are one dispatch, and a stop's label and marker one write. A step is checked
before its first write and taken whole or held whole; a held step is
reported on its line and left to the next pass.
A held start takes the slot it would have had, so a capped pass reads no
further than an uncapped one. The numbers for the scheduled pass are an
[open question](architecture.md#open-questions).
The caller uses trusted default-branch configuration and a pinned build, and
supplies credentials through the environment, never the file. Issue text, PR
bodies, run names and comments other than authenticated operator direction are
data, not instructions.

`--fix-bounds FILE`, absent by default, names the caller's agentic-job bounds
file for its `fix` kind (tracker's `.github/agentic-job/fix.toml`), from the
same trusted checkout as `--config`. With it, stage 2 starts no fix, rebase
or continuation round, all dispatched as that kind, on a pull request
whose repository or head branch the file's `repos` and
`outputs.push_to_pull_request_branch.branches` leave out; its line says
`skip: left to the operator: head branch "B" is outside the fix bounds`, and
nothing is claimed, marked, labelled or dispatched. Merges are unchanged.
The [poll](poll.md) says which globs it reads. It does not replace
agentic-job's policy step, which stays the boundary; it saves the run that
step would refuse.

A pass captures one clock and performs these stages in order:

1. Refresh usage from the configured broker, retaining the existing normalized
   paced-window calculation (target, burst, short-window exhaustion and original
   observation time). Read the previous trusted snapshot and publish the new
   `bot-usage/v1` snapshot to the configured private issue. Preview computes it
   without publishing, and paces by it all the same. A failed refresh is
   visible; it cannot turn missing or stale readings into spare capacity.
2. Follow up PRs using today's `poll` decisions: read followed repositories,
   PR heads, reviews, checks, comments and runs; dispatch bounded fixes/reviews,
   merge only an approved head with green required checks, or comment/label for
   a person. For a harness PR (the bot's PR from its fork), an `APPROVED`
   review by the configured `operator` at the current head suffices in place
   of the review job's approval. An operator approval at an older head and a
   visitor's approval count for nothing. This uses the same merge path,
   including enqueueing where a merge queue is required: required checks,
   head rechecks and per-pass write caps still gate it. Its log is
   `merge OWNER/REPO#N: approved by the operator at <head>`.
   Retain its claim and head-recheck rules, but follow the
   [bookkeeping rule](architecture.md#bookkeeping): in an external repository
   the claims and markers become one hidden comment the bot edits in place, and
   it posts no claim or status comments there. Count every dispatch made
   here against capacity before starting anything later. Pacing here reads
   stage 1's reading, or where the refresh failed or is not configured, the
   previous trusted snapshot; missing/stale readings hold new PR runs,
   including on a cold start.
3. Read the complete board, Priority options, live epics, their children,
   authenticated operator comments, accepted plans, apply receipts and current
   runs. Recover completed epic applies, apply an accepted pending epic plan,
   or start at most one due epic-planning run. Epic apply may create/link issues,
   set Priority, rescope or close children and post plans/receipts within the
   existing epic bounds; planning itself only dispatches a triage run. Refresh
   affected board/issue facts after an apply before scheduling.
4. With [`reruns`](#reruns), rerun once a candidate's failed run, then
   choose and dispatch work by the rule below. Dispatch writes the existing
   plan claim and run link, and the existing board Run update where supported;
   it does not close issues from guessed outcomes.
5. Derive Status for every board item, closed issues and merged pull
   requests included (this stage reads those, which earlier stages skip),
   from this pass's facts and its own starts, and write each one that differs:
   * closed issue, or merged or closed pull request: **Done**;
   * otherwise, the `needs-human` label on the item: **Needs human**;
   * otherwise, a run in flight for it, or an open pull request for it (the
     item itself, or one that says it closes the issue, in any repository and
     by any author; draft or not): **In Progress**;
   * otherwise, a derived value that no longer holds (Needs human, In
     Progress, or Done on an issue open again), or no Status at all, goes
     to **Todo**;
   * otherwise the Status stays. **Blocked** and **Backlog** are a person's
     holds: only Done replaces them, so neither the label, a run nor a pull
     request moves them (the label still holds scheduling). The legacy
     columns (Triage, Draft, In Review, Cancelled) give way to any rule
     above; a person's **Todo** stays. An item added to the board without a
     Status, by `gh project item-add` or by the pass when it files one,
     thus becomes Todo on the next pass that reads its runs and pull
     requests whole.

   The rules' precedence is shared with poll's `statusReconcile` preview.
   No person or agent sets the derived values, `agent-board ask` included,
   which only sets and clears the label; an edit to one is overwritten on the
   next pass. An item whose facts were not read whole keeps its Status:
   its own fields, labels or state incomplete, or, for the fall back to Todo,
   runs that could not all be listed or an open issue's closing pull requests
   that could not all be read.
6. With `cost`, from its hour each day, publish the last days' cost reports
   that are not on `epics.repository`'s `data` branch yet, as one write step
   within request bounds of its own (see [cost](cost.md#publishing)).

The result names actions, holds, incomplete reads and failures, with a nonzero
exit for an operational failure. Independent PRs may still be followed when an
epic cannot be read. Do not schedule from an incomplete candidate set or missing
hold facts. Re-read the chosen plan, holds and capacity before each dispatch;
reserve its slot before sending, including when the response is ambiguous.
There is no transaction across stages: preserve receipts for writes already
made, stop the affected operation, and recover by observation on the next pass.
Deleting a local cache must never authorize replay.

To stop an unbounded board scan or runaway dispatch loop, use one fixed pass
budget: at most 500 forge requests and 15 minutes, including existing subcommand
work; existing tighter read/action bounds still apply. Report exhaustion and
defer unresolved decisions, never interpret truncated data as empty. There is
no second fill-page budget. Preview performs no forge writes or dispatches and
does not change the apply cache.

## Scheduling

There is one candidate set: open board issues in explicitly configured work
repositories, excluding epics and the usage issue. An epic child qualifies
only through a live epic whose latest `epic` label event is the operator's
or the bot's: the operator files epics through the bot.
A live epic is in `epics.repository`, or with `epics.inWorkRepositories` in
any work repository; stage 3 plans only the former. A child of any other
parent does not qualify, and is held as `epic-not-live`, so the operator sees
what waits on the label (see the hold snapshot above).
An unparented issue qualifies only when opened by the operator or bot; public
visitors must not be able to spend runs simply by filing issues. Deduplicate by
repository and number. No separate under-pace candidate source exists.

Order by Priority (P0, P1, and so on; unset/unrecognized last), then oldest
creation time, then repository/number for stable ties. For epic children compare
epic Priority first, then child Priority, then age; an unparented issue uses its
own Priority as the first rank. A child in several live epics uses its highest
ranked parent. Priority is the only readiness ordering; there is no Ready step.

`wip` is the total cap on noncompleted caller-workflow runs, including queued,
waiting, planning, triage, implement, review and fix runs. Include starts earlier
in this pass even if the API has not listed them. With `pr.reviewPools`,
the review job's runs the pass started in the followed repositories count
while they run and their head waits for them ([reviews](#reviews)). A pre-existing excess is not
cancelled; it leaves no new slots. PR repair retains its own existing bounds;
if it consumes/exceeds WIP, later stages start nothing. No planning exemption.
GitHub can leave a run `in_progress` after every job has completed
(agent-board#376). Such a run is not in flight, for the slot count, the
run-in-flight and overlap holds, the Status stage and an epic's planning run
alike, once it is over an hour old and its jobs have all completed, the last
over ten minutes ago (a run's next job is not listed until it is due). Age
alone never ends a run. It is then handled as a finished run with no
conclusion. A younger run costs no extra request, an older one's jobs are read
once a pass, and a jobs read that fails or does not fit one page leaves the
run in flight.

Respect `needs-human`, `needs-design`, board Blocked, open dependencies, an open
PR for the issue or plan target, a run in flight, and the existing bot-PR/path
overlap hold, including draft rescue PRs. Keep explicit stacking semantics;
never guess a stack from overlap. An unreadable hold is not permission to start.
Check both the board issue and a plan's target; neither may escape configured
repositories. To avoid duplicate/conflicting work, pass always enables the
existing bot overlap check and conservatively waits when it cannot complete it;
this is stricter than standalone dispatch's best-effort heuristic.

With `overlap` set (agent-board#426), an open pull request of the bot's that
overlaps a start does not hold it when it is a draft opened and last
committed to at least `overlap.staleDraftHours` before the pass's clock (a
draft nobody moves races no run), or when every path it shares is
documentation (`*.md` or under `docs/`) and the issue is in the board's first
Priority option (such a conflict is cheap to resolve, and P0 work should not
wait on it). Its head's commit time stands in for its last push. Each overlapping
pull request is judged alone, and any one not waived still holds the start;
a run in flight is never waived. A waived overlap is said as
`overlap ignored: OWNER/REPO#N: open pull request … changes …, but …`, kept
in the hold snapshot as kind `overlap-ignored` (not blocking, not the
operator's), and the dispatch record says it too. The draft rule reads one
more request per overlapping pull request, for at most four of them, which
a start's request reservation covers; any past those, and one that cannot
read, holds the start, as any unreadable overlap check does.

With no accepted plan, start one triage run if enabled and a slot/pool is
available, for an issue in the triage scope (below). It proposes an
implement plan, or explains a needs-design/human hold; it does not close
the issue itself. Record the question using the
existing dispatch claim protocol, not another scheduler marker. A completed run
without a usable plan remains visible for a person; do not automatically retry,
unless `triageFollowUpDays` is set. Then the triage brief asks for a
`schedule-triage` verdict, and once the run is no longer in flight the pass
reads the newest one the bot posted after the dispatch record, unedited but by
a writer; a visitor's comment is never a verdict. A comment by the operator
after it (or after the record, with no verdict) triages the issue again.
Otherwise `done`, `obsolete`, `needs-design` and `needs-operator` label it
`needs-human`, so it shows as the operator's ask, and post one comment
whose hidden first line, `<!-- agent-board-hold: verdict COMMENT-ID -->`,
names the verdict comment it holds, then a sentence saying so: one step of
two writes under `--max-writes`, neither made in a preview. The label then
keeps the issue out of the follow-up; taken off with no operator comment,
the same verdict labels it and posts the comment again.

With `triageClose` (agent-board#428), `done` instead closes the issue as
completed and `obsolete` as not planned, and the pass posts one line
linking the verdict, so the operator can reopen it: the line, then the
close, again one step of two writes under `--max-writes`, and no label.
No review follows a close, so, as the supervisor's `close` does
(agent-board#111), it closes only an issue locked from before its triage
plan was posted until now, so that no visitor could add or delete text the
triage read, and whose body and every comment were written, and edited if
at all, by the operator or the bot, none of them a supervisor agent's note
(one more read, for the body and lock events). An unlocked issue, or one
locked only later, is never closed this
way, nor is one on an earlier verdict (below), whose run start the pass does
not know. Neither is one whose body or title was edited after the verdict,
nor one with any comment posted or edited after it, an earlier comment the
operator edited, a later word or an `ask create` hold alike, but for the
triage's own dispatch record and its run's agentic-job status comment: the
verdict was about the issue as triage read it. The newest lock, unlock,
title edit and reopen are each read on their own, so that no number of other
events hides one. It also closes once:
reopened after the verdict, whoever closed it, or left open by a failed
close, which leaves the pass's line for that verdict, the verdict then labels
it as above, as does one any of these checks refuses, the line saying why. Without
`triageClose` the pass never closes an issue on a verdict; the
supervisor's `close` may, and takes the label as the pass's hold of a
`done` verdict only with that comment. Before opening a question,
`ask create --apply` comments on the
blocked item to invalidate any earlier verdict, even if its additive labeling
leaves the pass's existing label and event unchanged
([supervisor requests](supervisor-requests.md)). Any other verdict had
nothing to do, and the issue is triaged again only once its inputs changed
(agent-board#383), and no sooner than a day after the verdict, doubled for
each follow-up triage in a row before it (one the operator's comment
started included), up to `triageFollowUpDays`. An unchanged issue waits
for a change or the operator. With no verdict, where the run may have
failed, the issue is triaged again `triageFollowUpDays` after the record,
changed or not, as is one whose triage plan predates this and carries no
fingerprint.

An issue triaged before the pass's own triage, as by a supervisor's
dispatch, can already carry a verdict. With `triageFollowUpDays`, before a
first triage the pass reads the newest verdict the bot posted on the issue,
unedited but by a writer, and takes it as the triage's when nothing happened
after it: no comment posted or edited since but agentic-job's status
comments, the bot's own other comments included (an `ask create` hold is
one), and no edit of the issue's body or title (one more read, made only
when such a verdict exists). It is then
acted on as above, but labels rather than closes the issue. Any other verdict holds
it (`earlier triage verdict …; nothing changed since`) until
`triageFollowUpDays` after the verdict, as a follow-up holds an issue whose
plan carries no fingerprint, or until someone comments or edits a comment, the body or the title;
then the first triage starts.

Work starts from the epics (agent-board#431). Under the triage scope
`epics`, triage, its follow-ups above, re-planning below, a triage's rerun
and [revisits](#revisits) are only for the children of live epics. An
issue outside every live epic, an unparented one the operator or the bot
opened, still runs an accepted plan (its own plan comment, or with
`bodyPlans` its body's), but is otherwise held as `outside-epics`
(`outside every live epic, so not triaged (triage scope epics)`), not the
operator's; an ended triage's verdict is still acted on: it labels the
issue, or with `triageClose` may close it.
The `candidates:` line then counts these issues too (`, N unparented: run
only with a plan`), and with `sweep` set the hold adds `; the weekly sweep
lists it`: the [weekly sweep](#the-weekly-sweep) looks at them as one batch.
The scope `all`, or `triage: true` as before scopes, triages every candidate.

The inputs are a fingerprint of what the pass reads of the issue: its title
and body, the comments of anyone but the bot, its labels, Priority, open dependencies
and open closing pull requests. The bot's own comments (plans, dispatch
records, verdicts) are left out, so they never make an issue due; its other
writes, such as a Priority an epic's apply sets, do. With
`triageFollowUpDays` or `revisit`, each triage plan comment the pass posts
carries the fingerprint as read just before its start, on a hidden line
`<!-- agent-board-inputs: HASH -->` after its intro; the forge stays the only
state. A pass compares it with a fresh read only once the wait is over, at
the cost of a request for the body each pass while such an issue stays
unchanged. The sub-issues of an issue outside an epic are not read for it.

With `replanAfterDays` (agent-board#347), an issue whose newest plan is an
implement plan that was dispatched, whose run is no longer in flight, and that
is still open with no open bot or operator pull request, is triaged again to
plan the rest of it, through the same triage run and dispatch-record protocol,
with no other scheduler marker. It is due `replanAfterDays` after the plan's
dispatch record last changed: the pass does not read when the run ended, and
the run-in-flight hold already waits while it runs. Until then the issue is
held with its due time. The triage posts its own plan, which becomes the
newest and gets its own record, so each implement run is re-planned at most
once; once that triage ends, it is handled as any triage above.

With `bodyPlans` (agent-board#342), an issue in the board's first two Priority
options (P0 and P1) that has no plan comment is first read for a plan in its
own body: one `agent-board-plan` block, weighed as a plan comment is. The
body must be the operator's or the bot's, if edited last edited by one of
them, and its plan must pass the plan checks. Such a plan is treated as the
issue's accepted plan, with the same holds, target repository and pool checks.
At its start the pass reads the body and comments again, and holds the issue
if the body changed or a plan comment appeared. It then posts a copy as the
issue's plan comment and dispatches and records that copy through the plan
protocol, only while it is still the newest plan, so it runs once; from
then on the copy is the plan, and a later edit of the body changes nothing. A
body with no such block, or another author's, leaves the issue to triage. A
body plan that is invalid, or that someone else edited last, holds the issue.
An epic plan may not put a plan block in a body it writes.

The one automatic rerun is meant for infrastructure: a scheduled run that
failed before the agent's work could succeed or fail on its own (runner lost,
setup or checkout failed, broker or forge outage). With `starts`, a run that
failed before its agent session started, or whose inference token its
broker lost mid-run, is that, by the rule of
[start failures](#start-failures); without it, [`reruns`](#reruns) re-runs
any failed run once, and a second failure is left for a person.

With an accepted implement plan, dispatch precisely that plan once. An invalid
newest plan does not mean “no plan”; report it, never fall back. Recorded plans
do not run again, except by the rerun above, or with `starts` once their run
and its rerun failed on infrastructure; an operator/planner
edit or replacement is needed. Research or
triage plans explicitly posted on issues remain manual dispatches.

Choose uniformly among the eligible configured automatic pools, using the same
draw as poll pacing. Headroom (`target_percent * elapsed_fraction - used_percent`)
and config order do not weight selection; duplicate names are one ticket.
Exclude held, exhausted, reset, missing or stale readings (snapshot older than
45 minutes or paced observation older than 30 hours), and readings more than five
minutes in the future. If none qualifies, wait;
do not fall back to a held/unknown pool. Negative room alone does not exclude a
pool if its normalized burst-aware hold is false. An explicit plan pool is
respected, not silently replaced, and must pass the same checks. Pacing applies
to planning and triage too. Capacity is filled by this same rule whether under
or over pace; there is no fill mode, retry pool or shortened planning interval.

This covers implementation from pool-less saved/body plans, epic planning,
no-plan triage and revisits; stage 2's fixes and continuations use poll pacing.
Explicit plan pools remain singleton choices and wait when unavailable. Generated
triage/revisit plans carry the selected pool through to workflow inputs; the
dispatch protocol refuses a conflicting saved plan rather than replacing the
checked pool. Manual dispatch and supervisor requests still name explicit pools,
as does the supervisor agent's own configured runtime: they are not automatic
candidate draws. No manual-only pool is newly opted in. Existing bounded cold
usage probes remain a separate opt-in path, not a missing-usage fallback added
by this selection change. Eligibility is based on known snapshots and cannot
guarantee freedom from provider 429s. In-flight jobs are not changed.

## Revisits

Triage runs once per plan, and `prune` only lists heuristic close
candidates, so an old issue done or overtaken elsewhere, or a held question
that answered itself, is otherwise never looked at again (agent-board#374).
With `revisit` set (off unless set), stage 4 ends by spending the slots its
starts left free on a sample of old candidates:

1. It does nothing with no slot free (`revisit: no slot free`), no room on
   a revisit pool, `revisit.pools` or else `triagePools`, by the rule of
   [scheduling](#scheduling) (`revisit: no pool: why`), or past the pass's
   time bound. A pass that held every new run earlier (WIP, pools, budget,
   another pass) never gets here.
2. Of stage 4's candidates, an issue is due once nobody has touched it (its
   `updatedAt`, which the board read asks for only with `revisit`) for
   `revisit.afterDays`, or for `revisit.heldAfterDays` where a person holds
   it (`needs-human`, `needs-design`, board Blocked). A closed issue, one
   whose labels or pull requests could not all be read, one with an open
   pull request of the bot's or the operator's and one with a run in
   flight, this pass's starts included, are not; a person's hold and open
   dependencies do not keep it off.
3. Three times `revisit.perPass` of them are drawn in order without
   replacement, each by weight: focus, times its own Priority, times its
   silence. With N Priority options, focus is (N + 2) to the power of its
   live epic's Priority counted down from the board's first option (with
   P0 to P3: 6⁵ for P0 down to 6¹ for unset), so at equal silence one step
   of the epic's Priority outweighs any difference of its own; an issue outside a live
   epic has focus 1, the least, but stays eligible (not under the triage
   scope `epics`, which revisits only the children of live epics). Its own Priority counts
   down likewise (5 to 1 with P0 to P3), and silence is how many of its days
   it has been untouched, 1 to 4. The draw is seeded by the pass's run id
   (the clock outside Actions) with a generator in the code, and logged as
   `revisit: 9 due, seed 4242, drawn: OWNER/REPO#N (weight 38880), …`, so
   the seed and the board the pass read (`--record`) reproduce it.
4. Each drawn issue in turn, until `revisit.perPass` are revisited or no
   slot is left, reads its comments and is left alone
   (`revisit OWNER/REPO#N: why`) where a writer's revisit plan comment
   changed less than its days ago, where its newest plan has not been
   dispatched (a revisit's plan would replace it) or is invalid, where its
   last revisit gave a verdict less than 90 days ago and its inputs are
   those that revisit's plan carries (`nothing changed since its revisit`,
   see [scheduling](#scheduling); the code it is checked against may have
   changed, so not for longer), or where no revisit pool
   has room. Otherwise it gets a triage run as
   [scheduling](#scheduling) starts one, `start revisit OWNER/REPO#N
   pool=P`: rechecked just before (with the same holds as step 2), its plan
   posted after `The board pass asks a triage run to revisit this issue`
   and dispatched by the plan protocol, within `--max-dispatch`, WIP and
   pacing. That comment is the record of the revisit; the dispatch record
   keeps it from running twice.

The run's brief asks it to check the issue against today's code and board
and do one of: close it as done or obsolete, citing the evidence; post an
implement plan for what is left; or, for a held issue, restate its question
with today's facts, or say how the evidence answers it. Its outputs go
through agentic-job's check and apply like any triage run's, so a close
happens only where the caller's bounds for its triage runs allow one; the
pass itself closes nothing for it but on a verdict with `triageClose`. With
`triageFollowUpDays` the brief also asks for a verdict, and the revisit's
plan is then followed up as any triage plan is.

## The weekly sweep

Under the triage scope `epics` no issue outside every live epic is triaged
on its own (see [scheduling](#scheduling)), so one sweep a week looks at
them together (agent-board#431). With `sweep` set (off unless set), stage 4
ends, after its starts and revisits, with the sweep. Where stage 4 starts
nothing (every slot taken, no pool, the weekly budget reached), an open
sweep is still applied, finished or labelled (step 4), which takes
no run, on a board read for it; its run is not started, no new sweep is
filed, and an epic its reply names is read as stage 4 would read it, where
it is a parent on the board:

1. Before stage 4 reads its candidates, the pass looks in
   `sweep.repository` for the newest issue of the bot's whose body starts
   with `<!-- agent-board-sweep v1 -->`: among its open issues first, else
   among those filed since this week's due time, open or closed, each up
   to three pages of 100, pull requests included. It leaves that issue out
   of the candidates: its run is the sweep's to start. A list that cannot
   be read, or that goes on past three pages, fails the stage's sweep
   (`sweep error: …`): no sweep is filed or started, and the issue is then
   not left out.
2. With none open, a sweep is due from `sweep.weekday` at `sweep.hourUtc`
   each week, unless one was filed since (`sweep: this week's, URL, is
   closed; the next is due from T`). It then files one issue in
   `sweep.repository`, `Weekly sweep: N issues outside the epics`, one
   write within `--max-writes`, nothing in a preview (`sweep: file …; a
   preview files nothing`). It lists the candidates outside every live
   epic, those nobody touched for longest first (the board's `updatedAt`,
   which the board read then asks for, else when they were opened), at
   most `sweep.max`, each as a link and in one `agent-board-sweep` JSON
   block, `{"schema": "agent-board/sweep/v1", "due": T, "issues":
   ["OWNER/REPO#N", …]}`. It lists only issues of `sweep.repository` and
   of repositories read as public: an issue of another, private or of
   unread visibility, is left out (`sweep: N issue(s) outside the epics
   are in repositories not read as public, …`), since the sweep issue and
   its run's reply would show it to other readers. Only the bot's token
   files it, as only the bot's issues are found again. The pass does not
   put the issue on the board and gives it no parent; its marker, not its
   Priority, keeps it apart. So at most one sweep is filed in each weekly
   window, and none while one is open.
3. While it is open and has no plan, its one triage run starts below all
   other work, unless it lists an issue of another repository not read as
   public (`it lists an issue of OWNER/REPO, not read as public; no run
   starts`, labelled `needs-human`): with a slot left (`sweep URL: no slot free; it waits`),
   every pool of `triagePools` under its pace, room above zero by the rule
   of [scheduling](#scheduling) (`sweep URL: waits for every pool to be
   under its pace: …`), and the weekly budget not reached. It is started
   as stage 4 starts a triage run, within `--max-dispatch`, WIP and
   pacing, its plan posted after `The board pass asks a triage run to
   sweep the issues outside the epics listed here.` and recorded by the
   plan protocol (`start sweep OWNER/REPO#N pool=P`). Its brief asks for
   exactly one comment on the sweep issue, with a line per listed issue
   and one `agent-board-sweep-verdicts` JSON block, `{"schema":
   "agent-board/sweep-verdicts/v1", "items": [{"issue": "OWNER/REPO#N",
   "verdict": "done|obsolete|attach|question", "epic": …, "reason": …,
   "question": …}]}`, naming the live epics the pass read of
   `sweep.repository` and of repositories read as public (the plan is
   posted on the sweep issue), and no write to the listed issues.
4. Once its run is no longer in flight, the pass reads the newest comment
   after its dispatch record that the bot wrote, edited by nobody else,
   holding that block; a body somebody else edited, or no such reply, is
   left for a person (`sweep URL: …; a person …; label needs-human`), as
   are comments that cannot be read (past their page bound, say), a plan
   that cannot be used (invalid, or edited by another account), one with
   no dispatch record and a reply that cannot be read: the
   label, one write, is how the operator learns it is stuck. Only listed
   issues count, the first item for each, and a listed issue the reply
   has none for is a question (`the sweep gave it no verdict`). `attach` to a live epic the brief named
   attaches the issue, still open and without a parent on the board, to
   it through the sub-issue API (one that is a sub-issue of that epic
   already counts as attached); an `attach` to anything else, and an
   unknown verdict, become questions. `done` and `obsolete` are not
   closed by the pass: they are listed for the operator to close, with
   their reasons, as are the questions. A closed issue is left out; as the
   board holds open issues only, the pass reads the state of one it does
   not hold, and lists one not read as closed with its verdict, unapplied.
   The visibility of each listed issue's repository is read again: one no
   longer read as public is listed without its verdict, which may hold
   what the run read there after it turned private, and not attached.
   Then one comment on the sweep issue, whose hidden first line
   `<!-- agent-board-sweep-applied: ID N -->` names the reply and counts
   what is left, says what was attached and what is left. The pass adds
   it and then edits it, and reads only one the bot edited last: the run
   posts as the bot too, but cannot edit a comment, so a marked comment of
   its own is not taken for the pass's. With
   something left the sweep issue is labelled `needs-human`, else it is
   closed as completed. The attaches, the comment's two writes and the
   label or close are taken together within `--max-writes`, or none of
   them, and only with the bot's token; a preview writes nothing (`sweep:
   attach …; a preview writes nothing`). The
   comment ends the sweep: later passes only say it waits for the operator
   to close the issue, after labelling or closing it where a pass stopped
   between the comment and that write, and no new sweep is filed while it
   is open. The live epics are those stage 3 read in `epics.repository`
   and the parents stage 4 read.

## Reruns

A run that failed for a reason outside the work waited for a person: a
review job failed during a usage outage left a green pull request at review
required for three hours, and two failed triage runs waited 17 hours for the
operator's “Rerun failed jobs” (agent-board#396). With `reruns: true` (off
unless set), the pass asks GitHub to run a failed run's failed jobs once
more (`POST …/actions/runs/ID/rerun-failed-jobs`): the same run, inputs and
event. It does not tell an outage from the agent's own failure, so it does
this once, on the run's first attempt (`run_attempt` 1). For agent and review
runs a second failure is a person's; the attempt number on the forge records
their rerun. Required-check reruns also record the head in the PR's
`tracker-poll` marker, as described below. Only
a run created in the last day, and so ended in it, is re-run: switching
`reruns` on re-runs no old failure, a refused rerun (`-> not re-run: GitHub
HTTP status 403: …`, such as for a run too old) is not asked for again after
that day, and the workflow a rerun runs, as its first event had it, is at
most a day old. A run created earlier that failed only now, after waiting for
a runner, is a person's. A second failure is a person's at any age.
An agent run is re-run only on the conclusion `failure`: cancelling a run is
how a person stops one. The review job, which pushes nothing, is re-run when
cancelled too.

* **Review job, stage 2.** For the bot's pull request from its fork whose
  head waits with no verdict (`wait: no approving review of the head yet`),
  the pass reads the newest ten `pr.reviewWorkflow` runs on
  `pull_request_target` for the head, one request. Where the newest failed,
  no review at the head cites it, and it was created after the base last
  changed (re-run, an older one would run the old base's workflow), it is
  re-run as the bot:
  `review rerun OWNER/REPO#N SHA: the review job's run URL ended (failure)
  with no review of the head, so its failed jobs run once more -> re-run`.
  That is a write step within `--max-writes`, paced as a fix round on the fix
  pools (`-> not re-run: why`). Once a head: where any run read was re-run
  already, it is `needs-human: the review job's run URL ended (failure) again
  after a rerun, …`, and where ten were read, so that an older one re-run may
  have been left out, `needs-human: … which has more runs than the 10 read
  for an earlier rerun; …`. With `pr.reviewPools` it takes the runs the
  pass started instead ([reviews](#reviews)).
* **Required checks, stage 2 (agent-board#413).** Before spending a fix round
  or stopping the bot's pull request from its fork, rerun the Actions runs
  named by its failed checks once per head. This uses the existing failed-check
  selection: with a merge queue, required checks (or all checks where none
  are required); without a merge queue, all checks, including optional ones. Each
  job URL must be in the PR's repository; the job's run must be completed with
  `failure`, on attempt 1, created in the last day and for the current head in
  that repository. Distinct runs are rerun once, using the bot's token, with
  reads bounded by the existing check-rollup and pass request limits. An
  operator answer, stack operation, explicit queue stop or running fix round
  is not displaced.
  `check rerun OWNER/REPO#N SHA: failed jobs ci (run ID) at head SHA, … -> re-run`
  logs the jobs and head. The claim, marker and rerun requests together are
  one write step within `--max-writes`, not a fix round or agent dispatch.
  The marker records `checks_rerun: SHA`, selected `checks_runs` IDs and the
  reservation time `checks_at` **before** the rerun requests, so an
  interrupted pass or refused request cannot buy another retry; authenticated
  older markers also prevent a reset or return to that head buying one.
  Subsequent polls read those runs: stale attempt 1 results and in-progress
  retries wait rather than spending a fix round or stopping. A completed
  second failure spends a fix round or stops as before; successful retries
  wait for the check rollup to catch up, then use the normal approval and
  merge gates. A request still on attempt 1 after ten minutes, or an orphaned
  claim older than ten minutes (or without a readable time), stops for a
  person without repeating the POST. In-progress retries and stale rollups
  stop after a day from reservation. Legacy receipts without run IDs also
  need a person. A new head gets its own chance.
* **Fix, rebase and continuation rounds, stage 2.** A round whose run failed
  and pushed no new head is re-run with the dispatch token that started it,
  paced on the round's pool and within the fix bounds, before the poll would
  label it `needs-human`:
  `run rerun OWNER/REPO#N SHA: fix round 1's run URL ended (failure) and
  pushed no new head for SHA, so its failed jobs run once more (why) ->
  re-run`. That is a dispatch within `--max-dispatch` and the poll's three a
  pass, so it takes a WIP slot from stages 3 and 4. A round a broker outage
  failed is still given back first; one that failed again is `needs-human`
  (`… ended (failure) again after a rerun …`).
* **Triage and implement runs, stage 4.** Stage 4 lists the caller
  workflow's runs created in the last day that failed, the newest page (one
  request). A candidate with no person's hold or run in
  flight, whose newest plan's dispatch record names one of them, gets
  `run rerun OWNER/REPO#N: its implement run URL ended (failure), so its
  failed jobs run once more pool=P run=URL` in its turn, checked as a start
  of its plan is now: the plan's item in a work repository and not held,
  the overlap check, a WIP slot, the pool its run's title names under the
  rule of [scheduling](#scheduling), `--max-dispatch`, the recheck of the
  candidate and the plan's item, and with `leases` a lease taken at the
  request and bound to the run once GitHub accepts it. A triage plan's run
  is re-run only where the plan is the candidate's own; any other plan's, a
  stacked plan's, whose base may have moved, and a batch's extra's are held
  for a person (`needs-operator`). A refused rerun holds it (`other`, `…;
  its rerun was refused: HTTP 403: …`). One that failed again holds the
  candidate for that day (`needs-operator`, `hold OWNER/REPO#N: its
  implement run URL ended (failure) again after a rerun, so it waits for a
  person`); after that it is held or followed up as before. An epic's
  planning run keeps stage 3's own retry.

`reruns` also lets a stacked pull request go on once the one below it merged
and it was retargeted: an approval from before its base changed does not
merge it, and where GitHub reports its head behind the new base
(`mergeStateStatus` `BEHIND`, which it does where the base requires branches
to be up to date), stage 2 rebases it onto the base (`update: approved before its base
became main; …, so it is rebased onto main -> brought up to date with
main; …`, one write step, one pull request a base each pass), whose push asks
the review job for a review against the new base. A conflict is a rebase or
fix round as before; a head not behind still goes to `needs-human`.

## Start failures

On 29 October every agent run failed for four and a half hours at the same
step, before the agent session started (agentic-job's `run` said `the run did
not start: …`, its exit state 4). The pass dispatched three runs into it,
recorded each plan as dispatched, held those issues for two days, and told
nobody (agent-board#440). With `starts` set (off unless set; it needs
`epics.repository` to be `dispatchRepo`, as its issues name that
repository's runs), stage 4 does three things.

A run failed before its agent started where, in its latest attempt, the
agent's step (`Run ./.agentic-job-source/run`) failed with an annotation of
agentic-job's that begins `the run did not start` or `agentic-job run ended
with exit state 4`, or where that step did not run and the first failed
job has no failed step (a lost runner), failed at its setup or checkout,
or failed at a step listed before the agent's. An agent's step that ran
otherwise, cancelled at a timeout say, had started, whatever failed after
it. A job of the caller's own that fails at its own steps, such as a
policy refusal, would fail the same way again, so it is not one. Its first
error line is that job's first failure annotation, else the job and step,
and the breaker compares it exactly. Telling costs two reads a run, once a
pass: its jobs and that job's annotations, and for some a third, below.

A run whose agent had started fails on infrastructure too where the
inference proxy lost its token mid-run, as when its broker is redeployed:
the agent's requests are refused from then on, and its plan was not tried
(agent-board#449). agentic-job has no exit state of its own for that, so
where the agent's step failed with exit state 1 or 3 (`agentic-job run
ended with exit state 1` or `3`), the pass reads that job's log, a third
read of at most 4 MiB, for agentic-job's own line `warning: the inference
proxy at URL no longer knows this run's token (HTTP 401; did it
restart?)` at the start of a log line, after the runner's timestamp. A log
that cannot be read, gone or longer, does not say so, and a later pass
reads it again. Its first error line is then always the same, `the
inference proxy no longer knew the run's token (HTTP 401; did it
restart?)`, and lines below say the run `lost its inference token
mid-run` where others say it `failed before the agent started`. The
agent's condensed output in that log has lines of its own, so an agent
that printed that line and failed could earn its run the same one rerun
and its plan a release, each time two runs within WIP and the pass's
caps, as a broker restart would; an annotation of agentic-job's, which
the agent cannot write, would close that. Either is a run that failed on
infrastructure below.

1. **The run is re-run, and its plan not spent.** Stage 4 reads the failed
   runs of the last day as [reruns](#reruns) does. A candidate's run that
   failed on infrastructure gets the one rerun of
   [reruns](#reruns), checked as it is there, with or without `reruns`:
   `run rerun OWNER/REPO#N: its implement run URL failed before the agent
   started (LINE), so its failed jobs run once more …`. Where the rerun
   failed on infrastructure too, an implement plan's dispatch record is
   released as a refused dispatch's is: the bot edits it to say how the run
   failed, without its marker or the error, which
   readers of the issue's repository may not see. The plan then starts
   again on a later pass as any undispatched plan does (`hold OWNER/REPO#N:
   its implement run URL failed before the agent started again after a
   rerun (LINE), so its record is released and its plan starts again`), one
   write within `--max-writes`; a preview releases nothing. A triage plan's
   run is re-run but not released. A run that
   failed later is left to `reruns` as before. Only the day's failed runs
   are read, so a run that failed earlier stays spent.
2. **A breaker.** Before it starts anything, stage 4 reads the caller
   workflow's newest 20 runs, one request. Where the newest
   `starts.breakerRuns` (default 3) that ended, across issues and kinds,
   all failed on infrastructure with the same first error line, it
   starts nothing (`breaker: the newest 3 runs failed before the agent
   started: LINE (URL, …); stage 4 starts nothing until a run starts
   cleanly, and probes it from T`). A run in flight neither trips nor
   clears it. An hour after the newest run read was created or last
   started (a rerun keeps its creation time), it lets one run start to
   find out whether the cause is gone (`…; one run starts to probe it`);
   one that fails the same way keeps it tripped, and the next probe waits
   another hour. Any run that ends otherwise among those newest,
   succeeded or failed otherwise once its agent started, clears it. Stage 2's fix
   rounds are not stopped. A breaker that cannot be read holds every start,
   as an unreadable hold does.
3. **A stall alarm.** Where stage 4 starts nothing with slots free, stage 2
   and 3 started nothing either, the newest run was created or started at least
   `starts.stallAfterMinutes` (default 60) ago, and a candidate was held as
   `other` or `unreadable` (not a person's hold, nor a wait on a pull request,
   run, date, overlap or pacing, which end by themselves), it says so
   (`stall: nothing started since T, with N slot(s) free and M candidate(s)
   held as unreadable`). A quiet board then does not look like a healthy
   one.

Each alarm is one issue of the bot's in `epics.repository`, labelled
`needs-human`, whose body starts with `<!-- agent-board-alarm: breaker -->`
or `<!-- agent-board-alarm: stall -->`: the breaker's names the error line
and the runs, the stall's the time and the hold kinds but not the
candidates, whose repositories may be private. The pass finds them among
the bot's open issues there, up to three pages of 100 (more is an error,
`alarm KIND error: …`), files one where it is raised and none is open
(`alarm breaker: file "…" in OWNER/REPO`), edits its body where the text
changed (`alarm breaker: update URL`), and closes it as completed once the
breaker clears or nothing stalls (`alarm stall: close URL, cleared`): each
one write within `--max-writes`, only with the bot's token, and none in a
preview. A pass that stops before its candidates (WIP full, no pool, the
budget, another pass) leaves the stall's issue as it is.

## Reviews

The review job starts on every `pull_request_target` push, on the model the
repository's variables fix, out of sight of the pass's pacing, pools and
WIP: on 28 October about 95 reviews took a subscription to 79% of its weekly
limit with six days left (agent-board#439). With `pr.reviewPools` (off
unless set), stage 2 starts reviews itself.

For the bot's pull request from its fork into a public repository, the only
one whose review job's verdict counts, whose head waits with no verdict
(`wait: no approving review of the head yet`), the pass reads the
`pr.reviewWorkflow` runs on `workflow_dispatch` in its repository created
since the start of the previous day (UTC), one page of 100, one request a
repository a pass, and keeps those whose title is `review OWNER/REPO#N HEAD`
for the current head, optionally followed by ` (POOL)`. With none, it starts
one as the bot from the repository's default branch, with the inputs `pr`,
`head` and `pool`:
`review OWNER/REPO#N SHA: no run of the review job for the head, so it
starts -> started on POOL`. The pool is chosen among `pr.reviewPools` as a
fix round's is among `pr.fixPools`, by stage 1's reading; where every pool
is held the line ends `-> not started: every pool is held (…)` and the head
waits for a later pass. A start is a dispatch within `--max-dispatch` and the
poll's three a pass, is counted in the tally, and takes a WIP slot from
stages 3 and 4. A run in flight (`wait: the review job's run URL reviews the
head`) keeps its slot on later passes while its head waits so: stage 4
lists only the caller's workflow, so stage 2 counts it. A run that ended with no review is not
started again; with `reruns` its failed jobs run once more as
[above](#reruns), paced on the pool its title names, else on
`pr.reviewPools`, a write step as before. Where the runs fill more than a
page the head waits, rather than get a second review. A head still without
a verdict once its run is older than the read, 24 to 48 hours, gets
another. Heads are started in stage 2's order, by
repository and number; Priority does not order them yet.

The pass starts only the head it has just read. A later push leaves that
run reviewing a superseded head, whose verdict counts for nothing; the
workflow stops it (below). The merge rule's checks stay as they are: the
approval must be the review job's, at the head, citing its run and submitted
while that run ran. A `workflow_dispatch` run counts in place of a
`pull_request_target` one only with `pr.reviewPools`, only where its
`head_branch` is the repository's default branch (a tag of that name passes
too; whoever can push one can push the branch), and only where its title
names the pull request and the head. The title is the
workflow's `run-name`, made from the inputs; whoever can dispatch the
workflow can write to the repository, and is already trusted with the
verdict ([poll](poll.md)).

The callers turn it on, together (cgwalters-forge/agentic-job#2163):

* Each followed repository's review workflow takes `workflow_dispatch` with
  the string inputs `pr`, `head` and `pool`, and for it sets
  `run-name: review ${{ github.repository }}#${{ inputs.pr }} ${{ inputs.head }} (${{ inputs.pool }})`.
  It maps the pool to its agent and model as the caller's dispatch workflow
  does, reviews pull request `pr` only while `head` is its head, and submits
  its review on `head`; a `concurrency` group a pull request with
  `cancel-in-progress` stops the run of a superseded head. On
  `pull_request_target`, for the bot's pull requests from its fork, it only
  records that the head needs a review, its status, and runs no agent;
  other authors' pull requests, which the pass does not review, keep their
  review there. The bot's token needs `actions: write` there, as review
  reruns already do.
* tracker's pass configuration sets `pr.reviewPools`, in the same change
  that switches the workflows' `pull_request_target` mode: before it, the
  head gets a review on both events; after it without the key, none.

## Maintain

The operator wants about a fifth of the agent budget spent helping maintain
their projects: each day, one digest of the incoming pull requests they can
act on in about an hour (agent-board#384). With `maintain` set (off unless
set), the pass decides after stage 1 and before stage 2 whether that digest
is due, and plans its run:

1. Before `hourUtc` it is not due (`maintain: not due until T`). From then
   on, the day's first pass derives the repositories (`maintain:
   repositories: OWNER/REPO, …`). It runs two searches for the operator's
   pull requests updated in the last `repos.sinceDays` days,
   `is:pr is:public author:OPERATOR` and `is:pr is:public reviewed-by:OPERATOR`,
   each up to 10 pages of 100, the newest first; public only, as the pass's
   lines name the repositories and may be public. A search GitHub marks
   `incomplete_results`, or one that fills all 10 pages, fails the stage
   (`maintain error: …`): a partial ranking could leave a repository out
   for the day. A repository counts each pull request
   once. It is kept with at least `repos.min` of them, unless its owner is
   the operator, the bot, or the owner of `dispatchRepo` or of the digest
   repository, or it is in `repos.exclude`. `repos.include` comes first,
   then the rest by count, most first and ties by name, up to `repos.max` in
   all. Before printing names or listing pull requests, it checks every
   source repository's current visibility, including explicit includes and
   cached repositories. Anything nonpublic or unreadable fails the stage
   without naming it; a public search result alone is not sufficient.
2. The pass then reads its own plan comment on the digest issue, found on
   the forge each day, not in its state, so that a hosted pass with no
   cache advances as one with it: of the bot's comments that start with the
   `<!-- agent-board-maintain-plan v1 -->` marker (below) and were edited,
   the one changed last, read through GraphQL, which names the last editor.
   A run posts as the bot, marker and all, but can only add comments, and
   every edit made with the bot's token (the pass's records, dispatch
   records and status comments, agentic-job's run-status comment) replaces
   a comment's whole text with that writer's own, of which only the pass's
   plan starts with the marker. So a marked comment the bot edited last
   holds text the pass wrote; this rests on those writers, and on the
   digest issue being kept dedicated to maintain (step 6), not on anything
   a run says. The pass therefore adds its comment without the
   marker and then edits the plan in (step 7), and never reads a comment
   nobody edited, however much like its own. So heads a prompt injection
   wrote in a run's comment, digest, forged plan comment or not, are never
   read. Edited by anyone but the bot, or by an account GitHub cannot name,
   the comment records neither a day nor heads, as whoever may edit
   comments on the issue could otherwise keep pull requests out of review,
   and the pass's next record replaces it. With no such comment, because
   it was deleted, lost its marker or was never edited, the pass trusts no
   heads, all pull requests are due, and it adds a new comment when
   recording the next plan. A plan recorded for today ends the day (`maintain: today's plan is URL;
   the next is due from T`), whether or not its digest has come: a pending
   dispatch is never started again the same day.
   An older plan's pending pull requests are then acknowledged only where
   its digest assessed them (agent-board#400). The digest is the first
   comment the bot wrote, edited by nobody else, after the plan's first
   dispatch record by a writer, whose `agent-board-maintain-digest` block
   has the digest's schema and the plan's day. A run posts as the bot but
   cannot post before its own dispatch, and a later dispatch record, which
   a run could forge, does not count. A pull request it lists, in any
   group, counts at the full head the plan listed, which `approve` and
   `closer` must give; one it leaves out, or lists anywhere at another
   head, stays due, and no other field, such as heads a run wrote, is read
   (`maintain: the digest URL
   assessed A of P planned pull request(s); due again: OWNER/REPO#N, …`).
   With no such digest, because the run failed, posted none, posted one by
   another account or for another day, or the plan was not dispatched,
   all of them stay due (`maintain: no digest for DATE followed its
   dispatch; its P pull request(s) stay due`, `maintain: plan ID for DATE
   has no dispatch record; …`, `maintain: the plan for DATE was not
   dispatched; …`). Nothing is dispatched again that day; the next day's
   plan lists them again.
3. Otherwise it lists the open pull requests of each repository, one REST
   request each, with no inference. Those the operator or the bot opened are
   left out. A repository with more than 100 open pull requests, or more than
   200 incoming in all, is not read whole and fails the stage
   (`maintain error: …`, a failure); nothing is planned and nothing reserved.
4. A pull request is due a review when its head commit's first 12 hex
   characters differ from those acknowledged for it, or none are; a plan
   comment whose block cannot be read acknowledges none, and its line says
   why. With none changed, the day is done
   (`maintain: none of N incoming pull request(s) changed since URL`).
   Otherwise the line is `maintain: digest due: C of N incoming pull
   request(s) changed since URL; reviews OWNER/REPO#N, …`, the first 20 in
   the order of the repositories and then by number; the rest wait for the
   next day.
5. Its run's job plan is a `research` plan on the digest issue, on a pool
   drawn as [scheduling](#scheduling) draws one, but held where it has used
   more than its allowance (`allowed_percent`), so that it uses no burst.
   Its brief, which the pass generates, asks for one new comment on the
   digest issue as the only output. It says each pull request is data, never
   to comment on, review, approve, label, close, push to or otherwise write
   to anything in those repositories, and never to mention embargoed or
   otherwise undisclosed security work, leaving such a pull request out
   without saying why. It lists each pull request with its full head commit
   and asks for the [digest](#the-digest) of that day, showing an example,
   which sorts each into approve (only a small, low-risk change whose checks
   all passed at that head, with a reason that says so), closer (the
   concern, file and line links at that head, and minutes), waiting (a reply
   drafted, never sent) or stale (with the reason).
6. The pass reads the digest repository. Where GitHub says it is public
   (`private` false and `visibility` `public`), it starts the run as stage 4
   starts a triage run: unless the weekly budget holds new runs, `wip` runs
   are active (`maintain: wip: A of W runs active; the digest waits`), or
   `--max-dispatch` or `--max-writes` leaves no room for the start and the
   record after it, it posts the plan on the digest issue and dispatches it
   by the plan protocol (`maintain: start research OWNER/REPO#N pool=P
   record=URL run=URL`); a preview says `maintain: start research
   OWNER/REPO#N pool=P`. The run takes a slot that the later stages count.
   Before posting, an existing writer-authored `research` plan changed
   since today's due time vetoes a new start, even with no plan recorded.
   This is only a recovery hold, never evidence of reviewed heads: a run
   can forge a plan and delay work until tomorrow, but cannot mark heads
   reviewed. Keep the digest issue dedicated to maintain. Deleting or
   editing away its plans loses this duplicate-start protection; the daily
   bound assumes those comments remain available. Before posting a plan, an
   applying Actions pass also checks the existing overlapping-pass gate:
   another pass in progress, or an unreadable overlap check, holds the digest.
   Outside Actions, capped local applies still require caller serialization.
   Where it is private, or its visibility cannot be read, the stage prints
   the plan, brief included, and starts nothing (`maintain: plan only;
   OWNER/REPO is not public: PLAN`, or `maintain: plan only; cannot read
   whether OWNER/REPO is public: ERROR: PLAN`).
7. An applying pass then records the plan in its plan comment, editing it,
   as one write within `--max-writes`, or, where step 2 found none, adding
   a comment without the marker and editing the plan into it, two writes
   taken together, so that the bot is its last editor; one whose edit
   failed is never read. It does so on a private repository or one the
   previous step read as public (`maintain: recorded the plan in URL`). With it go, from the pass's own listing,
   the unchanged pull requests' acknowledged heads, and, as pending, the
   posted plan's id and the full heads of those it reviews, which only its
   digest can acknowledge (step 2); those left waiting are in neither.
   That ends the day, as does a dispatch whose record fails, so that the
   run is not started twice. A start that waits records nothing, and a
   later pass tries again. A failure before the dispatch transport is
   called, or a confirmed dispatch refusal (a 4xx response, including a
   final 422), also records nothing; if a plan was already posted, the
   recovery hold defers it until tomorrow. Once a dispatch request is
   attempted, a lost response may hide a start, so the plan is recorded as
   pending and the day ends. A
   preview records nothing (`maintain: record the plan on OWNER/REPO#N; a
   preview records nothing`).
8. Until the day ends, every later stage's pool choice, stage 2's fix
   rounds included, reads a copy of the usage snapshot in which a pool that
   has used more than `1 − share` of its allowance is held, where its entry
   gives both figures and does not hold already (`claude has used
   45% of the 43.4% that the due maintain digest leaves the other stages`).
   So the other stages leave the share unused, and maintain, which stops at
   the allowance, uses no more than it. The pass cannot meter one stage's
   use apart from another's, so this bounds where maintain starts, not what
   its run then spends; it starts once a day. The published snapshot is not
   changed.

The day's repositories, and whether the day is done, are kept in the poll
cache, `state`, which an applying pass writes, with `follow` set or not. A later
pass the same day with the same maintain configuration, operator, bot and
dispatch repository reuses the repositories without searching, and once the
day is done neither reads the digest issue nor lists anything (`maintain:
done for today; the next is due from T`). Configuration changes invalidate
the day's cache. The cache only saves requests: which pull requests a
digest assessed, and whether today's plan was recorded, come from the
digest issue (step 2), so a pass that lost the cache, or never had one,
searches and lists again and then advances as one that kept it. An older
cache's creation receipt of the plan comment is accepted and ignored, and
a plan comment an older pass added but never edited is not read, so its
pull requests are due once more.

**Why only a public digest is dispatched.** The run is the caller's
`research` run, which may add one comment, but on any item of its
repository, and whose logs, step summary and artifacts, which hold the
comment's text, are public in the caller's public repository. So the digest
is public in any case, and is dispatched only where its own issue is too:
the operator chose a public digest on the public tracker, already a dispatch
target ([tracker#965](https://github.com/cgwalters-forge/tracker/issues/965)).
The check reads the repository's visibility, not its name. A private digest
would need a dispatch workflow in its repository, whose bounds allow
`add_comment` there alone
([tracker#963](https://github.com/cgwalters-forge/tracker/issues/963)); until
then it stays a dry run, recorded once a day with no plan id, so that its
pull requests stay due and the plan is printed again each day.

The pass's plan comment starts with its marker, then one fenced block with
the info string `agent-board-maintain-plan` holding one JSON object,
`agent-board/maintain-plan/v2`:

```json
{"schema": "agent-board/maintain-plan/v2", "from": "2026-10-27T09:00:00Z",
 "heads": {"example/up#12": "0123456789ab"},
 "pending": {"plan": "4011223344@2026-10-27T09:12:00Z",
   "heads": {"example/up#15": "89abcdef0123456789abcdef0123456789abcdef"}},
 "plan": {"schema": "agent-board/job-plan/v1", "…": "…"}}
```

`from` is the start of the day it was planned for, from `hourUtc`; `heads`
maps `OWNER/REPO#N` to the first 12 lowercase hex characters of the head
commit a digest acknowledged; `pending` holds the posted plan's id (its
comment's id and time), or null where none was posted, and the full head
commit of each pull request the plan lists; `plan` is the job plan. A
`agent-board/maintain-plan/v1` record, which kept planned heads as if
reviewed, still counts for its day, but acknowledges no heads.

### The digest

The digest comment is a markdown summary, then one fenced block with the info
string `agent-board-maintain-digest` holding one JSON object,
`agent-board/maintain-digest/v1`. The pass reads only its `schema`, `date`
and each group's `pr` and `head`, to acknowledge heads ([step 2](#maintain)); review's Maintain
view reads it all ([review#186](https://github.com/cgwalters-forge/review/pull/186),
`src/github/maintain.ts`), and this is its schema.
`fixtures/pass/maintain-digest.md` is the example the brief shows, for
2026-10-23; in part:

```json
{"schema": "agent-board/maintain-digest/v1", "date": "2026-10-23",
 "approve": [{"pr": "up/proj#7", "head": "1111111111111111111111111111111111111111",
   "reason": "Dependency bump, lockfile only; all checks green at this head."}],
 "closer": [{"pr": "up/proj#9", "head": "3333333333333333333333333333333333333333",
   "concern": "Changes the lock order.", "minutes": 40,
   "links": [{"path": "src/lock.rs", "start": 12, "end": 30}]}],
 "waiting": [{"pr": "up/proj#10", "reply": "Thanks! Could you rebase on main and add a test?"}],
 "stale": [{"pr": "up/proj#3", "reason": "No activity in 90 days."}]}
```

`date` is the day assessed, `YYYY-MM-DD`. Each list holds at most 100
entries, and each pull request reviewed is in one: `pr` is `OWNER/REPO#N`;
`head`, in `approve` and `closer`, is the full 40-character lowercase head
commit the brief listed, at which the operator approves and the links open;
`minutes` is 1 to 480; a link's `path` is relative to the repository root,
with `start` and an optional `end` line from 1. The view refuses a digest
that breaks these rules, and skips approving a pull request whose head has
moved since. These are the run's output: the pass compares them with the
heads it planned, and never records one the run chose.

## Epic planning and recovery

A live, unheld epic is due initially, after changed intent/operator direction
or membership/state changes in its children, and never on a timer alone
(agent-board#383); body, label and Priority changes in its children are
churn, not demand (agent-board#429). Coalesce automatic changes for a day
after a request, doubled for each applied plan in a row with no actions,
up to `triageFollowUpDays`; new operator direction may bypass that
interval. An epic whose children are all closed is closed or asked about
once instead of planned. Ignore
the controller's own comments/timestamps as change triggers. Do not repeatedly
plan an unchanged empty epic. A planning run in flight holds that epic. A plan
must still match its requested intent and target preconditions; drift requires
a new plan, not overwriting changed child text. Read Priority values from the
project, never from a second configured list. New children default to its last
Priority option (the lowest priority); a plan's explicit set_priority overrides
that. Use the same derived default when verifying recovered create effects.

Use the existing dispatch record to identify the planning request/run and the
accepted epic plan's comment ID and change time to identify the answer. Pin
request, comment and change time when applying. No separate `coordinator/v1`
pending checkpoint may override the forge evidence. A completed run gets five
minutes for its answer to arrive; an unconfirmed dispatch gets six hours before
being reported unresolved. An unresolved request is retried once, six hours
after its run ended (or after the request, where GitHub named no run), since
a run that answers nothing usually failed for a passing reason; the retry's
plan comment names the request it retries, so the next pass reads it from the
forge. A retry that is unresolved too is not retried again: the epic is
labelled `needs-human` with a `Q:` in its Why, so that it reaches the
operator's queue. New operator direction or a replacement plan is the
recovery path from there.

An epic's repository is first-party, so its apply receipt follows the
[bookkeeping rule](architecture.md#bookkeeping): one comment on the epic, the
claim posted before any write and updated as writes are confirmed, readable
first. It has one line per sub-issue saying what the apply did to it, for
example `- Created agentic-job#715 (P0)` or `- Closed #611 as not
planned`, then one fenced
`agent-board-epic-apply` JSON block with the machine detail: the plan comment
ID and change time it claims, each confirmed action with the identity it
produced, the outcome, and the post-apply fingerprint. It replaces the hidden
`agent-board-epic-apply` claim and `agent-board-epic-fingerprint` markers, which
are still read on older epics.

On every pass, examine the trusted receipt **before** deciding that a plan is
still waiting. A claim means “do not replay,”
not “all actions succeeded.” Inspect its confirmed writes and refresh the
census. A successful dated apply result plus its
fingerprint records the post-apply membership/state baseline;
those writes are not fresh demand for planning. That fingerprint does not cover
body or Priority: retain/compare those facts separately from the resolved
request and actual effects.

If the final status was lost, establish completion only by checking every
action's effects against confirmed identities in the receipt and current
complete facts (including board membership, text, Priority, labels and child
plans as applicable). Do not identify a created issue solely by title. If all
effects are proved, resolve the request and use the fresh post-apply baseline.
If partial, ambiguous or unreadable, report the exact unresolved actions for a
person; retain the claim and never replay it. In particular, `Already claimed;
nothing changed.` is not success evidence, and stale local pending state cannot
freeze an epic whose apply is already proved. This observation-based recovery
is part of the first implementation, not deferred cleanup.

## Operator direction

With `direction` (agent-board#395), the operator's direction is state on the
forge: the body of one issue, a short distillation the operator and the bot
edit in place. The pass reads it once a pass and puts it, under the heading
`## The operator's direction`, in front of every brief it writes: triage and
its follow-ups, revisits, epic planning and the maintain digest. A plan written
by hand, in a comment or an issue body, is dispatched as it is.

A run that could edit the direction could steer every brief after it, so the
pass uses it only where its repository is private, is none it starts runs on
(`dispatchRepo`, `workRepositories`, `follow`, `epics.repository`) and is
outside `--fix-bounds` when that is given, and where the body was last edited
by `operator` or `bot` (its author where it was never edited). The pass
cannot read the caller's bounds for other kinds; keep the repository out of
them. A body over 4,000 characters is refused, not cut short. Any of these is
a `direction error:` line and a failure, and the pass goes on with no
direction.

The briefs are posted in plan comments, so the direction is as public as the
issues they are posted on. The record of each plan the pass writes carries the
direction's hash on a second hidden line, `<!-- agent-board-direction: HASH
-->`. An epic whose last planning request carries a hash other than this
pass's is due again, `the operator's direction changed since it was last
planned`; the request that plans it carries the new hash, so each change plans
it once. A request with no hash, from before `direction` was set, plans
nothing.

## Leases

The pass's WIP limit and pacing bound only what the pass starts; a run
dispatched by hand, by a peer agent or by the review app skips them
(agent-board#382). A lease is a slot of the runs' capacity that a run takes
before any inference, whoever started it. `agent-board admit --config FILE
--pool P --item OWNER/REPO#N --run ID` takes one with GH_TOKEN, and exits
non-zero with one line, `admit refused: …`, when it gets none; `agent-board
release --config FILE --pool P --run ID` frees the run's own. The caller's
`dispatch.yml` is not wired to them yet.

A lease is the ref `refs/agent-board/leases/SLOT` in `dispatchRepo`, SLOT
below 100, at a commit on a tree of one fixed `README` (GitHub refuses
to create an empty tree) whose message is
`{"run", "item", "pool", "taken_at", "expires_at"}`, with `"override": true`
where the operator overrode. Every pool shares the slots, so admit refuses
once there are `wip` live leases, whatever their pools and slots; and it
refuses a run on a pool, however much WIP is free, unless the published
usage snapshot gives that pool room as stage 4 reads it, its holds included
(the five-hour window used up among them), and the weekly budget, where
set, is not spent. A run that holds a live lease of the pool already, as
when admit is retried after its answer was lost, gets that lease back and
takes no second. `--override` takes a slot past `wip` and pacing (at most
100 leases in all), only with the operator's token: any other is an error.
It prints `admit: override by LOGIN, past wip and pacing`, and the lease
says so.

The lease destination `dispatchRepo` must be private: lease commit messages name
work items and remain in Git history after release. Every lease write verifies
visibility before creating any Git objects, including with `--override`.

With `usage.probe`, a fresh snapshot also publishes `probes`, the pool-to-provider
map of no-reading pools with zero requests since the broker started. Admission
lets such a pool probe without a reading, but not past the weekly budget. All
probes contend for slot zero and wait while any lease is live: this deliberately
conservative shared bound admits at most one cold probe at a time, even across
providers and passes. Missing eligibility or a stale snapshot never permits one.

A ref is never deleted. Admit tries the lowest slot no live lease holds,
when capacity remains, by creating its ref, which GitHub refuses while it
exists, or by moving it with `force` off to a child of the commit it read,
which GitHub refuses unless the ref is still there. Release and a reap move
the ref likewise, to a commit that is no lease, which frees the slot. So of
two writers that read the same commit exactly one moves it: of two admits
racing for the last slot exactly one wins, and a stale reap cannot free a
lease taken since. Losing a slot race refuses this attempt; retry admission to
read current ownership rather than risk a second lease for the same run.
Retries of one run can still take two different slots, as when a slot frees
between their reads; after taking one, admit reads the leases again and frees
all but the run's lowest, so the later of the two keeps the run to one.

A lease may be reaped once its `expires_at`, 24 hours after it was taken,
has passed, or its run has ended: completed, or `in_progress` with every job
finished as the [scheduler reads it](#scheduling) (agent-board#376). A run
that cannot be read or is not found in `dispatchRepo` keeps its lease until
it expires. Admit reaps the one whose slot it takes; stage 3 or 4 of a pass
with `leases` set reaps every one, each one write step (a preview frees none
and prints `lease: reap NAME: why; a preview does not free it`), and counts
the runs holding the rest toward `wip`, once each with the runs it lists. A
commit there that is no lease holds nothing, and a ref that is no slot is
ignored. More than 100 lease refs, or a lease that cannot be read, is an
error: capacity read without them would be guessed.

With `leases`, the scheduler also merges validated lease item identities into its
busy map and reads leases again at its final item/capacity recheck. Scheduled
implement, triage, epic and digest dispatches claim a shared slot at the actual
send boundary, so a peer admission after that recheck cannot bypass the bound.
The pending lease has `run: 0`; a named dispatch response binds it to that run by
fast forward. The caller retries admission while binding is pending. A
refused reservation sends nothing: the plan's dispatch records are released
and the item held, so a later pass dispatches it once there is room. A failed,
ambiguous or unnamed response leaves the reservation until expiry; it is never
given to an arbitrary caller merely because its item matches. This can hold
capacity for 24 hours on GitHub versions without named dispatch responses.
Reservation and response binding are part of the existing dispatch step, not
additional write steps. Admission subtracts active unleased caller runs from
available capacity (excluding the requesting run itself); incomplete caller
listings refuse admission. Every path must participate before inference for a
shared bound: arbitrary external work started without admission cannot be bounded.

## Budget tree

`agent-board budget --config FILE` reads the pass configuration and prints
what work has cost so far (agent-board#281). The first line is the board, with its
`budget.weeklyUsd`. Below it come the open epics of `epics.repository`, then
each epic's sub-issues, nested as deep as GitHub nests them. Each item shows its
`Budget ($)` number field on `board` where one is set, and its actual: the cost
of its own runs plus that of its descendants. An epic that sits under another
epic appears only there. The command is read-only and holds nothing.

An item without its own `Budget ($)` under a parent that has a budget, set or
derived, gets a share of what the parent leaves unallocated: the parent's
budget, minus the budgets its children set, minus the cost of the parent's own
runs, split equally among its children without one, open or closed, and never
below $0. Such a budget is marked `shared`. An item with no budget and no
budgeted ancestor shows none. A budgeted item shows its remaining budget,
`remaining $N`, or `over by $N` once its actual has reached its budget; a
parent whose children's set budgets exceed its own shows `over-allocated by
$N`. As actuals are lower bounds, a remaining budget and a share are upper
bounds. Epics do not share the board's `budget.weeklyUsd`: it is a rate over a
week, while actuals cover all time.

A run's cost is the `<!-- agentic-job-cost: RUN usd=N partial=B -->` line that
agentic-job (agentic-job#1945) writes into the run's status comment on its
target. It is the list price in dollars. An item's own runs are those on the
item and on every pull request that closes it (GitHub's closing references,
closed pull requests included), so its implement, fix rounds and reruns all
count. A line counts only if it stands on a line of its own, in a comment by
`bot` that nobody else edited last, and that comment also carries the same
run's `<!-- agentic-job-run: RUN -->` line, as agentic-job's status comment
does. Anyone can comment on a public issue, so this keeps a pasted line from
moving an actual, and the run marker keeps a cost line copied into the agent's
own result comment from counting; it does not stop an agent that writes both
lines on purpose. Each run counts once in the whole tree, at the
first item that names it in the order shown: a pull request that closes two
sub-issues adds its runs to the first of them only. Each actual is a lower
bound, and an `at least` marks one that includes a partial cost. Some costs are
left out without an error: a run with an unknown cost leaves no line, a status
comment written as `github-actions` is not `bot`'s, a rerun that edits a single
marked status comment replaces the line before it, and a pull request that does
not say which issue it closes is not read. Actuals cover all time, not the
week. What it reads, it reads whole: it refuses more than 100 open epics or 300
items, 1000 requests, 1000 comments on an item or pull request, a sub-issue
list, a list of more than 20 closing pull requests or a set of boards that
could not be read whole, and a `Budget ($)` value that is not a dollar amount.

`agent-board budget --config FILE --split --since TIME [--until TIME]`
(agent-board#355) prints instead the share of a window's public spend that
went to upstream work rather than to the harness, as one line of percentages
and never dollars, for example `spend: 62% upstream, 38% harness (14 and 9 runs;
2 without a cost; at least, partial costs)`. A run is in the window when its
status comment last changed in it, and the window runs to now without
`--until`. One search, `commenter:BOT updated:>=SINCE`, finds the issues
and pull requests to read, with no upper bound since an item touched after the
window can still hold a status comment from it; items of private repositories are left out, as
`changes --public-only` leaves them out. The cost lines count under the rules
above, each run once. A run is the harness's when its status comment is on an
item in `budget.harnessRepositories`, and upstream otherwise. The percentages
are of the summed known cost, and the run counts are of priced runs; runs whose
status comment has no cost line are counted apart, and a window with no cost
reads `no priced runs`. `--split` is refused without `budget.harnessRepositories`,
and so is a search that finds more than 1000 items or a read past 1000 requests.
The supervisor's daily status update can carry the same line (see
[supervisor](supervisor-requests.md#lines), `agent.passConfig`).

rounds and existing default continuation handling. Its runs use the same inline
pool definitions for pacing, by stage 1's refreshed usage like later
starts; no tiers or second pools file.

`pr.staleDays` (agent-board#325) ends the hold a stopped pull request keeps
on every item that overlaps it. A pull request of the bot's from its fork
that the poll labelled `needs-human`, and that conflicts with its base or has
changes requested (the operator's, or the review job's by its run), is stale
once the poll's stop is that many days old and the operator has not acted
since: no comment, review or review comment of theirs with text, no new head,
and the label's newest `labeled` event still the bot's. If no fix round ran
before the stop, it gets fix round 1, claimed from the stop and started as
the round on an operator's answer is (`fix: … so it gets a fix round`): the
label comes off once the run is recorded, and the old head's approval
cannot merge it until the round succeeds with a new head. Otherwise the poll
reads the label, head and operator's comments again, claims the close from the
stop as a reset or answer round is claimed, posts a new stop saying why and
closes it (`close: … so it is closed`), one `--max-writes` step; reopened, it
is left for another `staleDays`. A pull request with more reviews, checks or
labels than one query reads is left alone, as the poll waits on one otherwise. A round
on a stale stop counts as fix round 1, so a pull request gets at most one
such round before it is closed, unless a person resets it. The round
respects `--fix-bounds`, `--max-dispatch` and pacing like any other.
No additional poll optional switches are exposed in this initial pass schema;
`poll` becomes this stage rather than a separate command, so the switches
not listed here go with it at the cutover unless a need adds them.
Credentials and transport-specific provider normalization are not
per-deployment config keys. The caller enables new work by setting
`workRepositories`, `wip`, pools and usage; triage additionally needs
`triage`, epic planning `epics.repository`, and the daily maintain
digest a `maintain` section, whose run is dispatched only where
`maintain.digest.repository` is public and `wip` leaves a slot. The cutover
PR must supply those settings explicitly; merely upgrading the binary
enables none of them.

## Replay and release gate

Record sanitized, complete live facts with injected clock and expected actions,
holds, writes and dispatch count; replay the contract, not every JavaScript unit
test. Include idle/free-slot boards on **22 and 23 October**, frozen epics with
completed applies but stale pending state, partial/ambiguous applies, overlap
behind rescue drafts, under-pace and over-pace pools, and Status derivation
on every rule above. Also exercise full WIP, an infrastructure failure rerun
once and a second one left for a person, missing/stale usage, invalid latest
plans, incomplete pages, lost dispatch responses and reruns after each write
boundary. Reruns must never duplicate creates or dispatches. Document
intentional differences under the drop list; zero dispatches on an idle board
with eligible free slots and usable pools is a regression, not success.

Before production, run preview then apply in a separate staging organization
with isolated repositories/project and credentials. Verify actual receipts,
recovery after interruption, capacity and overlap holds, and a second idle pass;
compare the recorded action trace with replay expectations. This document does
not claim those fixtures or the staging run have happened.

Cut over only after approval and that gate. One caller PR replaces the old
`poll.yml` jobs with a cron, serialized apply job, pinned agent-board build and
`agent-board pass --config … --apply`; delete the replaced scripts, their tests
and Justfile recipes, and disable their wake/chain triggers. No dual apply
actors. Move supervisor/release-train starts to their own crons first, preserving
their independent authorization. Keep existing receipts; optional caches may be
discarded. Rollback is reverting that single caller PR and stopping any queued
new pass before restoring the old actor; inspect ambiguous writes, never erase
claims to force a retry.

**Deployment examples only:** the source audit below is from
`cgwalters-forge/tracker` main at `1a550cc7d5089b30b5bd1e383a2efc7a9c27759c`;
the required staging deployment for that caller is `cgwalters-forge-stage`.
Neither name is a default or an agent-board policy.

## Drop list

These are deliberate removals from the audited caller, not implied parity;
the operator decided the list on 23 October 2026
([architecture](architecture.md#reruns-and-the-drop-list)). Everything here is
dropped except the one infrastructure rerun kept from the retry entry.
Links are immutable source locations; retained semantics are described above.

* [Fill mode, issue-page/candidate caps and accelerated planning][fill]: used
  spare pace to scan outside epics; one complete board candidate set and one
  scheduling rule remove starvation and the second set of limits.
* [Requested items][requested] and [enqueue][enqueue]: reordered work, wrote
  Priority/Todo and woke poll; use ordinary board Priority and the next cron,
  with no `items` bypass or `just enqueue` recipe.
* [Operator retry pools][operator-retry] and [recorded-plan outcome retries][retry]:
  retried failed runs, inferred blockers, closed merged outcomes and escalated
  exhaustion; retain receipts, but require a replacement plan/person instead
  of another retry state machine. GitHub closing keywords remain effective.
  Kept: one rerun of a run that failed for an infrastructure reason
  ([scheduling](#scheduling)), not of an agent's failure.
* [Scheduler triage verdicts, short-body heuristic and lost-question retries][triage]:
  guessed done/design from body length and answers, closed issues, retried then
  escalated; triage now only proposes a plan/hold, once per recorded request.
* [Automatic batching and batch-release probes][batch]: bundled sibling plans
  and recycled extras; one issue per scheduled run makes capacity and recovery
  unambiguous. Existing standalone dispatch batching is not removed.
* [Coordinator checkpoints, daily UTC boundary, failure counters and empty retry][checkpoint]:
  maintained a second pending/applied history; existing request/apply receipts
  plus observed effects replace it, elapsed intervals replace the wall-clock
  boundary, and unresolved runs require inspection rather than three retries.
* [Model-written status briefs/project health updates][status]: sampled PR/run
  history and published prose; not needed to start work or recover applies.
  Keep factual pass diagnostics, not a second reporting agent.
* [Title-based missing-effect matching][effects]: inferred created identities
  after a retained claim; use confirmed receipt identities or stop as ambiguous.
* [Approved-plan assignment/label choreography][approval]: special-cased an
  assigned needs-human plan and removed its label; explicit human removal of
  holds and operator epic designation suffice, with no implicit hold removal.
* [Broker probe/outage-issue lifecycle and global preview hold][broker]: opened,
  refreshed and closed outage issues, held all actors; fresh usable usage and
  ordinary dispatch failure reporting, plus the one infrastructure rerun,
  suffice for this pass. Outage monitoring
  belongs outside scheduling, in the [broker probe](broker-probe.md); no outage-based fix-round refunds are configured.
* [Encrypted private Decisions baseline][decisions]: read/compared private
  answers on every poll; the decisions document folds into the `needs-human`
  label, which is already a scheduling hold.
* [Supervisor starts][starts] and its [due][due], [profile][profile] and
  [repeat-failure][repeat] helpers: woke/paced a separate health actor and packed
  operator tasks; relocate with that actor's own cron, not into pass.
  [Release-train starts][starts] likewise move to its own cron.
* [Comment wakes][wake], [completion wakes, successor chain and dual jobs][workflow]:
  reduced cron latency but created several clocks and capacity races; one cron
  and serialized pass suffice. Remove separate BOARD_DISPATCH/COORDINATOR modes,
  stderr parsing and inter-job dispatched-item files.
* [Branch-head builds and revision-keyed artifact restore/backoff][workflow]:
  rebuilt twice and restored cached state to sustain a chain; pin once, make
  cache optional, and let the caller cron supply cadence. Never restore fork
  artifacts as trusted cache if a caller later adds persistence.
* [Usage freshness-only workflow wake][usage-refresh], [first-page publication
  restriction][publish] and [provider cost/empty machine meters][meters]:
  skip/wake optimization and UI compatibility fields are not scheduler rules;
  refresh inline, locate the trusted comment with bounded complete reads, omit
  cost estimates and machine-only meters. Keep private-only publication,
  authenticated writer, paced-window/burst/exhaustion calculation and original
  timestamps. Do not carry an old paced reading as proof that a missing short
  window is safe; a restart without current hold facts waits.
* [Old caller configuration][config]: remove source/branch, coordinator/status,
  fill/batch/retry/tier knobs and the separate usage/pools config files. The
  initial pass also does not expose optional standalone-poll operator-comment
  relays, notification subscriptions, operator-answer label clearing,
  collaborator locking, admission envelopes, diagnostic/continuation overrides
  or custom attribution. With `poll` folded into pass they go at the cutover;
  adding them to pass later requires a demonstrated need, not silent migration.
