# Weekly digests

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

`agent-board digest --config digest.json` gathers public board changes, public
releases of followed repositories, and project status updates into a weekly issue.
The generic name leaves the publication format to the caller's templates: a blog
post is one use, not a built-in destination or writing policy. This ports the
material, issue and start steps of tracker's `weekly-blog.yml` at `3d010f1`.

Nothing writes without `--apply`. `--dry-run` explicitly selects the default:
print the assembled body and the issue creation, board placement and dispatch
requests that would be made. A new issue number is shown as `<new issue number>`;
an existing issue's body is never updated, even when the preview prints freshly
gathered material. Reads still require `GH_TOKEN` (or `GITHUB_TOKEN`). Writes use
that token; run lookup and dispatch use `DISPATCH_TOKEN` when set, otherwise the
same token. Run this from a trusted checkout, not an agent-controlled head.

## Caller configuration

All fields are required; unknown fields are refused. The following is a marked
example, also available as [a test configuration](../fixtures/digest/config.json):

```json
{
  "owner": "example",
  "project": 1,
  "operator": "example-operator",
  "bot": "example-bot",
  "follow": ["example/tool"],
  "siteRepository": "example/site",
  "title": "Weekly notes: week ending {week}",
  "brief": "Material for {week}, from {since} to {until}.",
  "task": "Write content/blog/{week}.md from this issue alone. Open a pull request that closes #{issue}.",
  "priority": "P0",
  "changesChars": 26000,
  "releaseBytes": 10000,
  "bodyBytes": 56000,
  "dispatchRepository": "example/controller",
  "dispatchWorkflow": "dispatch.yml",
  "dispatchRef": "main"
}
```

`owner` and `project` name an organization's project. `operator` is passed to
`changes`, so its newly opened pull requests count alongside the token viewer's.
`follow` lists at most 50 repositories to inspect for releases. Templates expand
`{week}` (YYYY-MM-DD), `{since}` and `{until}` (UTC RFC3339); `task` also expands
`{issue}` to the issue number. Supply the full publication and safety instructions
in `task`, and the material's introduction in `brief`. There is no built-in site,
title, brief, task, Priority, budget or dispatch workflow.

`changesChars` uses the existing `changes --max-chars` renderer: longest sections
lose their last lines first, ending with `+K more`. `releaseBytes` is at most
10,000; `bodyBytes` is at most 56,000. These byte caps keep the material below the
dispatch wrapper's task size ceiling; the caller must still leave room for its
own profile, brief and task. The generated body keeps changes, releases, then
status updates. Releases sort by repository, publication time and tag; the end of
that list is dropped to fit its share, with the source workflow's omission note.
Status updates sort oldest first; the oldest are dropped first until the entire
UTF-8 body fits, including the source workflow's note linking to the project.
If the changes, releases and omission note alone do not fit, the command fails.

## Window and reruns

The window ends on the latest calendar Sunday at 18:00 UTC and starts seven days
before that. Midweek reruns use that same completed window. On Sunday before
18:00 the command refuses unless `--partial` is given, in which case the end is
now and the brief gains a partial-material note. The start is inclusive and end
exclusive. `--partial` does not mark an already complete window partial.

Nothing from private repositories enters the changes or release sections. Each
release repository's visibility is checked before its metadata is read. Draft
and unpublished releases are excluded; prereleases count. At most ten pages of
100 releases per repository are read; a full tenth page is refused rather than
claimed complete. API and decoding failures abort. The latest 100 project status
updates are read, as in the source workflow; complete HTML comments are stripped
from their bodies, including multiline hidden controller state. Project updates
are caller-owned publication material: this does not redact private facts that
someone wrote into their visible prose.

The issue is the lowest-numbered exact title match among `bot`'s issues in
`siteRepository` (not pull requests). Its listing is also bounded to ten pages
and refuses a full last page. A closed issue or an open closing pull request
stops board placement and dispatch. Otherwise the issue is added to the board
and assigned the configured Priority, using `item add`'s existing behavior
(including Turn=Coordinator where available). Before dispatch, the latest 100
runs of the configured workflow are checked: a non-completed run whose title is
`implement REPO#N`, optionally followed by a space and suffix, prevents another
start. The request supplies `kind=implement`, `repo`, `item`, and expanded `task`.

The caller must serialize applying invocations (for example, one non-cancelling
workflow concurrency group), as the source workflow does. This command is not a
transaction or a distributed lock: a failed write leaves earlier writes done,
and reruns reuse the issue. No scheduler or caller enablement is installed here.
There are no new token permissions or agent mutation paths; this is a
credential-bearing controller command, not a command to give an agent.
